# M39–M45 补充报告：从「数据在库里」到「用户查得到」

> 完成日期：2026-10-12 ~ 2026-10-13
> 目的：M39–M45 这七轮的改动此前只存在于 commit message 与开发记录中，
> 本文统一归档。
> **贯穿主线：这七轮解决的是同一件事 —— 「表里有这行数据」不等于「用户能查到它」。**

---

## 0. 为什么值得单独写一份报告

M1–M13 建立的是**数据管道与评测体系**：抓取 → 编码 → 入库 → 检索 → 评测。
每一环都有指标、有报告、有回归测试。

但用户实际使用后连续提出三个问题：

| # | 用户原话 | 我的第一反应 | 实测结果 |
|---|---|---|---|
| 1 | 「你的中文翻译是在哪里找的 感觉像机翻」 | 数据没错 | ✅ 数据没错，**异译别名从没显示过** |
| 2 | 「还是缺失很多替身啊 第九部的替身我基本没看见」 | 确实缺数据 | ⚠️ 数据缺了，**但补完仍查不到** |
| 3 | 「还是缺失很多替身啊 比如繁荣之墓 再度失言」 | 确实缺数据 | ✅ **两个替身都在库里**，缺的是中文名 |

**三次都把「用户看不到」误判成「数据没有」。**

这个偏差有结构性原因，见第 8 节。本文先逐轮记录修了什么。

## 1. M39：异译别名不可见 + 检索过程占屏

### 问题

用户问「中文翻译像机翻」，实际输入「娃娃脸」时系统能查到 Baby Face，
**但卡片上只显示主译名「婴儿面孔」** —— 用户输入的字和屏幕上的字对不上。

### 实测

```
输入「娃娃脸」→ 命中 baby_face ✓
卡片显示     → 名称: 婴儿面孔   Baby Face · ベイビィ・フェイス
```

「娃娃脸」就躺在数据里当第 2 别名（`name_zh_variants`），**从没被展示过**。

### 修法

1. `zh_card` 透传 `name_zh_variants`，卡片补「其他译名」行
2. 标注译名**可信级别**（156 条分 4 档：官方 15 / 双源 19 / 单源 120 / 反推 2）
3. 补口语缩略名（黑安息日 / 卖鸡小子）

★ 缩略名**没有用规则生成**：对主译名跑「去 色/之/的」得 32 个候选，
但「白金星」「隐者紫」「绿法皇」中文圈根本没人这么说 ——
收录会把自造词当有效查询。改用**逐条确认的白名单**（+5 条）。

### 另一处

界面有三块检索相关内容，**只有「检索过程」卡默认展开**（铺开 6 行），
把答案挤出首屏 → 改为 `<details>` 默认收起。

★ 验证时踩到一个坑：`<details>` 收起时**内部元素仍报 `offsetHeight`**（352px），
一度误判成"折叠没生效"。改用**外层卡片高度**才看准：
收起 58.8px ↔ 展开 419.7px，与截图一致。

### 结果

别名表 571 → 576；`test_m39_zh_variants.py` 22 项通过。

## 2. M40：部数列表 + 四处「数据进了库却查不到」

### 问题

用户：「第九部的替身我基本没看见」。

### 实测

现有替身按部数分布：第3部 33 / 4部 28 / 5部 27 / 6部 25 / 7部 24 /
**8部仅 7 / 9部 0**。

根因：主数据源 `jojowiki.com/Stand_Stats` 那张表**不含第 8/9 部多数替身**。
→ 从角色页的 `|stand = [[X]]` 反查缺失清单，补 31 个。

**但补完数据后，用户仍然查不到。** 这才是本轮的重点 ——
入库成功 ≠ 用户查得到。挖出四个断链：

| # | 断链 | 根因 |
|---|---|---|
| 1 | `001/002` 顺序错 | 001 里给 `character_id` 建索引，但旧库该表无此列（`CREATE TABLE IF NOT EXISTS` 跳过），列由排在**后面**的 002 加 → `column does not exist` |
| 2 | 聚合父记录**静默覆盖母体** | `echoes/tusk` 形态组无条件补建聚合记录，与新增的 `tusk` 母体同 id → `ON CONFLICT DO UPDATE` 把 owner / 日文名 / 类型全抹掉，**不报错** |
| 3 | 部数上限写死「9」 | `OUT_OF_RANGE_PART` 把「第9部」判为"不存在的内容"→ 直接拒答。而第9部**已有 13 个替身** |
| 4 | 意图识别只认阿拉伯数字 | `INTENT_PART = r"第\s*(\d+)\s*部"` → 「第八部有多少替身」匹配不到 → 退回语义检索 → 返回无关 wiki 片段 |

★ 第 3 条还有更糟的细节：该正则**只认阿拉伯数字**，中文「第九部」不被匹配
→ **同一问题的两种写法，一个能答一个拒答**。

### 修法

- 新列的索引与 `COMMENT` 全部挪到 `002`（加列之后）
- 聚合父记录改为「母体已在 `stands.json` 则跳过」
- 部数越界判定改为只判**真正越界**（第 0 部 / 第 10 部及以后）
- `part_to_int()` 支持中文数字；新增 `part_list` 意图 + 前端渲染分支

### 结果

| 项 | 前 | 后 |
|---|---|---|
| 替身总数 | 154 | **187**（第9部 0 → 13）|
| text_chunks 入库 | 2407 | **5669** |

`test_m40_part_list.py` 34 项通过（含「第10部」必须仍拒答的反向断言）。

## 3. M41：补替身中文名（数据源全部失效后的替代路径）

### 问题

用户举了两个例子：「繁荣之墓」「再度失言」。

### 实测

**两个替身都在库里**：
- 繁荣之墓 = `Tomb of the Boom 1 2 3`（第7部）
- 再度失言 = `Big Mouth Strikes Again`（第9部）

缺的是**中文名映射**，而且是两层：

1. **完全没有中文名** —— `stand_name_zh.json` 只有 156 条，
   M40 新补的 30 个替身一条都没有
2. **只收了一个写法** —— Tomb of the Boom 库内主名是 bilibili 版
   「盛世之墓」，用户用的是萌娘百科版「繁荣之墓」→ 换个写法就查不到

第 2 条与 M39 的「娃娃脸 / 婴儿面孔」**完全同一模式**。

### 数据源排查（原有源全部不可用）

| 源 | 结果 |
|---|---|
| `jojo.huijiwiki.com/api.php` | **403**（反爬升级，原脚本靠它） |
| `zh.moegirl.org.cn/api.php` | `action-notallowed` |
| `zh.moegirl.tw` | SSL 间歇失败 |
| **`moegirl.uk/api.php`** | **✅ 可用** |

★ `moegirl.uk` 的能力：`list=search` 用**英文名**能直接搜到中文条目名
（November Rain → 十一月雨）；条目用 `{{替身信息}}` 模板，含 `title` / `别名`。

### 修法

- 新增 `fetch_moegirl_stands.py`（走 moegirl.uk，带 cache/重试/限速）
- 新增 `zh_names_manual.json`（自动抓不到的 15 条人工核实，逐条注明出处）
- `build_zh_map.py` 加载两源，**并纳入异译**（不只补主名）

### ★ 途中抓到的四个错收/回归（都不报错）

1. **英文名校验不够** —— 搜 "Lyin' Eyes" 命中「迈克尔·杰克逊《Bad》完整版1987」
2. **「含 JOJO」仍不够** —— 搜 "Enigma" 命中「Modern Crusaders」（JOJO 片尾曲），
   其 `|title=` 取到「**原版MV**」被当成译名
   → 最终判据：页面必须用 **`{{替身信息}}`** 模板
3. **2 字译名 = 日常高频词** —— 萌娘给的「**天气**」（Weather Report 简称）
   被收后，日常问句「今天天气怎么样」抽出实体「天气」→ 不再拒答
   → 只收 ≥3 汉字的译名
4. **单字名逐分支拦不住** —— Tusk 的 `|ja_kanji=タスク (牙)` 提取出「牙」，
   在 official 分支拦掉后**又从 fetched 源兜底拿回同一个「牙」**
   → 改为**出口统一过滤**

### 结果

| 项 | 前 | 后 |
|---|---|---|
| 替身总数 | 185 | 187 |
| 中文名覆盖 | 156 | **181/187（97%）** |
| 别名表 | 637 | **827** |

## 4. M42：全量覆盖核查 —— 「覆盖率」之外的第二类风险

### 转折

M41 补完中文名后，我原本打算补最后一个"缺失"的 Light Rod Stand。
**查完发现不该补**：`Light Rod Stand` / `Holy's Stand` / `Jonathan's Stand`
的日文名都是**空的** —— jojowiki 用**描述性标题**给官方未命名的替身占位，
那不是作品里的名字。

→ 于是改做更有价值的事：**逐个替身验证「到底能不能查到」**。

### 新增 `evaluation/verify_full_coverage.py`

对每个替身，把它**所有可匹配写法**（英文名 / 中文主名 / 异译）
丢进别名表，看是否都能映射回**它自己**。三类问题分别报出：

1. 完全查不到
2. **映射到别的替身**（比查不到更危险）
3. 无中文名

★ 一跑就抓到 **13 个既有问题**（都不是 M41 引入的，此前从没被发现）。

### 修的三类

**【A】judgement 彻底查不到（1 条）**

`_NON_SIMP_JP`（判"含繁体字形"的字符集）里混进了「**判**」——
而「判」在简繁中**同形**。于是正确简体译名「审判」被判成繁体写法 →
标记 `_excluded_from_matching` → **该替身无路可走**。

**【B】同一译名挂多个替身 → 张冠李戴（12 条）**

```
「华丽挚爱」同挂 Love Deluxe(第4部) / Love Love Deluxe(第8部)
「杀手皇后」同挂 Killer Queen / Sheer Heart Attack
「恶行易施」同挂 Dirty Deeds / D4C Love Train
```

别名表按注册顺序覆盖 → 搜「华丽挚爱」命中第4部（错）。

★★ **关键证据（萌娘百科）**：「**素质替身**」同时出现在「娃娃脸」和「辣妹」
两个条目的别名栏里，且两条都写着「**同为素质替身**：回音ACT3、辣妹 / 回音、娃娃脸」
—— 它是**一类替身的梗标签**（指会给本体甩脸色的替身），不是替身名。
收成别名必然张冠李戴。

→ 两级处理：
- **M42 别名归属仲裁**：译名若是 A 的主名，就从其他替身的异译里删掉
- **M42b 共享译名剔除**：一个写法若同时挂在 ≥2 个替身上，**一律不收录**
  —— 系统无法判断用户指谁，宁可让他改用主名，也不给一个"看起来对"的错答案
  （与 `detect_intent` 的 `unknown` 不兜底是同一条原则）

**【C】共享剔除误伤真译名（1 条）**

「杀手皇后」是 Killer Queen **最通行**的译名，但剔除后用户搜不到了。
→ 新增 **M42c 主名覆盖**（`zh_names_manual.json` 的 `overrides` 段，逐条注明理由）：
提为主名（萌娘对应条目的条目名就是「杀手皇后」）；
原主名「皇后杀手」降为异译并**豁免**剔除，但只保留在 Killer Queen 身上。

### 结果

| 项 | 前 | 后 |
|---|---|---|
| 完全查不到的替身 | 1 | **0** |
| 译名映射到别的替身 | 12 | **0** |

### ★ 本轮的元教训

> 覆盖率 97%，但有一条译名张冠李戴，用户拿到的是「**看似正确的错答案**」。
> 这比"查不到"更危险 —— 查不到用户会换说法，答错了用户发现不了。

## 5. M43：扩语料接入检索链路（B 方案的收益终于可见）

### 问题

用户问「还有什么可以加的」，我按实测短板排序。第一项：

问「臭氧宝贝的能力是什么」→ 返回的 6 条证据**全是无关旧块**
（strength / dirty_deeds / spice_girl），而：

```
旧语料 text_chunks.json   里「臭氧宝贝」命中 0 次
新语料 article_chunks.json 里命中 4 块
```

→ B 方案扩的语料**从未进入服务检索链路**，只活在离线实验里。

### 三层原因（逐层修）

**【1】语料路径**
`merging.build_chunks()` 硬编码读 `text_chunks.json`（2407 块）。
→ 改为运行时合并原语料 + 文章块。

★ 为什么可以合并（**实测核实**）：
- 原语料 `chunk_id` 区间 1~2407，文章块 2408~5669 → **id 空间不重叠**
- 评测集 `eval_set.json` 的 **55 个 gold 全在 43~2405**，0 个落在新空间
  → 合并后评测集照样有效

★ 为什么不直接重写 `text_chunks.json`：`merging.py` 开头已写明 ——
评测集 T4/T5 直接引用 `chunk_id`，覆写会毁掉评测。

**【2】★ 向量索引缓存命中旧文件（最隐蔽）**

缓存 key 是 `m3_bge_m3`，而 `index/m3_bge_m3.pkl` 是 **10-03** 生成的
—— 那时还是 2407 块 → 服务**命中了旧索引**。

表现极具迷惑性：`health` 的 `n_chunks` 来自 chunks 列表（显示 5669 ✓），
但向量索引其实是 2407 块的 —— **两个来源不一致，界面看不出来**。

原注释已经警觉「缓存 key 必须含合并参数」，但没考虑**语料内容本身变化**。
→ key 加**语料指纹**（块数）。

**【3】★ 新补的替身根本没有文章块**

即便前两层修好仍是 0 条。根因：B 方案抓取（268 页）是在
**补第 8/9 部替身之前**做的，那时库里只有原 154 个替身。
实测缺口 **33 个**（第7部1 / 第8部19 / 第9部13）。

→ 重跑 `fetch_articles.py`（断点续抓）：命中 84 页，累计 352 页 / 6.74 MB。
★ 顺带修一个脚本 bug：该文件用了 `sys.path.insert` 却没 `import sys`。

### 结果

| 项 | 前 | 后 |
|---|---|---|
| 语料字符 | 69.6 万 | **355.9 万（×5.11）** |
| 块数 | 2407 | **6761** |
| 有文章块的替身 | 151/187 | **184/187** |

端到端实测：臭氧宝贝 / November Rain / 秋日落叶 / 奇迹于你
→ 证据来源全部命中正确替身。

## 6. M44：元数据消融实验 —— 原假设被证伪

### 原本要验证什么

用户最初问「数据库感觉有点少啊 真的适合做成 rag 吗」。
当时的回答是"问题不在规模，在语料的规整程度"（语料带 `stand_name`/`section`，
BM25 靠关键词就能定位，向量使不上劲）。

但这只是**论点**。本实验想把它变成证据。

### 实验

同一批 46 条有 chunk-gold 的评测问题：
- **A 完整**：文档文本 = `content + stand_name×2 + section`
- **B 消融**：文档文本 = `content`

### 结果：假设被证伪

BM25 绝对性能确实垮了（符合预期）：
```
recall@1   0.0870 → 0.0435  (−4.35pp)
recall@5   0.3696 → 0.3043  (−6.52pp)
recall@10  0.7174 → 0.6087  (−10.87pp)
```

**但 hybrid 相对 BM25 的增益没有上升，反而归零**：

| 条件 | @1 | @5 | @10 |
|---|---|---|---|
| A 完整 | +0.00 | **+4.35** | −4.35 |
| B 消融 | +2.17 | **+0.00** | −2.17 |

### 为什么

RRF 融合的增益来自**两路检索器看到不同的信息**。

- 条件 A：BM25 看 `content+元数据`，向量看 `content` → 信息**有差异** → 能互补
- 条件 B：BM25 也只看 `content`，向量也只看 `content`
  → 信息**高度重合** → 融合失去意义

消融不是"剥夺 BM25 的优势让向量顶上"，而是"**让两路退化成同一路**"。

### 与 M41 答案级判分合并，得到统一结论

| 实验 | 操作 | 增益变化 |
|---|---|---|
| M41 | 语料扩大（2407→5669），BM25 因候选池稀释变弱 | +2.17 → **+8.70** |
| M44 | 抹掉元数据，BM25 与向量信息重合 | +4.35 → **+0.00** |

> **融合增益 = f(两路检索器的信息互补程度)。**

这比原来的「f(非结构化程度)」和「f(规模)」都更准，
也解释了为何本项目 BM25 单独就很强（语料自带元数据 → 信息量已接近向量）。

★ 结论分支写了**三分**：成立 / 无变化 / 证伪 —— 证伪时不粉饰。

## 7. M45：M38 遗留两条

### 遗留一：形态链断裂

实测定位（不是笼统"待修"）：
- `stand_forms.json` 146 条，**`parent_id` 一个都没有** → 链根本没连
- echoes / tusk 的 **7 个形态成员在表里完全不存在**
- 它们在 `stands.json` 里是 `form_count=0, form_chain=[]`
- ★ **但六维数据是齐的**（`stand_stats.json` 里有 `pwr`/`spd`/... + `*_raw`）

→ 一句话：数据都在，只是**从没建进形态表**。

```
echoes__f0=ACT1(base) → f1=ACT2 → f2=ACT3
tusk__f0=ACT1(base)   → f1=ACT2 → f2=ACT3 → f3=ACT4
```

实测递进合理：Echoes `E/E/B/B/C/A → C/D/B/B/C/A → B/B/C/B/C/A`；
Tusk `E/E/E/B/E/A → … → A/B/C/A/B/E`（ACT4 明显跃升）。

★ 顺带发现 `load_db` **漏读该字段**：`stand_forms` 的 INSERT 根本没写 `parent_id`
—— 即便 JSON 里有值，DB 里也永远是 NULL（schema 早已定义该列并带外键）。

### 遗留二：角色日文名 0%

`characters.name_ja` 178 条**全 NULL**。但数据**早就在手上**：
B 方案抓的 168 个角色页，每个的 `{{Character Infobox}}` 都带
`|ja_kanji = 空条 承太郎`，只是**从没被提取过**。

→ 新增 `extract_character_ja.py`（**零新增抓取**），提取 163 条：
**覆盖率 0% → 92%**。
未覆盖的 13 个是抓取时拼接的脏角色名（如
`'Caravan SeraiChakaFour Unnamed miceKhan...'`），非真实角色。

| 角色日文名 | 0 / 178 | **163 / 178（92%）** |

## 8. 贯穿七轮的结构性教训

### 8.1 为什么我三次把「用户看不到」误判成「数据没有」

因为**静态校验与用户入口用的是两套东西**：

| | 静态校验用的 | 用户实际用的 |
|---|---|---|
| 查替身 | `SELECT count(*) WHERE part=9` | 「第九部有哪些替身」 |
| 查中文名 | `len(stand_name_zh.json)` | 「繁荣之墓」 |
| 查内容 | 语料里有这块 | 检索能否召回它 |

**左边全绿，右边可能是 0。** 上面七轮修的断链，静态校验一个都发现不了。

→ 对策：新增 `verify_full_coverage.py`（逐替身验证"能不能查到"），
并把端到端验证固定为**用用户真实问法**，而不是程序化 SQL。

### 8.2 静默错的清单

七轮修的问题里，**只有 1 个是硬报错**，其余全是静默的：

| 类型 | 例子 | 危险之处 |
|---|---|---|
| 静默丢数据 | 聚合父记录覆盖 tusk 母体 | 不报错，数据没了 |
| 静默答错 | 「素质替身」命中 Baby Face | 不报错，答案看似正确 |
| 静默拒答 | 部数上限写死「9」 | 不报错，第9部直接说"不存在" |
| 静默用旧数据 | 向量索引缓存 key 不含语料指纹 | `n_chunks` 显示对，索引是旧的 |

### 8.3 「写死数字」这个坑踩了三次

`load_db` 的 `expect` 里：
- `stands: 156` → 补第 8/9 部后失效
- `text_chunks: 2407` → 接入文章块后失效
- `stand_forms: 146` → 补形态链后失效

→ 现在全部改为**从磁盘推导**。
