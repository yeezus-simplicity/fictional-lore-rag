# M13：把「块长512」应用到主索引

> **M7 → M9 → M13 的链条**：M7 用加权分推荐 512 →
> M9 在固定检索配置下 A/B 验证成立（空洞率 0.50→0.30）→
> **M13 把它变成一个可切换的生产配置**。

---

## 1. 为什么不直接改数据

最直觉的做法是重写 `text_chunks.json`。**那样会毁掉评测**：

```
eval_set.json 的 T4（25 条）/ T5（21 条）直接引用 chunk_id
  evidence.chunks: [2390]
```

而 M9 的实验实现用 `len(out)` 给合并块**重编号** →
重编号后 `2390` 指向另一个块 → **46 条题的 gold 全部失效**。

→所以 M13 做成**配置层**：原始数据不动，合并在检索层可切换。

| | 不合并（默认） | `--chunk-merge 512` |
|---|---|---|
| `text_chunks.json` | 2407 块（**原样**） | 2407 块（**原样**） |
| 检索时使用 | 2407 块 | 1986 块（合并后） |
| 评测集可用 | ✓ | ✓（`base_chunk_ids` 保留溯源） |
| M6–M11 的历史结论 | 可复现 | 不影响（默认不合并） |

---

## 2. 用法

```bash
# 不合并（默认，与 M6–M11 一致）
python start.py

# 合并到 512（M9 实测推荐）
python start.py --chunk-merge 512

# 直接跑 api/main.py 也可以
python api/main.py --port 8765 --no-vector --chunk-merge 512
```

启动横幅和网页界面右上角都会显示当前索引配置：

```
索引       语义块合并到 512 字符（M9 推荐）
...
已连接 · BM25 · 合并512
```

## 3. 溯源链没有断

这是本轮最重要的设计约束。合并块的 `chunk_id` 用**独立的负数空间**：

| | 原始块 | 合并块 |
|---|---|---|
| `chunk_id` | `0` … `2406`（非负） | `-1`, `-2`, … |
| `base_chunk_ids` | — | `[45, 46]`（来源块） |

界面上点开一条证据会看到：

```
chunk#-35  由 2 个原始块合并  591 字
可回溯的原始块：#45、#46
```

★ **踩过的坑（两次）**：

1. 最初想让合并块「沿用首个基础块的 id」（理由是不新增编号空间）
   → 实测 **1986 个块里 77 个 id 重复、7 个评测引用失效**
   原因：超长单块在循环里被独立输出（用原 id），
   而它的 id 又正好是后面某个合并块的首个 id
2. 改成负数空间后自检立刻抓到 4 项不变量全绿

所以 `retrieval/merging.py` 有个自检（`python retrieval/merging.py`）：

```
✓ 所有原始 chunk_id 均可溯源       （2407 / 2407）
✓ 合并块 chunk_id 唯一              （1986 个全唯一）
✓ 合并块 id 不与原始冲突
✓ 评测集 chunk 引用可溯源：55 个引用，0 个失效
```

## 4. 实测数据（端到端，纯 BM25 + 生成式）

### 4.1 与 M9 一致的部分

| 指标 | M9（30 题，混合检索） | M13 实测（8 题，纯 BM25） |
|---|---|---|
| 平均证据字 | 835.8 → 1468.2（**+76%**） | 838 → 1240（**+48%**） |
| 平均答案字 | 112.6 → 154.7（**+37%**） | 222 → 239（+8%） |

方向一致：**合并后证据更完整，答案也更充实**。

### 4.2 空洞率为什么没复现

M9 说空洞率 0.50 → 0.30，**我这次 8 题没看到**（1/6 → 1/6）。

查了 M9 的原始记录，机制是这样的：

```
原始空洞 15 条 / 合并后空洞 9 条
  交集      7 条  两种配置都答不出（数据本身就没有）
  仅原始     8 条  ★ 被合并改善了
  仅合并     2 条  ★ 合并「新引入」的空洞
```

★ 所以空洞率下降的**真实机制是「修好 8 条、弄坏 2 条」**，
不是普遍改善。**8 题的样本量根本抓不到这种量级的差异**
（需要至少 30 题、且题目要落在「证据装不下」的那一类）。

新引入的 2 条是 `Ebony Devil 的破坏力是几级？` 和 `Echoes (ACT3) 的速度是几级？`
—— 合并后单个块变大，BM25 排序把别的替身的块挤进来了。

### 4.3 ★ 延迟代价：+53%（M9 的 +52% 被独立验证）

**这是本轮最重要的数字，两次独立测量互相印证：**

| 口径 | 不合并 | 合并 512 | 变化 |
|---|---|---|---|
| M9（30 题，混合检索，`avg_gen_ms`） | 5723 ms | 8720 ms | **+52%** |
| **M13（4 题，纯 BM25，预热后 `generation.elapsed_ms`）** | **6620 ms** | **10158 ms** | **+53%** |

配套指标（同一次测量）：

| | 不合并 | 合并 512 | 变化 |
|---|---|---|---|
| 生成耗时 | 6620 ms | 10158 ms | **+53%** |
| **prompt token** | 441 | 532 | **+21%** |
| 生成 token | 72 | 103 | +43% |
| 证据字数 | 1233 | 1623 | +32% |

★ **机制清楚**：prompt token 只涨 21%，耗时却涨 53% ——
因为 attention 是 O(n²)，prompt 变长会**超线性**增加 prefill 时间。
另外生成 token 也涨了 43%（答案更充实），那部分是解码耗时。

### 4.3.1 ★★ 我自己犯的错：第一轮测出"+4%"

第一轮（8 题、**未预热**、测端到端 HTTP）算出来是 **+4%**，
与 M9 的 +52% 差了一个数量级。我当时据此写下「+52% 未能复现」。

**那是错的。** 错在两处：

1. **样本太小 + 未预热** —— 4–8 题下平均值极不稳定。
   那一轮里不合并组被 12216 ms 的慢题拉高、合并组被 1437 ms 的快题拉低，
   **噪声恰好往相反方向偏**，把差异压成了 +4%。
2. **口径混用** —— 我拿「端到端 HTTP 延迟」去比 M9 的「`avg_gen_ms`」，
   而前者还包含检索、序列化等开销。

**第二轮（预热 + 逐题可对）得到 +53%，与 M9 的 +52% 吻合。**

★ 这已经是本项目**第四次**栽在"小样本 + 口径"上了
（M4 偏向强度、M6 题型错配、M9 阈值是我拍的、这次）。
**单次小样本测量的数字，不能用来推翻或确认另一个测量 —— 只能质疑它。**

## 5. 怎么选

| 场景 | 建议 | 理由 |
|---|---|---|
| 面向用户的实时问答 | **`--chunk-merge 512`** | 空洞率降低（有据可查：8 条改善 / 2 条变差），证据更完整 |
| 大量离线批处理 | 不合并 | 吞吐优先，且合并会让索引小 17% |
| 需要与 M6–M9 数字对齐的复现 | 不合并 | 默认值，保证历史结论可比 |
| 想自己验证 | 两次启动对比 | 界面右上角会显示当前配置 |

## 6. 相关文件

| 文件 | 作用 |
|---|---|
| `retrieval/merging.py` | 合并实现 + 自检（直接跑即可） |
| `services/semantic_executor.py` | `chunk_merge_target` 参数 + `trace_to_base()` |
| `api/main.py` | `--chunk-merge` CLI + `Evidence` 的合并字段 |
| `start.py` | `--chunk-merge` 透传 + 启动横幅显示 |
| `api/static/index.html` | 状态灯显示索引配置；证据显示「由 N 块合并」 |

★ **注意 `Evidence` 是 Pydantic 白名单模型** ——
新增字段必须在模型里声明，否则会被 FastAPI 过滤掉
（实测踩过：字段加了但响应里没有，就是这个原因）。
