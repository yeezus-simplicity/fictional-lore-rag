# M66 人物背景报告：「东方仗助是谁」现在答得出来了

> 完成日期：2026-10-15
> 承接 M65（地点维度）。用户最初的诉求是两半：
> **「补一下人物的背景」+「安杰罗岩 / 勒索之路 / 恶魔掌心这些特色地点」**。
> M65 做了地点，本轮补上人物背景这一半。

---

## 1. 为什么之前答不了

角色页**一直都在语料里**（168 页，中位 2.2 万字符，含 `Personality` / `Relationships` /
`Abilities` 章节），但：

| 层 | 现状 |
|---|---|
| `characters` 表 | 只有 5 个字段（character_id / name_en / name_ja / part / stand_ids）—— **没有简介** |
| 路由器 | 「东方仗助是谁」**不命中任何规则**：没有六维词、没有"替身"（DOMAIN_HINT 全落空）， 而 `是谁` 也不在 SEMANTIC 里（那里只有 `是什么`）|
| 结果 | 落到默认 `structured` → 执行器解析不出 → 降级语义检索 → 返回一段没头没尾的原文 |

**所以本轮要补的是：把角色页里本来就有的东西，变成可查、可看、可追溯的档案。**

---

## 2. 数据里有什么（都是源站原文，不加工）

**角色的 Infobox 字段极全**（实测一个角色 35–50 个字段）：
`ja_kanji` / `ja_romaji` / `alias` / `stand` / `age` / `birthday` / `gender` /
`height` / `weight` / `blood` / `nation` / `occupation` / `family` / `affiliation` /
`status` / `mangadebut` / `animadebut` / `seiyuu` / `voiceactor` / `namesake` …

**而且正文首段本身就是「人物背景」**，不需要我改写：

> *"Mariah is a secondary antagonist featured in the third part of the
> JoJo's Bizarre Adventure series, Stardust Crusaders, specifically the
> "'Bastet' Mariah" story arc."*

→ 于是有了三段可直接用的原文：**简介（lead，168/168）** ·
**背景（`Background` 节，106）** · **性格（`Personality` 节，162）**。

---

## 3. ★ 两条硬规则怎么落地

### 3.1 不机翻

简介/背景/性格保留 **英文原文**，中文只给**结构化事实**（中文名 / 替身 / 部数 /
性别 / 职业…）。这与 M32 中文摘要卡、M65 地点卡同一口径：
**机器翻译会破坏「证据可追溯」这个立身之本。**

界面上做成**默认收起、点开看原文**的折叠块，并标出语料块号。

### 3.2 每条都要能回查语料块

`bio_chunk_id` / `background_chunk_id` / `personality_chunk_id` 直接指到
`article_chunks.json` 的块（角色页切块时 `character_id` 已落在块上）。

**★ 块号查找是两级**（我第一版只做了第一级，实测 4 个角色拿不到块号）：

```
① 按 (角色, 节名) 精确找
② 找不到 → 拿这段原文的前 60 字符**去块里搜**
```

原因：语料块是按 `min_len=200` 合并出来的，**一个短的 `Background` 节会被并进上一块**，
那一块的 `section` 就成了别的名字。第二级保证"指到的一定是真正含有这段文字的那一块"，
而不是猜一个。修完后 **168/168 都有块号**。

---

## 4. ★ 部数：源站推断会把「上一部客串」算错

判部沿用地点那套（`mangadebut` 的章节编号区间，`from build_locations import part_of`
—— **不复制一份**，避免两处口径慢慢分叉）。

但**角色**多一个坑：

| 角色 | 源站首次出场 | 实际主要登场 |
|---|---|---|
| Jotaro Kujo | **Chapter 113（第 2 部最后一章，露个脸的伏笔）** | **第 3 部主角** |
| DIO | Chapter 1（第 1 部） | 第 3 部主要登场 |
| Muhammad Avdol | Chapter 115（第 2 部末） | 第 3 部 |

168 个里有 **9 个**属于这种情况。

→ 处理方式：**DB 的 `characters.part` 优先**（既有、已被前几个里程碑验证），
源站推断只作兜底；**两者不一致时把差异写出来**：

> 空条承太郎 · 第 3 部
> *按首次出场算是第 2 部（Chapter 113），主要登场为第 3 部*

★ **不静默丢弃**——否则用户看到"第 3 部"会以为数据错了。

## 5. ★ 解析踩的坑（都是"看着有值、其实是脏的"）

M65 已经在这类坑上花了很大篇幅（非贪婪截模板 / 空字段吞下一行 / 残留 `]]`）。
本轮又碰到**四个同族**的：

### 坑 1：嵌套模板 —— 逐层正则只吃得掉一半

`S` 模板里嵌链接、链接里又嵌 S 模板：

```
{{S|Latin Spanish Dub, [[Stone Ocean (Anime)|SO, {{S|ep. 12}}]] only}}
```

`[^}]*` 遇到内层 `}` 就停 → 清理后剩下 `Sergio Becerril ]] only` 这种残句。
→ 改成**按括号配对扫描**（`_strip_templates`）。

### 坑 2：`{{cvt|185<ref …/>{{CharSheet}}|cm|ftin}}` —— 值直接丢了

同样是嵌套：`cvt` 里嵌了 ref 与 `CharSheet`。逐条正则取不到值，
**DIO 的身高整个消失**。
→ 改成一次配对扫描 + **内层先展开**的 `_expand_simple_templates`：
按模板名取值（`cvt`→数字、`Gender`→性别、`W`/`Ruby`→文本），未知模板整段丢弃。

★ 关键教训：**不能"先转换再删"就一定安全** —— 真正的要求是
**「按配对扫描，且内层先展开」**。逐层正则在这两种写法上都会栽。

### 坑 3：源站自己写错的括号

```
|status = Retired {{S|Part 7}}}}      ← 4 个右括号
```

扫描器吃掉配对的 2 个，剩一对孤儿 `}}` → 用配对扫描做兜底收尾。

### 坑 4：图片残片成了"第一段"的开头

`Josuke` 的 `Personality` 首段开头是 `|260x260px|alt=]]`（源站 File 链接的一截）。
→ 清洗时先摘掉媒体残片，再取段落。

### 坑 5：半截模板会把**错误的词**留在答案里

`Diego Brando` 的源站首段是
`commonly referred to as {{Ruby|Dio|ディオ}}'''}}, is a primary antagonist` ——
`'''` 后面多了一个 `}}`，配对就断了。清洗后留下 `{{Ruby`，
去掉大括号后答案里就出现 **"referred to as Ruby"（真值是 Dio）**。

→ 规则：**宁可少一句，不留错词** —— 连同它后面到下一个逗号/句号的内容一起去掉。
★ 顺序很重要：这条必须在 `replace("{{","")` **之前**（我第一版写在后面，规则匹配不到，
Ruby 还是留在答案里）。

### 我自己的检查也差点放过

自检最初只查 `{{`/`[[`/`<ref>`/`<br>` → **URL 与 `]]` 漏网**
（`seiyuu` 字段是 `[http://myanimelist.net/… Yuki Ono]` 这种写法）。
→ 判据补上 `https?://` 与 `]]`。**最终：5712 个字段残留 wiki 标记 0 处。**

## 6. 前端：一个同族 bug 的**第二次**出现

M65 已经栽过一次「内联 onclick 里的引号提前闭合 HTML 属性」。
本轮加角色卡时又碰到了**同一个坑的另一种形态**：

```html
onclick='ask("Satoru Nakae's Apartment 是什么地方")'
                    ↑ 撇号把单引号属性提前闭合
```

而**地点列表**（M65 写的）用的正是这种写法 —— 也就是说
**M65 只修了我自己发现的那一处，列表那处还留着同样的隐患**。

→ 统一改成 **`data-ask` + 事件委托**：HTML 里只放转义后的值，
JS 侧挂 `onclick`。**无论名字里有什么引号都不会坏。**

顺带把「相似替身」那处从 M32 起就带着同样隐患的内联 onclick 也改掉了。

**真浏览器验证**（Playwright）：

| 检查 | 结果 |
|---|---|
| 「东方仗助是谁」→ 渲染出「答案 + 角色资料 + 检索过程」 | ✓ |
| 卡含 中文名/英日名/罗马字/其他译名/别称/第4部/替身/12 项事实字段 | ✓ |
| 三段原文折叠（简介/性格）标出语料块号 | ✓ |
| **点「使用者」→ 进入角色卡** | ✓ |
| **点带撇号的地点条目 `Satoru Nakae's Apartment` → 正常跳转** | ✓ |
| 「第 4 部有哪些角色」→ 25 个可点名单 | ✓ |

| 局限 | 说明 |
|---|---|
| **DB 178 vs 档案 168** | `characters` 表有 178 行，其中 **10 行没有独立角色页**（它们来自 stands 的 owner 字段）。这 10 行的名字还暴露了一个**既有数据质量问题**： |
