# M70 报告：两个用户反馈暴露的两类缺陷 —— 抓取盲区与同名歧义

> 完成日期：2026-10-16
> 触发：用户两条实测反馈
> 「比如勒索之路我记得不单单是一个地方 他是有替身」
> 「我搜索 lisalisa 二乔的母亲 并不会返回结果（没有检索到）」

---

## 0. 一句话

两条反馈都不是「数据缺一点」，而是各暴露了一个**结构性问题**：
抓取名单有一个看不见的盲区（「不是替身持有者的角色」永远进不来），
实体模型没处理同名歧义（「勒索之路」既是地点也是篇章）。

---

## 1. 反馈一：Lisa Lisa 检索不到

### 1.1 查证过程

| 检查项 | 结果 |
|---|---|
| 源站有独立条目？ | **有**（`Lisa Lisa`，49,542 字符） |
| 语料里提到过？ | **35 处**（在 Joseph 的角色块里） |
| 523 个已抓页面里有？ | **没有** |
| `characters` 表里有？ | **没有** |

### 1.2 根因：抓取名单是从业务字段反推的

`fetch_articles.build_targets()` 的角色名单一直是：

```
stands.json 的 owner_name  →  拆分  →  就是角色 target 名单
```

即「**谁是替身持有者就抓谁**」。于是有一个结构性盲区：

> **不是任何替身持有者的角色，从来不会进抓取队列。**

为什么这在第 1、2 部是致命的：**波纹时代没有替身**，
所以没有任何 `owner_name` 会提到波纹战士。实测 `owner_name` 里：

```
Jonathan Joestar          in owner_name? False
Lisa Lisa                 in owner_name? False
Caesar Anthonio Zeppeli   in owner_name? False
Kars / Tarkus / Wamuu     in owner_name? False
```

### 1.3 ★ 这个盲区和 M65 地点那个坑是同一形状

M65 时我写过：源站 `Category:Locations` 只有 30 个成员、几乎全是沙盒页，
所以改用 `list=embeddedin` 模板反查（`{{Location Infobox}}`）才拿到 159 个正文页。

**同一形状**：从业务字段反推覆盖面 ≪ 用分类/模板反查。
M65 用了正确做法，角色这一侧却一直停在「从 owner_name 反推」。
更巧的是 `Category:Characters` 也是**顶层容器**（实测只有 9 个成员、8 个是子分类），
必须逐个取 `Category:Part N Characters`。

### 1.4 修法

新增 `fetch_character_titles()`：取 9 部正传分类并集（**用户口径：只 9 部正传**）。

```
源站 9 部正传分类并集  382 个 ns0 成员
已抓（修前）            180
★ 补入                  196 个从未进队列的角色
抓取页总数              523 → 719 →（+189 篇章）908
角色档案                180 → 376
语料                    8042 → 10042 块
```

### 1.5 分类名单不干净，三类污染

实测这 382 个里混着：

| 类型 | 样例 | 处理 |
|---|---|---|
| 列表页 | `Minor Characters/Part 1` | 按 `/Part N` 形状排除 |
| 替身页（分类交叉） | `Foo Fighters`、`Weather Report`、`Anubis` | target 层按 kind 去重 |
| 组织/条目页 | `Locacaca Organization`、`List of Horses` | 抓了但**不给中文名**（见下） |

### 1.6 ★ 中文名：宁可少给，不给错的

`zh_char_pairs.json` 由「替身页 → 本体中文名」链路生成，
非持有者角色**天然不在这条链路上** → 没有中文名 → 用户打中文搜不到。

补了 `zh_char_m70_manual.json`（人工核对 JoJo 中文圈通行译名，逐条带依据+可信度），
并写 `apply_m70_zh.py` 应用。**脚本里有一道 id 校验**：

```
⚠ fu_fighters 在 characters_ext.json 里不存在，跳过（防造出指向不存在角色的中文名）
⚠ weather_report 在 characters_ext.json 里不存在，跳过
```

这两条正是分类交叉混进来的**替身**（Foo Fighters / Weather Report）。
如果不做这道校验，就会把替身的中文名「多元之神」挂到一个不存在的角色上。
**校验替身页 id 不在角色表里 → 拦住。**

人工表里另有 3 条 `confidence: "skip"`（组织页/列表页）刻意不给名字。

角色中文名 130 → **149**（另有 6 个角色是替身被拦下）。

### 1.7 顺带修的：驼峰误报

补抓后「标题可疑（疑两角色名粘连）」从 0 涨到 **4**，全是这个形状：

```
Joseph Joestar (JoJolion)     ← JoJolion 的 oJ 被当成两角色粘连
Josuke Higashikata (JoJolion)
Tomoko Higashikata (JoJolion)
Yoshikage Kira (JoJolion)
```

括号里是**作品名**（标注同名角色属于哪一部），不是人名。
修法：判驼峰前先剥掉尾部的 `(...)`。
与 M67「不用驼峰边界判 owner 粘连」是同一条教训 ——
**任何「看起来像两个东西」的规则，都要先在真实数据上跑一遍**。

## 2. 反馈二：勒索之路不只是一个地方

### 2.1 根因：源站有同名歧义，我们只建了一半

源站里 `Shakedown Road` 是**两个独立页面**：

```
地点页  Shakedown Road
  {{Hatnote|This page is for the location. For the story arc of the
              same name, see [["Shakedown Road" (Story Arc)]].}}
  |type = Car-free road | place = Morioh, Japan

篇章页  "Shakedown Road" (Story Arc)
  {{Hatnote|This page is for the location of the same name, see
              [[Shakedown Road]]}}
  |part = [[JoJolion]] | manga = {{Ch3|JJL|18|22}}
```

我们只抓了地点 → 用户问篇章的诉求（这一段里有哪些替身），
被答成「这个地点条目里写到过谁」。

### 2.2 判据做窄：全库 116 个 hatnote，只认 2 个

统计 523 页里 116 个 hatnote，分三类：

| 类型 | 样例 | 是否处理 |
|---|---|---|
| 同名 location ↔ arc | Shakedown Road、San Diego Beach | ✅ 处理 |
| 角色 ↔ 替身 | `Foo Fighters` ↔ `Foo Fighters (Stand)` | ❌ 与地点无关 |
| 消歧页 | `Name Variants` | ❌ 与地点无关 |

**只认「hatnote 里出现 story arc 且目标页带 `(Story Arc)`」**，
不泛化成「把所有 hatnote 都解析」。硬套会造出一堆无意义关联。

结果：189 个篇章页中，**恰好 2 个**能与地点对上 —— 与手工统计一致。

### 2.3 篇章数据

```
篇章 189 个，覆盖第 1–9 部（第 5 部 0）
  第1部 10  第2部 14  第3部 28  第4部 28  第6部 26  第7部 25  第8部 22  第9部 9  未标 27
章节区间 188/189 抽到（如「JJL 18-22」「SBR 1-4」）
```

### 2.4 答句怎么变

`勒索之路的替身是什么` 仍走 `location_related`（不破坏既有路由），
但答案里多一个**醒目的同名歧义提示**：

```
勒索之路  Shakedown Road —— 该地点条目正文里写到的：
  相关替身：Les Feuilles  Nut King Call  Soft & Wet  Tusk

┌ ⚠ 同名歧义：这个名字在源站里同时指一个地点和一个篇章。
│   上面列的是「该地点条目里写到的」。
│   若你想问的是「这一篇章里有哪些替身/角色」，口径不同。
│   篇章：Shakedown Road（第 8 部）· 章节 JJL 18-22
└
```

**为什么不给两套完整答案而只给提示**：篇章与「该段出场的替身」的关联
目前没有语料证据链（M65 的 `location_mentions` 只覆盖地点），
硬造一份就是违背项目「不准瞎掰，必须有语料证据」的口径。
所以先说清口径差异，不假装能答。

非同名地点（安杰罗岩等）**不给**这个提示 —— 不硬造。

## 3. 这轮踩的坑

### 3.1 `infobox()` 硬编码模板名 → 189 个篇章字段全是 None

`infobox(wt)` 内部固定找 `{{Location Infobox`。篇章页用的是
`{{Story Arc Infobox}}` → 返回空串 → `part` / `chapters` / `name_en`
**全部静默为 None**，而输出看着仍像个正常文件（189 条、一个字段没抽到）。

改成 `infobox(wt, key="{{Location Infobox")` 后立刻抽到 188/189 的章节。

**我第一次改只改了一半** —— sed 替换匹配到的行数与预期不符，
`_arc_part`/`_arc_chapters` 里的参数没加上，跑出来还是 None，
我又以为是自己判断错了。查了 `grep -n 'infobox(wt'` 才发现漏了两处。

### 3.2 没 `clean_text` → 部号一个都匹配不上

源站 `part` 字段写的是粗体链接 `''[[JoJolion]]''`，
直接拿原始值 match 部名 → 全部落空 → `part` 全 None。

### 3.3 `.strip('"')` 把内嵌引号吃掉

篇章名大量内嵌引号：`"Bastet" Mariah`、`"Green Day" and "Oasis"`。
`.strip('"')` 会剥掉**所有**首尾引号 → 变成 `Bastet" Mariah`。
改成只剥首尾**成对**引号。

（修完后我一度以为剩下 7 条带引号的是 bug，查源站才发现引号就是名字的一部分。）

### 3.4 heredoc 把 `\n` 写成 `/n`

`_arc_id` 的函数头被写成 `def _arc_id(title: str) -> str:/n        """...`
→ `SyntaxError`。老坑，第二次栽在同一类地方。

### 3.5 `characters` 表只从 owner_map 构建 → 外键约束失败

M70 补了 196 个非持有者角色，它们的语料块存在，但 `characters` 表
只从 `owner_name` 反推构建 → 没有对应行 → 撞
`text_chunks_character_id_fkey`（实测 `Key (memetaa_frog) is not present`）。

**`text_chunks.character_id` 的外键指向的是「语料块归属的角色」，
和「替身持有者」不是同一集合**。M66 时两者恰好重合，掩盖了这个问题。

修法：`load_db` 里 union 上 `characters_ext.json` 的全量角色，
`stand_ids` 仍只填 owner_map 里有的（没有替身就是空数组，不编造）。

### 3.6 构建顺序：先跑角色解析、后重建块 → 196 个 chunk_id 全丢

`build_characters` 依赖 `article_chunks.json` 查 chunk_id。
我先跑角色解析、再跑 `build_article_chunks` → 查的是旧块 → 196 个 chunk_id 拿不到。

测试直接报「缺 196 个」。**产品链的顺序依赖，又一次靠测试暴露。**

## 5. 遗留

- **篇章与「该段出场的替身/角色」还没有语料证据链**。
  要做的话需要新增 `arc_mentions`（仿 M65 的 `location_mentions`），
  按章节区间反查块。本轮只做到「说清口径差异」，不假装能答。
- 27 个篇章判不出部号（源站 `part` 字段为空），如 `Sun`、`Tusk`。
- 分类里混进来的组织页（`Locacaca Organization`）抓了原文但没建结构化实体，
  目前只能通过检索命中，不进地点/角色维度。
- 人工中文名表只补了 19 个角色（用户反馈点名的 + 主要角色）。
  剩余 357 个角色仍无中文名 —— 逐条核对需要时间，不自动音译（M41 教训）。
