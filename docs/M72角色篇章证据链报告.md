## 1. 角色 ↔ 篇章证据链

### 1.1 数据来源

```
{{Appearance|BG=SBR|BG2=SBR2
|Chapters =
{{Tabber
|Part 7|
*{{Ch|SBR Chapter 2}}
*{{Ch|SBR Chapter 3}}
...
```

实测 **368 个角色页里 355 个有**这套模板（97%）。

### 1.2 章号口径复用 M71 的共享模块

M71 踩过的坑（第 1–5 部绝对章号、第 6–9 部部内相对）在角色侧**完全一样**。
这次没有重写一遍，而是先把归一化逻辑抽到
`dataset/pipeline/chapter_numbers.py`，两侧都 import 它。

> 这个项目已经在「两份规则各写各的」上栽过四次
> （M69 词表 / M70 抓取名单 / M71 出场记录口径 / 本次角色数），
> 每次都表现为「一边修了、另一边没修，输出看着还正常」。

### 1.3 结果

```
篇章 188 个：有角色关联 187 / 区间判不出 1 / 区间内无记录 0
```

**零空档** —— 每个篇章都能答出角色。

关键案例（人工核对）：

## 2. ★ 重定向副本清理（本轮最大的发现）

### 2.1 现象

给篇章答案做质检时发现：`Shigekiyo Yangu` 出现两次、
`DIO` 和 `Dio Brando` 并存、还混进了 `Urmd Avdul/fr`。

### 2.2 根因：`redirects=1` 把重定向抓成了正文副本

`fetch_wikitext()` 用 `redirects=1`，所以抓 `DIO` 会得到
`Dio Brando` 的**正文**（125,941 字符，一模一样）。

而源站的 `Category:Part N Characters` **同时列了重定向和它的目标**
→ 同一个角色被抓成两条。

```
DIO                        → Dio Brando
Anjuro "Angelo" Katagiri   → Anjuro Katagiri
Shigekiyo "Shigechi" Yangu → Shigekiyo Yangu
Former Tama                → Tama
Elder A. Phex Brother      → A. Phex Brothers
Younger A. Phex Brother    → A. Phex Brothers
Holy Joestar               → Holy Kujo
Star Platinum: The World   → Star Platinum（段落锚点）
Tusk ACT1/ACT2/ACT3/ACT4   → Tusk
```

**12 个重定向、7 组重复、16 个页面。**

### 2.3 ★ 判定方法：只有一种可靠

试了三种，两种会给出**自相矛盾**的结果：

| 方法 | 结果 |
|---|---|
| `action=parse` 的 `redirects` 参数 | ✗ **行为不一致** —— 同一个 `Holy Joestar`，带 `redirects=0` 返回 title=`Holy Kujo`，不带又返回 `Holy Joestar` |
| `pageprops.wikibase_item` | ✗ 本 wiki **全为 None**（没接 Wikidata），区分不了任何页面 |
| `action=query&prop=revisions` 拿未解析原文 | ✓ **可靠** —— 以 `#REDIRECT` 开头即为重定向，`[[...]]` 里就是目标 |

### 2.4 还有第二条中招的路：`owner_name`

清掉页面后，DB 里仍有 6 个副本。查下去发现：

**源站在替身页把持有者写成重定向名** —— The World 的持有者写作 `"DIO"`
（而 DIO 重定向到 Dio Brando）。`owner_map` 用 `_char_id("DIO")` 造出 `dio` 行，
而分类名单那边是 `dio_brando`。

→ 修法：入库前把 `owner_name` 规范化（24 个替身中招），
用同一张表 `dataset/pipeline/wiki_redirects.py`。
**只规范化、不重写 `stands.json`** —— 那是源站原文，要留着可回溯。

效果：角色 380 → **374**，6 个副本行被清掉。

### 2.5 顺带：陈旧块清理

删掉页面后 DB 里还留着它们的块（`text_chunks` 用的是
`ON CONFLICT DO UPDATE` —— **只增不删**），而这些块仍被副本角色行引用
→ 现有的「清理已不再产生的角色行」因有引用而删不掉。

→ 加了同步语义：以本次 `all_chunks` 的 chunk_id 集合为准，多则删
（实测清理 92 条陈旧块）。

## 3. 篇章块入库（migration 005）

### 3.1 又一个「下游产物没跟着重算」

M70 抓了 189 个篇章页，但**没重跑 `build_article_chunks`**
→ 1062 个篇章块一直没生成。这是同一类问题的**第四次**。

生成后入库撞上 `chk_chunk_owner`（三类约束不认 `arc_id`）。

### 3.2 迁移踩的三个坑

**① 我重写约束时漏了 `location_id`**

003 加地点时早就把约束从两类扩到了三类（stand/character/**location**），
我在 005 里重写时只写了 stand/character/arc → **1179 个地点块全部违反约束**。

> 又一处「改写别人定过型的东西时，没有先看它现在的全貌」。

**② 迁移必须幂等且顺序无关**

`load_db --all` 反复重跑时，002 和 003 加约束的地方都会失败
（库里已有 005 认可的新归属）。→ 两处都改成「先看有没有行会违反，有则跳过」。

**③ `NOT VALID` 只是过渡，不是终点**

迁移跑在数据**之前**，那时 `arc_id` 全是 NULL，扫全表必然失败。
→ 标准模式：`ADD CONSTRAINT ... NOT VALID`（只约束新行），
数据填完后 `VALIDATE CONSTRAINT`。

（`VALIDATE` 要放在 `cur.close()` **之前** —— 我第一版放在了后面，
报 `InterfaceError: cursor already closed`。）

最终约束是**四类归属**：替身 / 角色 / 地点 / 篇章。

## 5. 顺带发现并修掉的两个解析 bug

质检篇章答案时连带发现两个**静默出错**的解析问题。

### 5.1 ★ 撇号被吃掉了（24 个篇章名全被改坏）

`build_locations.clean_text()` 里清理 wiki 粗体/斜体标记的正则：

```python
s = re.sub(r"'''?|''?", "", s)     # ❌ `''?` 匹配「1 到 2 个撇号」
```

`''?` 的意思是「1 个或 2 个撇号」—— 所以**任何单个撇号都被删掉**：

实测 **24 个篇章显示名**全被改坏（占含撇号篇章的 100%）：

```
Yoshikage Kira's New Situation  →  Yoshikage Kiras New Situation
D'Arby the Gambler              →  DArby the Gambler
DIO's World                     →  DIOs World
I'm an Alien                    →  Im an Alien
Let's Go Eat Some Italian Food  →  Lets Go Eat Some Italian Food
Narancia's Aerosmith            →  Narancias Aerosmith
The Devil's Palm                →  The Devils Palm
Ermes's Stickers                →  Ermess Stickers
Lulu's Bags' Groove             →  Lulus Bags Groove
…（共 24 个）
```

★ 影响范围**仅限篇章**：地点名用的是页面标题（`{{DISPLAYTITLE}}` 之前的
  原始 `title`），不过 `clean_text` —— 实测地点侧只 1 个 `name_romaji`
  受影响。不夸大。

**后果特别隐蔽**：库里存的是一串「少了个撇号的错名字」，
输出看着完全正常；而用户打**正确的**名字反而匹配不上 ——
`篇章 Yoshikage Kira's New Situation` 返回「没找到」，
而我一开始以为是路由问题。

修法：MediaWiki 的标记都是**成对**的（`''斜体''` / `'''粗体'''` /
`'''''两者'''''`）→ 只删**连续 2 个及以上**的撇号，单个撇号原样保留。



### 5.2 ★ 章节字段的第二种写法（1 个篇章因此完全答不出）

源站 `manga` 字段有两种写法，我第一版只处理了第一种：

```
① 区间式：  {{Ch3|JJL|18|22}}                    → "JJL 18-22"
② 首尾两点：{{Ch3|DU|105}}<br />{{Ch3|DU|112}}   → "DU 105-112"
```

第二种让第一版**静默产出空列表**（两个 match 都只有 2 段 < 3 被跳过，
fallback 的 `clean_text` 又把模板剥光）→ 该篇章 `chapters=[]`
→「区间判不出」→ 问它什么都答不出来。

修法：把同一作品前缀下的所有章号收齐取 min-max，两种写法统一成区间。

效果：**区间判不出 1 → 0**，角色侧 188/188 全覆盖。

### 5.3 源站分类不干净：如实记录「这一页是什么」

排查「13 个角色页没有 Appearance 模板」时发现，源站的
`Category:Part N Characters` 里混着**不是个体角色**的页面：

| 页面 | 实际是什么 |
|---|---|
| `Locacaca Organization` | `{{Group Infobox}}` —— 组织 |
| `Rock Human` / `Rock Organism` | `{{Group Infobox}}` —— 物种 |
| `Boomboom Family` | `{{Family Infobox}}` —— 家族 |
| `List of Horses` | 纯列表文章（无 Infobox） |

它们的内容是真的（用户可能问「岩人是什么」），所以**不删数据**，
而是新增 `page_kind` 字段如实标记，答案层据此说明
「这是一个群体概念，不是某一个人物」。

**★ 判定用 Infobox 模板名，不用关键词** —— 模板名是页面自己的结构声明，
而关键词（含 "Family"/"Group"）会误伤真人名。

**★★ 又栽在「只认一种写法」上（本轮第二次）★★**

第一版硬编码了 4 个模板名，结果 **9 个页面被判成 `unknown`**，
其中 3 个其实能识别出来（2 个是真角色、1 个是道具页）：

```
355  {{Character Infobox}}      ← 主流
  3  {{Group Infobox}}
  2  {{Character Info}}         ← ★ 别名！第一版漏了
  1  {{Family Infobox}}
  1  {{Item Infobox}}
  6  （无 Infobox）
```

→ 改成用正则匹配 `{{...Infobox}}` / `{{...Info}}` 家族，不逐个硬编码。

最终：357 character / 3 group / 1 family / 1 item / 6 unknown。

### 5.4 连带修复：重定向副本的中文名

清掉副本角色后，`zh_char_pairs.json` 里仍留着副本键
（`dio` / `former_tama` / `shigekiyo_shigechi_yangu` /
`anjuro_angelo_katagiri`），而它们身上挂着**更有价值的简称**：
`迪奥` / `猫草` / `胖重` / `安杰罗`。

`build_char_alias_table()` 用 `setdefault`，字典序在前的 `dio`
会先占据「迪奥·布兰度」→ 映射到一个**已不存在的 character_id**
→ 路由查不到 →「迪奥·布兰度的替身是什么」从 `stand_of`
退化成语义片段（实测 M21 挂了 2 项）。

→ 把副本的中文名合并到规范页 + 删掉副本键。
角色中文名 130 → **154**。
