## 1. 角色 ↔ 篇章证据链

### 1.1 数据来源

```
{{Appearance|BG=SBR|BG2=SBR2
|Chapters =
{{Tabber
|Part 7|
*{{Ch|SBR Chapter 2}}
*{{Ch|SBR Chapter 3}}
...
```

实测 **368 个角色页里 355 个有**这套模板（97%）。

### 1.2 章号口径复用 M71 的共享模块

M71 踩过的坑（第 1–5 部绝对章号、第 6–9 部部内相对）在角色侧**完全一样**。
这次没有重写一遍，而是先把归一化逻辑抽到
`dataset/pipeline/chapter_numbers.py`，两侧都 import 它。

> 这个项目已经在「两份规则各写各的」上栽过四次
> （M69 词表 / M70 抓取名单 / M71 出场记录口径 / 本次角色数），
> 每次都表现为「一边修了、另一边没修，输出看着还正常」。

## 2. ★ 重定向副本清理（本轮最大的发现）

### 2.1 现象

给篇章答案做质检时发现：`Shigekiyo Yangu` 出现两次、
`DIO` 和 `Dio Brando` 并存、还混进了 `Urmd Avdul/fr`。

### 2.2 根因：`redirects=1` 把重定向抓成了正文副本

`fetch_wikitext()` 用 `redirects=1`，所以抓 `DIO` 会得到
`Dio Brando` 的**正文**（125,941 字符，一模一样）。

而源站的 `Category:Part N Characters` **同时列了重定向和它的目标**
→ 同一个角色被抓成两条。

```
DIO                        → Dio Brando
Anjuro "Angelo" Katagiri   → Anjuro Katagiri
Shigekiyo "Shigechi" Yangu → Shigekiyo Yangu
Former Tama                → Tama
Elder A. Phex Brother      → A. Phex Brothers
Younger A. Phex Brother    → A. Phex Brothers
Holy Joestar               → Holy Kujo
Star Platinum: The World   → Star Platinum（段落锚点）
Tusk ACT1/ACT2/ACT3/ACT4   → Tusk
```

**12 个重定向、7 组重复、16 个页面。**

### 2.3 ★ 判定方法：只有一种可靠

试了三种，两种会给出**自相矛盾**的结果：

| 方法 | 结果 |
|---|---|
| `action=parse` 的 `redirects` 参数 | ✗ **行为不一致** —— 同一个 `Holy Joestar`，带 `redirects=0` 返回 title=`Holy Kujo`，不带又返回 `Holy Joestar` |
| `pageprops.wikibase_item` | ✗ 本 wiki **全为 None**（没接 Wikidata），区分不了任何页面 |
| `action=query&prop=revisions` 拿未解析原文 | ✓ **可靠** —— 以 `#REDIRECT` 开头即为重定向，`[[...]]` 里就是目标 |

### 2.4 还有第二条中招的路：`owner_name`

清掉页面后，DB 里仍有 6 个副本。查下去发现：

**源站在替身页把持有者写成重定向名** —— The World 的持有者写作 `"DIO"`
（而 DIO 重定向到 Dio Brando）。`owner_map` 用 `_char_id("DIO")` 造出 `dio` 行，
而分类名单那边是 `dio_brando`。

→ 修法：入库前把 `owner_name` 规范化（24 个替身中招），
用同一张表 `dataset/pipeline/wiki_redirects.py`。
**只规范化、不重写 `stands.json`** —— 那是源站原文，要留着可回溯。

效果：角色 380 → **374**，6 个副本行被清掉。

### 2.5 顺带：陈旧块清理

删掉页面后 DB 里还留着它们的块（`text_chunks` 用的是
`ON CONFLICT DO UPDATE` —— **只增不删**），而这些块仍被副本角色行引用
→ 现有的「清理已不再产生的角色行」因有引用而删不掉。

→ 加了同步语义：以本次 `all_chunks` 的 chunk_id 集合为准，多则删
（实测清理 92 条陈旧块）。

## 3. 篇章块入库（migration 005）

### 3.1 又一个「下游产物没跟着重算」

M70 抓了 189 个篇章页，但**没重跑 `build_article_chunks`**
→ 1062 个篇章块一直没生成。这是同一类问题的**第四次**。

生成后入库撞上 `chk_chunk_owner`（三类约束不认 `arc_id`）。

### 3.2 迁移踩的三个坑

**① 我重写约束时漏了 `location_id`**

003 加地点时早就把约束从两类扩到了三类（stand/character/**location**），
我在 005 里重写时只写了 stand/character/arc → **1179 个地点块全部违反约束**。

> 又一处「改写别人定过型的东西时，没有先看它现在的全貌」。

**② 迁移必须幂等且顺序无关**

`load_db --all` 反复重跑时，002 和 003 加约束的地方都会失败
（库里已有 005 认可的新归属）。→ 两处都改成「先看有没有行会违反，有则跳过」。

**③ `NOT VALID` 只是过渡，不是终点**

迁移跑在数据**之前**，那时 `arc_id` 全是 NULL，扫全表必然失败。
→ 标准模式：`ADD CONSTRAINT ... NOT VALID`（只约束新行），
数据填完后 `VALIDATE CONSTRAINT`。

（`VALIDATE` 要放在 `cur.close()` **之前** —— 我第一版放在了后面，
报 `InterfaceError: cursor already closed`。）

最终约束是**四类归属**：替身 / 角色 / 地点 / 篇章。

## 4. 权威计数：data_facts.json

闸门连续报「对外写 X，产物是 Y」，查下去发现两边都不是错的：

```
characters_ext.json   368 个
DB 的 characters 表   380 个   ← owner_map ∪ characters_ext 的并集
```

差的是「只出现在 `owner_name` 里、没有独立角色页」的角色。
**同一个概念有两个来源** —— 这是本项目第五次栽在「两份规则」上。

→ 单一来源：`load_db` 是唯一知道「到底入库多少行」的人，
由它写 `dataset/processed/data_facts.json`，闸门改读它。

- **Tusk ACT1-4 / Echoes ACT1-3 仍是 M1 遗留的「形态组未消解」问题**：
  `stands.json` 把它们当独立替身登记，`load_db` 为此建了聚合父记录。

  与正传编号体系对不上），已标 `note` 不猜。

- 人工重定向表 12 条：若源站新增重定向，需往 `wiki_redirects.py` 加一行并补测试
  （刻意不做运行时自动判定，理由见该模块 docstring）。
