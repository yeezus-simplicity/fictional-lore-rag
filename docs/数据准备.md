## 0.5 可选：替身图片（M17）

问属性时会画六维雷达图（**无需任何准备**，数据来自数据库）。

问替身时的图片需要联网抓取（首次约 5-15 秒/替身，之后走本地缓存）：

```bash
# 抓指定几个（推荐先抓常见的）
python dataset/sources/images/fetch_stand_images.py "Star Platinum" "Gold Experience"

# 全量 154 个（很慢，每张要3-5 秒）
python dataset/sources/images/fetch_stand_images.py --from-stands
```

**注意**
- 抓到 `images/<stand_id>/`，该目录**不在 git 里**（体积大 + 有版权），需本地重抓。
- **必须能访问外网**：jojowiki 的图片 CDN 在部分网络下不可达
  （脚本会读`https_proxy` 环境变量；没有代理会直接超时）。
- 首次问某个没抓过的替身时会**自动后台抓取**，回答**立即返回**（不等图片），
  图片抓完（约 20-40 秒）在页面底部自动出现，不必重复提问。
- 只想看文字时用 `python start.py --no-images` 关掉。
- 图片版权归荒木飞吕彦 / 集英社所有，来源 jojowiki.com，仅作技术演示。

## 0.6 中文名（替身名 + 角色名）

仓库里**已包含**构建好的中文名词典，开箱可用：

| 文件 | 内容 | 覆盖率 |
|---|---|---|
| `dataset/processed/stand_name_zh.json` | 替身中文名 | **156/156** |
| `dataset/sources/zh_names/zh_char_pairs.json` | 角色（替身使者）中文名 | **130/144** |

想重新抓取（或补新增替身/角色）：

```bash
# 角色中文名（M21）：中文维基替身表「本体」列 + 各部条目 nihongo 模板
python dataset/sources/zh_names/fetch_zh_characters.py

# 替身中文名（M16 已有）：中文维基总表 / 灰机 wiki
python dataset/sources/zh_names/fetch_zh_huiji.py
python dataset/sources/zh_names/build_zh_map.py
```

**数据来源与口径**
- 只从表格单元格 / 模板参数取值，**不做翻译、不做音译、不凭记忆填**。
  抓不到就是中文圈确实没有通行译名，**如实留缺口**（替身 0 缺口；角色 14 个缺口）。
- 繁简转换用 **opencc**（`pip install opencc-python-reimplemented`）。
  ★ 项目自带的 `aliases.simplify_zh()` 只有 16 个字符映射，**不足以转角色名**
  （「阿布德爾」不会被转换），只适合历史遗留的少量替身名。
- 角色名的 14 个缺口主要是：游戏/小说专属角色（Dija Maker、
  Escape Room Player、The Funniest Valentine…）、无名配角（Female Paramedic、
  Copy of Coco Jumbo）、以及中文维基**只用英文**的角色（Forever、Mannish Boy、
  Kenzou）。这些在维基上确实没有中文译名可查。

**注意**
- 抓取需外网。中文维基需走代理（脚本读 `https_proxy`）；
  ★ SSL 偶发 `UNEXPECTED_EOF`，脚本对每个页面重试 3 次。
- 抓完会写**本地缓存**（`_cache_wiki_stands.wikitext` / `_cache_wiki_parts.json`），
  重跑时优先读缓存 → 不重复请求维基。缓存不入库（`_` 前缀视为中间物，
  共约 650 KB，脚本可重新生成）。
- 灰机 wiki（jojo.huijiwiki.com）**不可作主力来源**：连续请求会被限流并
  升级成硬封禁（api.php + /wiki/ 全 403），M16 实测踩过。

>★ 排错提示：若界面上一直转圈或看不到图，先看 `images/_server.log`。
> 图片抓取失败不会影响文字回答，只是图片区空着。

## 2. 模型（7.3 GB，必须自己下）

### 2.1 为什么不能自动下载

本环境 **huggingface.co 被拦（返回 502）**，代码里的注释也写了这件事：

```python
# retrieval/dense.py: resolve_model_path()
★ 本环境 huggingface.co 被拦（502），必须用 fetch_model.py
  下载到 models/ 后离线加载。直接用 HF 名会触发网络请求并失败。
```

实测：没放模型时，`SentenceTransformer("BAAI/bge-m3")` 会去联网，
拿到一个非 JSON 响应，报**看起来毫不相关的错**：

```
JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

★ 这个报错完全指不到真正的原因（模型没下载），第一次遇到很难自己定位。

### 2.2 下载

```bash
# bge-m3 向量模型（2.2 GB）—— 混合检索必需
python retrieval/fetch_model.py --repo BAAI/bge-m3

# 重排模型（2.2 GB）—— 可选，只在跑 M3 重排实验时用
python retrieval/fetch_model.py --repo BAAI/bge-reranker-v2-m3

# 生成模型（2.9 GB）—— 可选，只在 mode=generate 时用
python retrieval/fetch_model.py --repo Qwen/Qwen2.5-1.5B-Instruct
```

下载后目录结构必须是：

```
models/
├── BAAI_bge-m3/config.json          ← 这个文件是「找到本地」的判据
├── BAAI_bge-reranker-v2-m3/
└── Qwen_Qwen2.5-1.5B-Instruct/
```

验证：

```bash
python -c "import sys; sys.path.insert(0,'.'); from retrieval.dense import resolve_model_path; print(resolve_model_path())"
# 应输出绝对路径（含你的用户名），而不是 "BAAI/bge-m3"
```

★ 若输出仍是 `BAAI/bge-m3`，说明没找到本地模型 —— 代码会去联网并失败。

### 2.3 首次启动会重建索引缓存（实测 217 秒）

`index/*.pkl` 不在仓库里，**首次用向量模式时会从零embed 2407 个块**。

| 场景 | 实测耗时 |
|---|---|
| 纯 BM25（`--no-vector`） | **0.1 秒** |
| 向量模式·首次（从零建索引） | **217 秒** |
| 向量模式·第二次（读缓存） | **13 秒** |

★ **首次启动「看起来卡住了 3 分钟」是正常的**，不是崩了。
不想等就加 `--no-vector`。

实测环境：RTX 系 GPU + bge-m3 fp16。CPU 上会显著更久。

### 2.4 ★ 实测验证记录（2026-10-07，干净克隆）

在一个 `git clone` 出来的干净目录里完整走了一遍：

```
① 克隆（102 文件 / 5.2 MB）
② pip install -r requirements.txt        （用已装好的venv）
③ --no-vector 启动                → 2.2 秒，首页 200，三类路由正常
④ 放入 models/                → 向量模式可用
⑤ 首次建索引                    → 217 秒
⑥ 第二次启动（读缓存）             → 13 秒
⑦ 混合检索                → 命中正确（Star Platinum 破坏力块排第一）
```

★ **结论：照着本文档做，克隆者能跑起来。**

## 3. 数据库（可选，但推荐）

数据库提供**结构化查询（六维数值）、数据浏览、冲突记录**。

### 3.1 启动

前置条件：**Docker Desktop 必须已手动启动**（本项目不会自动拉起它）。

```bash
cd docker
docker compose up -d postgres
python ../database/load_db.py --all   # 建库 + 建表 + 入库 + 验证
```

### 3.2 不起数据库会怎样

**服务不会崩，会自动降级**（这是 M10 专门做的）：

```
[api] ⚠ 数据库不可用
[api]   降级为「仅语义检索」模式
[api]   ✓ 语义问答可用（走本地索引，不依赖 DB）
[api]   ✗ 结构化查询 / 数据浏览 / 冲突记录不可用
[api]   已从 stands.json 载入 154 个替身名（仅用于路由）
```

| 能力 | DB 可用 | DB 不可用 |
|---|---|---|
| 网页界面 | ✓ | ✓ |
| 语义问答（返回原文片段） | ✓ | ✓ |
| 编造实体拒答 | ✓ | ✓ |
| 结构化查询（六维数值等） | ✓ | 提示 + 降级 |
| 数据浏览 / 冲突记录 | ✓ | 返回 error 提示 |

> ★ **而且会自动恢复**：DB 后来起来了，`/health` 每次调用都会试一次重连
> （`_try_reconnect()`），成功后结构化查询自动启用，**不需要重启服务**。
>
> 这是实测修掉的一个真问题：原先服务在 Docker 未就绪时启动，
> 就永远卡在降级态，用户只能重启服务才知道「其实 DB 早就好了」。

回归测试：`python evaluation/test_degraded_mode.py`

## 4. 依赖清单是怎么来的（可复现）

`requirements.txt` 里的每一条都是从**代码里实际的 `import` 语句**反查的，
不是手抄的。重查方法：

```bash
grep -rhoP "^\s*(import|from)\s+\K[a-zA-Z_][a-zA-Z0-9_]*" \
  --include="*.py" api/ services/ retrieval/ database/ evaluation/ \
  | sort -u | grep -vE "^(json|re|sys|os|...)$"
```

再对照实测环境的版本：

```bash
python -c "import importlib.metadata as m; print(m.version('transformers'))"
```

★ 这次重查**清掉了4 个幽灵依赖**：`FlagEmbedding`、`jieba`、
`scikit-learn`、`httpx/langgraph/prometheus-client` ——
代码里从未 import，写在里面只会让人白装。

### ★★ 一个必须知道的版本约束

**`transformers` 必须 >= 5.0。**

bge-m3 走 FlagEmbedding 的 `BGEM3` 池化逻辑，在 transformers 4.x 下
会因内部 API 变更而报错。实测 **4.x 不可用 / 5.18.0 正常**。

★ 没写下来的话，排查这个不属于你的 bug 会花掉半天。

## 5. 已知会踩的坑

| 现象 | 真原因 | 怎么办 |
|---|---|---|
| `JSONDecodeError: line 1 column 1` | huggingface 被拦，代码去联网了 | 下模型到 `models/`（§2） |
| 首次启动卡几分钟 | 从零重建向量索引 | 正常，等；或用 `--no-vector` |
| 网页能开但查询全失败 | API 服务没起（静态 HTML 不需要后端） | 看界面右上角状态灯 |
| 查询全失败但页面正常 | 端口不对 | 用 `start.py`（自动避开被占端口） |
| bat 双击闪退 | 文件是 LF 换行，cmd 不认 | 仓库里的已是 CRLF；若自行编辑注意 |
| 端口 8000 页面能开但查询挂 | 该端口被代理劫持 | 用 **8765** |
| `pip install` 解析失败 | 默认清华镜像 | 加 `-i https://pypi.org/simple` |
