# M76：招式 / 必杀技覆盖（12 → 156 个替身）+ 自然语言入口

> 方向来自 `/ask` 的盘点：`data_facts.json` 里 `n_moves = 23`，
> 覆盖 **11 个替身**（占 187 的 6%）—— 全库覆盖率最低的一块。

---

## 1. 为什么只有 11 个

`render_fetch.js` 提招式有三条路：

| 路径 | 来源 | 适用 |
|---|---|---|
| 3a | `div.techBox`（源站的**招式卡片**组件） | 只有热门角色才有 |
| 3b | 能力段的**列表**项，格式 `Name (Alias): desc` | 少数页面 |
| 3c | 能力段的**段落**，格式 `Name: desc` | 少数页面 |

而 3b 的**段名判据是白名单**：

```js
if (!/attack|move|abilit|technique|method|form/i.test(h)) continue;
```

实测漏掉的段名 —— 它们**全都是 `== Abilities ==` 下的 h3**，只是名字不叫 abilities：

```
LIFE GIVER              （Gold Experience，18 个 list 被整段丢掉）
SUPERHUMAN CAPABILITIES （Star Platinum）
SPECIFIC USES / BUBBLE GENERATION / RESTORATION / TIME STOP …
```

→ 全库只有 **11 / 185** 个替身提得到招式。

### 还有第二类页面：招式名就是 h3 标题本身

Gold Experience 的结构：

```
== Abilities ==
=== Life Giver ===     ← 招式名在这里
=== Life Shot ===
=== Life Sensor ===
```

它下面装的是「Turning bank notes into butterflies」这类**用例**，
不是 `Name: desc` → 3a/3b/3c 一条都提不到，整页 `moves=0`。

## 2. 修法

**① 判据从白名单改成「在 Abilities 这个 h2 之下」+ 反向黑名单**

```js
const NON_ABILITY = /^(appearance|personality|color|contents|chapters?|
  gallery|trivia|navigation|references|site|history|merchandise|video|
  games?|quotes|creation|design|conception|other media|e?tymology)/i;
let curH2 = '';
for (const sec of sections) {
  if (sec.level === 'h2') curH2 = sec.heading || '';
  ...
  const inAbilities = /^abilit/i.test(curH2);
  if (!inAbilities && !/attack|move|abilit|technique|method|form/i.test(h)) continue;
```

★ **反向比正向稳**：能力段名是**开放集合**（每个替身自己起名，`Life Giver` / `Bubble Generation` / `Time Stop`…），
而非能力段是**封闭集合**（Appearance / Personality / History / Gallery / Trivia…）。

**② 新增 3d：该页一个招式都没提到时，把能力段下的 h3 标题当招式名**

```js
if (moves.length === 0) {      // ★ 只在完全没提到时启用
  // 遍历 Abilities 下的 h3，名称 = 标题，描述 = 该 h3 下第一段（>40 字符）
}
```

★ 为什么要加 `moves.length === 0` 这个前提：
Star Platinum 有 4 个 `techBox` 真招式，不该再补一条
"Superhuman Capabilities"（那是**章节名**，不是招式）。

## 4. 顺手补上自然语言入口

M37 就建了 `stand_moves` 表和 `/moves/{stand_id}` 端点，但**没有自然语言入口**：

```
「Star Platinum 有什么招式」→ unknown → 降级语义 → 返回一段人物介绍
```

这和 M71（出场记录）、M73（篇章）是**同一个模式**：数据在库里，用户问不到。

修法两层：

**① `detect_intent` 加 `moves` 意图**

```python
INTENT_MOVES = re.compile(r"(招式|必杀技|招数|技能|有哪些招|什么招|会什么招)")
```

★ 判据**刻意不收「能力」**：「疯狂钻石的能力是什么」问的是能力**描述**，
收了会被招式列表抢走（那里只有招式名 + 一句原文，反而答得更差）。

**② Router 里必须抢在 `SEMANTIC` 之前**

`SEMANTIC` 正则里**本来就有"招式"**，所以「白金之星有什么招式」会被判成
`entity_semantic` → 返回一段人物介绍。加一条：

```python
if stand_hit and self.MOVE_ASK.search(q):
    return RouteDecision("structured", "问某替身的招式 → 结构化", signals)
```

实测（端到端）：

| 问法 | 路由 | 答案 |
|---|---|---|
| 白金之星有什么招式 | structured | moves（4 个） |
| Star Platinum 的招式 | structured | moves（4 个） |
| Killer Queen 有什么招式 | structured | moves（3 个） |
| 黄金体验的必杀技 | structured | moves（3 个） |
| 疯狂钻石的能力是什么 | entity_semantic | 原文片段 ✓（未受影响） |

**③ 前端**：`moves` 类型渲染成 `<details>` 折叠列表
（源站描述一条常 300-700 字符，默认收起）。

## 5. 踩的坑

**① `--only` 不会覆盖已存在的快照**

```js
if (!force && fs.existsSync(outFile)) { /* 跳过写入 */ }
```

我第一轮改完重抓，日志说「完成：成功 4 / 4」，但文件 mtime 还是**凌晨 01:33** ——
白跑一趟，还以为是代码没生效，查了半天 `sections`、`paras`、`RegExp`。
→ **重抓必须加 `--force`**。

**② `console.log` 在 `page.evaluate` 里是浏览器上下文**

加到 `EXTRACT` 里调试根本看不到（node stdout 只收 puppeteer 自己的日志）。
→ 调试要把信息**写进返回值**，或者用 node 单独跑逻辑验证。

**③ 修改文件位置对了，但快照没变 → 先查 mtime**

如果早点看 `ls -l` 的 mtime，第一轮就能定位，不用怀疑代码。

## 7. 遗留

- **31 个替身仍无招式**（187 − 156）：源站条目里确实没有独立招式小节，
  能力写在正文里 → 问答会给「改问『XX 的能力』」的提示，不硬凑。
- **招式名偶尔是章节名**（如某个替身的 h3 叫「Abilities」本身）——
  3d 只在 `moves` 为空时启用，已尽量收窄，但无法完全排除。
- **描述未翻译**（源站英文原文），与项目一贯口径一致（不机翻）。
