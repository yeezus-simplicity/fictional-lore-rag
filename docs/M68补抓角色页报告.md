# M68：补抓「从没进过抓取队列」的角色页 —— 抓取层名单粘连的遗留

> 完成日期：2026-10-15
> 主线：**「修好了数据」≠「那条数据路径被跑过」**，以及**「改标题」不能顺手改主键**。

本文逐段记录修了什么，并在第 6 节归纳两类结构性教训。

## 1. 起点：一个被两轮报告接力记下来的遗留

M66 报告 §9 首次记录：「DB `characters` 178 行，10 行没有独立角色页，
名字是多个角色名粘连」。

M67 修了 **`stands.json` 的 `owner_name`**（粘成一串 → 拆开），
并在 §8 留下一条：

本轮（用户「接着做」）把这条挖到底。**结论和两轮报告的措辞都不一样**：

> 那些角色页不是「抓不到」，而是**从来没被放进抓取队列**。

## 2. 真相：target 名单是运行时生成的，旧数据污染会一直传下去

`fetch_articles.build_targets()` 的角色清单来自：

```python
for s in stands:
    for o in split_owner_names(s.get("owner_name") or ""):
        targets.append({"title": o, "kind": "character", ...})
```

M67 之前 `owner_name` 是 `Caravan SeraiChakaFour Unnamed miceKhan…` 这种
**一整串** → `split_owner_names` 返回一个「粘名字」→ 那个名字在 wiki 上
**不存在** → 抓取日志里一行 `– xxx 页面不存在` → **永久缺失**。

M67 修好了 `stands.json`，**名单自动就干净了**（我本轮第一件事就是验证这个）：

```
角色 target: 182 个
★ 名单里仍粘连的名字: 1  ← Thunder McQueen（其实是误报，见 §5.3）
★ 之前 3 个长粘连名: 已消失 ✓
```

但**语料不会自己长出来** —— `articles.json` 是 M58 起逐步抓的缓存，
M67 之后从没重跑过抓取。所以：

| | M67 修完 | 本轮补抓后 |
|---|---|---|
| 语料角色页 | 168 | **180** |
| 待抓（不在语料里） | 18 | 0 |

★ 这条值得单独记：**修好上游数据 ≠ 下游产物会更新**。
   `stands.json` 干净了，但 `articles.json` / `article_chunks.json` /
   `characters_ext.json` / DB 全是旧快照 —— 中间隔着**四个产物 + 一次入库**。

## 4. ★★ 「改标题」差点顺手改了主键

这是本轮最危险的一个坑，**它不报错**。

`TITLE_FIXUPS` 把页面标题从 `Unnamed Mountain Lodge Owner` 换成
`Mountain Lodge Owner`。我第一版的 target 是：

```python
targets.append({"title": o, "kind": "character", "entity_id": _char_id(o)})
                #                                              ^ 修正后的名字
```

→ `entity_id` 变成 `mountain_lodge_owner`，
而 **DB 的 `characters.character_id` 是 `unnamed_mountain_lodge_owner`**
（`load_db` 用 `stands.json` 里的**原名**算）。

后果不是报错，而是**四条链同时静默断裂**：

1. 语料块的 `character_id` 对不上 DB → 入库时违反外键
2. `characters_ext` 的中文名按 id 查 → 查不到（「古奇」丢失）
3. 块号回查（`chunk_id_of`）按 id 找 → 找不到
4. 前端角色卡按 id 取数据 → 空

★ 修法：**标题与主键分离** —— target 里同时带三个字段：

```python
orig = o                              # 原名（算 id 用）
if o in TITLE_FIXUPS: o = TITLE_FIXUPS[o]
targets.append({
    "title": o,                       # 真实页面名（点回源站用）
    "entity_id": _char_id(orig),      # ★ 按原名算
    "name_in_stands": orig,           # 原名（便于人复核）
})
```

下游 `build_characters.py` 也跟着改（它原先用 `_char_id(title)` 算 id）：

```python
cid = p.get("entity_id") or _char_id(title)     # ★ 用语料页自带的 id
name_en = p.get("name_in_stands") or title      # 展示名用原名（与 DB 一致）
```

测试里为这条加了 **7 条断言**（含「所有 `characters_ext` 的 id 都在 DB 里」）。

## 5. 途中踩到的三个坑

### 5.1 `Echoes (ACT1/2/3)` 被我误读成新 bug

抓取日志里三条 `– Echoes (ACT1) 页面不存在`，我第一反应是「又有问题」。
查完发现：它们是 **`kind=stand` 的形态条目**（M58 形态链把 Echoes 的三个
ACT 做成了独立替身条目），wiki 上没有独立页面是**正常的**，
DB 里也没有对应的 character 行。

→ 已写进 `NO_PAGE` 的注释：**这三条不在这张表里，因为它们的 kind 不是 character**。
★ 教训：**日志里同一行「页面不存在」，根因可能完全不同**（形态无页面 /
  匿名角色无条目 / 名字写法不一致）。处置方式也因此不同。

### 5.2 `suspect_title` 把 `Thunder McQueen` 判成「两角色名粘连」

```python
"suspect_title": bool(re.search(r"[a-z][A-Z]", title))   # `cQ` 命中
```

→ 与 M67 里「不用驼峰边界判 owner 粘连」**完全同一个教训**
（`McQueen` / `Jolyne Cujoh` / `McDonald` 都是正常驼峰名）。
M67 我在 `glued_owner` 上改了，**`build_characters` 这一处漏了**。

→ 排除 `Mc|Mac` 前缀后再判；实测「标题可疑」从 1 → **0**。

### 5.3 我自己写的测试断言错了两处

1. **规模数字写死 `==168`**：M66 测试的 5 条断言全是 M66 时点的数字
   （角色 168 / 简介 168 / 背景 106 / 性格 162 / 中文名 123）。
   这类数字**每补一批数据就变一次**，钉死等于每轮都要改测试。
   → 全部改 `>=`（M64 的教训原话：「断言绑死具体数字 → 新环境假失败」）。
2. **恒真检查**：我写了 `bool(ast.parse(fa_src)) is False or True`
   —— `or True` 让它**恒为真**，等于没检查。
   ★ 这正是本项目反复出现的那条：**检查工具写错比被检查的代码写错更危险**。
   → 改成 `try/except SyntaxError`。
3. 还有一处：heredoc 把 `\n` 写成 `/n` → 语法错
   （**我记忆里记过的「Git Bash heredoc 改反斜杠」**，这次又栽）。

### 5.4 ★★ 意外收获：5 个测试在「Docker Desktop 没启动」时会被静默打死

提交前跑全套回归，发现 `test_m68` 在连 DB 那步**整个进程消失**
（exit=1、没有 Traceback、只打了 15 行）。逐层查下去：

```
load_db.connect() 第 96 行：  raise SystemExit(1) from e
```

**`SystemExit` 不继承 `Exception`**（它继承 `BaseException`）→
我写的 `except Exception` 抓不到 → 测试被**静默终止**，
连「降级跳过」的 SKIP 行都打不出来。

顺着这条线查了全部 32 个测试，**5 个有同类问题**：

| 测试 | 原状 | 无 DB 时 |
|---|---|---|
| `test_m68_owner_pages` | 无 try | 进程直接死（15 行后消失） |
| `test_m58_forms` | 无 try | 同上 |
| `test_m66_characters` | 无 try | 同上 |
| `test_m40_part_list` | 有 try 但 `except Exception` | 同上 |
| `test_m67_owner_split` | 同上 | 同上 |

★ 而且这不只是「测试崩了」——其中 4 个还会把
**「Docker Desktop 没启动」报成「功能回归」**（服务优雅降级后，
断言自然失败）。

**修法**（两条，对应两种形态）：

1. **直连 DB 的**（m67/m68/m66 的 [1′] 段）：
   `except BaseException` + `isinstance(e, SystemExit)` → 打 SKIP、不计失败。
2. **起服务做端到端的**（m40/m58/m66）：
   服务就绪后探 `/health` 的 `database` 字段，
   未连上则整测 SKIP；`--require-db` / `CI=true` 时严格（缺库算失败）。
   ★ 这正是 `test_gui_e2e` 第 87 行**早就写好的模式**，
     我复用它而不是另造一套。

★ 顺带修了两处**补丁打一半**的残留：
- `test_m67` 里我加 `except BaseException` 时**漏删了原来 except 体**
  最后那行 `check("数据库可连接", False, ...)` → 它落在 except 块**之后**，
  无条件执行且必然 FAIL。**这类残留比原 bug 更隐蔽**：
  上面明明已经 SKIP 了，末尾却又判一次失败。
- `test_m67` 的块数断言钉死 `角色块 == 2961`（M68 后是 3063）
  → 改 `>=`（M64 的教训：**断言绑死具体数字 → 新数据下假失败**）。

★ 这一条的**普适价值**超出本项目：
  **「环境不满足」与「功能坏了」必须分开**，否则一次忘记开 Docker
  就会让你以为自己的代码回归了 —— 而真相是代码好得很。

### 5.5 ★★ 降级路径本身也要测，否则那段代码永远没被 CI 覆盖

上面 `[3]` 段的 `except BaseException` 只在「DB 真不可用」时才走到，
而 **CI 永远有 DB**（service 容器里跑 postgres）→ 这条分支平时**一次都不执行**。

→ 加 `[8]` 段：用 `PGPORT=1`（必然连不上，同 `test_degraded_mode` 的做法）
起子进程跑自己，断言它 **exit=0 + 打出 SKIP + 非 DB 断言照跑**。

★ 写这一段时又踩了一次**无限递归**：

```
test_m68 的 [8] 段起子进程跑自己
  → 子进程跑到 [8] 段又起一个子进程
    → ……
实测：SIGTERM（直接被系统杀掉）
```

→ 加环境变量守卫 `_M68_CHILD=1`：子进程跑到 `[8]` 段就停。
★ 这类「测试自己调自己」的设计**必须自带终止条件**，
  否则它会在你完全没料到的时刻把整个测试套件搞崩。

★ 顺带记一条本轮才看清的事实：**上一次全套跑出 17 个「失败」，
  并不是代码回归，而是当时 Docker Desktop 没启动**。
  等 Docker 恢复后重跑，**32/32 全绿且零 SKIP**。
  → 这恰好证明了那 17 个失败**不该被当成回归**，
  也是这次加降级标记的直接理由。

## 6. 两类结构性教训

### ① 「修好了数据」≠「那条数据路径被跑过」

M67 改的是 `stands.json`（源头），但产物链是：

```
stands.json → build_targets() → articles.json → article_chunks.json
            → characters_ext.json → load_db → DB
```

中间**四个产物 + 一次入库**。M67 修完只重建了 DB（`load_db --load`），
**语料与角色档案两个产物没重跑** —— 所以本轮补抓前，
`characters_ext` 还是 168 个。

→ 对策：**改源头就要沿产物链重跑到底**，并且**跑数字闸门**
  （它本轮又立功了，见 §7）。

### ② 数字闸门第三次立功

改完语料跑 `--check`，同时报 3 个 error：

```
✗ 数据.语料总量: 对外写 7940，产物是 8042
✗ 数据.角色数:   对外写 168，产物是 180
✗ 数据.角色简介覆盖: 对外写 168，产物是 179
```

→ 已全部同步。**另外发现 `docs/简历素材.md` 从 M65 起就停在 6761**——
  M65 语料涨到 7940 时没改它（当时只同步了 README）。
  → 本轮一并刷新（6761 → 8042），并在头部补上地点/角色两个维度。

★ 三次立功分别是：M64（六维完整度）、M67（语料总量）、M68（语料 + 角色数）。
  **这条经验已经稳定成立：改数据必跑闸门。**
