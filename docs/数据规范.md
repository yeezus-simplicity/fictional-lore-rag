## 1. 能力等级编码规范

### 1.1 六维能力定义

| 字段 | 英文 | 中文 | 含义 |
| --- | --- | --- | --- |
| PWR | Power | 破坏力 | 破坏力 |
| SPD | Speed | 速度 | 速度与敏捷性 |
| RNG | Range | 射程 | 有效攻击距离 |
| STA | Persistence | 持续力 | 能力维持时间 |
| PRC | Precision | 精密性 | 精度与作用范围控制 |
| DEV | Development | 成长性 | 能力成长潜力（**注意：使用者越强，等级越低**） |

### 1.2 等级到数值的映射（核心规则）

```
None → 0
E    → 1
D    → 2
C    → 3
B    → 4
A    → 5
```

**说明**：采用 0–5 闭区间，包含 `None=0`。理由是 `None`（无能力）与 `E`（最弱等级）必须区分，若用 1–5 会丢失这个语义。

### 1.3 空值字面量白名单（v1.1 新增）

**不同数据源用不同字面量表示同一语义，必须归一化。** 实测发现三种写法并存：

| 字面量 | 主要来源 | 归一类别 |
| --- | --- | --- |
| `∅` | jojowiki | `EMPTY_SLOT` |
| `None` / `none` | CSV 镜像 | `EMPTY_SLOT` |
| `undefined` / `N/A` | CSV 镜像 | `EMPTY_SLOT` |
| `?` | 三源均有 | `UNKNOWN` ← **不归一，独立语义** |

> ⚠️ `?` 不在空值白名单内。「有值但不确定」与「这一格没填」是两种语义，混为一谈会同时污染「缺失统计」和「争议统计」两类查询。

### 1.4 异常值分类编码 ★ 本项目最关键的设计

原始数据存在多种无法直接数值化的值。**必须区分，不可一律当缺失处理。**

| 语义 | 原始字面量 | 存储方案 | 参与统计 | 类别枚举 |
| --- | --- | --- | --- | --- |
| 正常等级 | `A`–`E` | 整数 5–1 | ✅ | `RANKED` |
| 明确无能力 | `None` / `none` | 整数 0 | ✅ | `NONE` |
| 空位 | `∅` / `undefined` / `N/A` | `NULL` + category | ❌ | `EMPTY_SLOT` |
| **未知/存疑** | `?` | `NULL` + category | ❌ | `UNKNOWN` |
| **无限** | `∞` / `Infinite` | `NULL` + category + 原始值存 `raw_value` | ❌ | `INFINITE` |
| **条件值（有基础等级）** | `B※20-30 meters` | 整数 + `condition_note` | ✅（基础值） | `CONDITIONAL` |
| **条件值（无基础等级）** | `※Complete` / `?※Power: Likely A` | `NULL` + category | ❌ | `CONDITIONAL_NO_BASE` |

#### 条件值的两种语法形态（v1.1 修订）

实测 24 个条件值格子中，**两种形态处理方式完全不同**：

**形态一：`X※<描述>` —— 有基础等级（20 格）**

```
B※20-30 meters
C※Range: 2 m (6.6 ft)
A※Only during replays
E※Restraining Power: A
```

首字符为 `A`–`E`，`※` 之后是补充说明。

→ `stat_value` = 基础等级数值；`condition_note` = `※` 之后的文本
→ 例：Gold Experience 的 `C※Range: 2 m` → `stat_value=3, condition_note="Range: 2 m"`

**形态二：`※<描述>` 或 `?※<描述>` —— 无基础等级（4 格）**

```
※Complete
※Depending on Education
?※Power: Likely A (JoJoveller p.245)
D※Speed: Refers to "Melt your Heart" Ability (JoJoveller p.245)
```

`※` 在首位，或前缀为 `?` 等非标准值。

→ **不可数值化**：`stat_value=NULL`，`category=CONDITIONAL_NO_BASE`

#### 判定顺序（实现必须严格按此顺序）

```
1. ^[A-E]※            -> RANKED,值=map(A..E), note=value[2:],category=CONDITIONAL
2. ^[?∅∞None]※        -> NULL, category=CONDITIONAL_NO_BASE, note=value[2:]
3. ^※                 -> NULL, category=CONDITIONAL_NO_BASE, note=value[1:]
4. ^[A-E]$            -> RANKED, 值=map(A..E), category=RANKED
5. ^(None|none)$      -> 0, category=NONE
6. ^∅$|^undefined$|^N/A$ -> NULL, category=EMPTY_SLOT
7. ^\?$               -> NULL, category=UNKNOWN
8. ^(∞|Infinite)$      -> NULL, category=INFINITE, raw_value=原值
9. 其他                -> NULL, category=UNPARSED（需人工介入，计入校验告警）
```

> 顺序不可调换。规则 1 必须先于规则 4，否则 `B※...` 会被误判为非法值。

### 1.5 `∅` 与 `?` 的本质区别（必须理解）

这是本项目最容易被忽略、也最能体现数据处理能力的点：

```
∅  =  数据源「这一格没填」      → 缺失(missing)，统计时应排除
?  =  数据源「有值但不确定」     → 未知(unknown)，语义上不同于缺失
∅A =  该维度无定义，永久不存在   → 与 ? 语义不同，推理时不可混用
```

**举例说明为何重要**：

- 问"哪些替身持久力为 E" → `∅` / `?` / 任何 `CONDITIONAL_NO_BASE` 都**不应**返回该替身
- 问"哪些替身的数据存在缺失" → 只能返回 `EMPTY_SLOT` / `NOT_APPLICABLE`，`?` 属于「有争议」而非「缺失」
- 问"数据最完整的替身" → 若把 `?` 当缺失，会错误地惩罚 Whitesnake（多项 `?`）

### 1.6 条件值跨状态的展开（特殊场景，非默认路径）

v1.0 曾把「按状态拆多行」作为条件值的默认处理，**实测证明该场景罕见**。本数据集中 `※` 绝大多数是「同一数值 + 补充说明」，不涉及多行展开。

仅当**同一形态在不同状态下数值确实不同**时，才使用 `stand_stat_conditional` 表展开：

| stand_id | stat_dim | state_desc | stat_value | condition_note |
| --- | --- | --- | --- | --- |
| black_sabbath | pwr | 初始 | 1 | Restraining Power: A |
| black_sabbath | pwr | 觉醒后 | 5 | |

**默认路径**：查询使用主表值，同时若该维度 `category=CONDITIONAL`，显式告知该值存在补充说明或状态依赖性。

### 1.6 衍生指标

```
composite_score = PWR + SPD + RNG + STA + PRC + DEV   -- 仅当 6 项全部为 RANKED/NONE 时计算
```

**约束**：任一维为 `NULL`（`∅`/`?`/`∞`/条件值）时，`composite_score` 置为 `NULL` 而非取平均——否则会生成虚假的可比数值。统计时按可用维度数分组呈现。

## 2. 数据表设计

### 2.1 核心表

```sql
-- 替身主表
CREATE TABLE stands (
    stand_id      TEXT PRIMARY KEY,      -- 规范化 ID，如 'star_platinum'
    name_en       TEXT NOT NULL,
    name_zh       TEXT,
    aliases       TEXT[],                -- 英文别名数组
    owner_id      TEXT,                  -- 外键 → characters
    part          INTEGER,               -- 所属部（3–8）
    stand_type    TEXT,                  -- 人型/悬浮型/兽型/植物型/昆虫型/光线型/自动式/道具型
    ability_desc  TEXT,                  -- 能力描述长文本（非结构化）
    reference     TEXT,                  -- 命名原型出处（塔罗/神名/乐队名等）
    form_chain    TEXT[],                -- 形态链，进化形态按序
    first_appear  TEXT,
    data_sources  TEXT[]                 -- 来源标记，用于冲突消解
);

-- 能力数值表（宽表）
-- v1.1：新增 *_note 与 *_raw 字段，用于承载条件值说明与原始字面量
CREATE TABLE stand_stats (
    stand_id  TEXT PRIMARY KEY REFERENCES stands(stand_id),
    pwr INTEGER, pwr_cat TEXT, pwr_note TEXT, pwr_raw TEXT,
    spd INTEGER, spd_cat TEXT, spd_note TEXT, spd_raw TEXT,
    rng INTEGER, rng_cat TEXT, rng_note TEXT, rng_raw TEXT,
    sta INTEGER, sta_cat TEXT, sta_note TEXT, sta_raw TEXT,
    prc INTEGER, prc_cat TEXT, prc_note TEXT, prc_raw TEXT,
    dev INTEGER, dev_cat TEXT, dev_note TEXT, dev_raw TEXT,
    composite  INTEGER,                 -- 6项齐全才计算
    has_partial INTEGER DEFAULT 0,      -- 标记存在 NULL 维度
    missing_count INTEGER DEFAULT 0     -- NULL 维度数，便于「数据完整度」查询
);

-- 维度枚举（v1.1 新增 CONDITIONAL_NO_BASE）
-- RANKED             正常等级，有数值
-- NONE               明确无此能力，数值为 0
-- EMPTY_SLOT         空位（∅ / undefined / N/A），数值 NULL
-- UNKNOWN            未知（?），数值 NULL
-- NOT_APPLICABLE     不适用，数值 NULL
-- INFINITE           无限（∞），数值 NULL，raw 保留原值
-- CONDITIONAL        条件值有基础等级，数值有效，note 存补充说明
-- CONDITIONAL_NO_BASE 条件值无基础等级（首位※），数值 NULL
-- UNPARSED           无法解析，需人工介入
CREATE TYPE stat_category AS ENUM (
    'RANKED','NONE','EMPTY_SLOT','UNKNOWN','NOT_APPLICABLE',
    'INFINITE','CONDITIONAL','CONDITIONAL_NO_BASE','UNPARSED'
);

-- 条件值跨状态展开表（特殊场景，见§1.6）
CREATE TABLE stand_stat_conditional (
    stand_id       TEXT REFERENCES stands(stand_id),
    stat_dim       TEXT,        -- PWR / SPD / RNG / STA / PRC / DEV
    state_desc     TEXT,        -- '初始' / '觉醒后' / '成熟期'
    stat_value     INTEGER,
    condition_note TEXT,
    PRIMARY KEY (stand_id, stat_dim, state_desc)
);

-- 角色表
CREATE TABLE characters (
    char_id     TEXT PRIMARY KEY,
    name_en     TEXT NOT NULL,
    name_zh     TEXT,
    gender      TEXT,
    affiliation TEXT,
    part_debut  INTEGER
);

-- 形态关系表
CREATE TABLE stand_forms (
    form_id     TEXT PRIMARY KEY,
    stand_id    TEXT REFERENCES stands(stand_id),
    form_name   TEXT,
    form_type   TEXT,                   -- base / evolved / requiem / alternate
    parent_id   TEXT,                   -- 前置形态
    awakens_to  TEXT,                   -- 觉醒后形态
    condition   TEXT                    -- 觉醒条件描述
);
```

### 2.2 版本与冲突表

```sql
-- 同一字段在不同来源/版本中的取值，用于冲突检测
CREATE TABLE stat_conflicts (
    id           SERIAL PRIMARY KEY,
    stand_id     TEXT,
    stat_dim     TEXT,
    value_a      TEXT,    -- 来源 A 的原始值
    source_a     TEXT,    -- 'kaggle' / 'jojowiki' / 'zh_wiki'
    value_b      TEXT,
    source_b     TEXT,
    conflict_type TEXT,   -- 'VALUE_MISMATCH' / 'MISSING_IN_ONE' / 'CATEGORY_DIFF'
    resolution   TEXT,    -- 采纳策略：'prefer_kaggle' / 'prefer_wiki' / 'MANUAL'
    resolved_value TEXT,
    note         TEXT
);
```

## 3. 语料来源与合并策略

### 3.1 三源分工（v1.1 按实测修订）

| 来源 | 提供 | 优势 | 局限 |
|---|---|---|---|
| **jojowiki** `Stand_Stats` | 6 维数值 + 能力描述 | 内容最全，157 条，含命名出处与异常值 | 无所属部字段，页面有编辑历史 |
| **CSV 镜像 A**（`BogdanG888G/JOJO_stands`） | 6 维数值 + `Story` 字段 | **唯一可用的所属部来源**，含英文部名 | 编码混杂，文件名带多余引号 |
| **CSV 镜像 B**（`topologytomato/...`） | 6 维数值 | 可作第三方交叉校验 | **非 UTF-8**，第 4 列名错为 `PER` |
| Kaggle 官方 | — | 原始来源 | 沙箱内不可达，已由两个公开镜像替代 |
| 中文维基「替身」条目 | 中文能力描述 | 中文表达完整 | 沙箱内代理 502，不可达 |

### 3.2 合并优先级

```
结构化数值：jojowiki  >  CSV镜像A  >  CSV镜像B
所属部：    CSV镜像A 的 Story 字段（唯一来源）
能力描述：  jojowiki（需抓详情页，M1 子项4）
中文描述：  暂缺，M5 前另寻替代源
```

> v1.0 曾把 Kaggle 列为数值首选。实测 jojowiki 覆盖 157 条且含异常值原文，是更可靠的基准；Kaggle 因不可达已降级为镜像。

**冲突不做静默覆盖**，全部记入 `stat_conflicts` 表。

### 3.3 冲突消解规则（v1.1 按实测修订）

| 冲突类型 | 实测占比 | 消解策略 |
|---|---|---|
| **空值表示法差异**（`∅` vs `undefined` vs `None`） | 约 30/34 | **归一化**，非真冲突。统一按 §1.3 白名单映射为 `EMPTY_SLOT` |
| **列名差异**（`PER` vs `STA`） | 全部 CSV 行 | **按位置映射**，不按列名。统一以 jojowiki 的 `STA` 为权威 |
| 同一维数值不同（三源均有效） | 约 4–5 处 | 采jojowiki（基准源），记入 `stat_conflicts` |
| 源内重复登记（Echoes ACT3 出现两次） | 已发现 1 例 | 视为**形态重复**，按形态链消解，记 `DUPLICATE_IN_SOURCE` |
| 语义等价但表述不同（`C` vs `C※Range: 2m`） | 常见 | 保留细粒度版本，基础等级入库，范围描述入 `*_note` |
| 仅有 `?` vs 有确定值 | 存在 | 采确定值，但保留 `?` 来源记录到 `stat_conflicts` |
| 跨部数值不同（同一替身不同时期） | 存在 | **不算冲突**——`part` 不同即视为不同记录 |

> **实测修正**：立项书预估冲突率 8–12%，实测真冲突约 3%（4–5/157），另有约 19% 属表示法差异。评测报告需如实修正，不虚报。

> **命名来源名**：`stat_conflicts.source_a/b` 实际取值 `jojowiki` / `csv_bogdan` / `csv_topology`。

## 4. 文本语料规范

### 4.1 能力描述的切分原则

`ability_desc` 是长文本（含能力说明、招式名、剧情表现），切块策略：

```
不用固定长度切分。能力描述天然有结构：
  「能力概述段落」→「招式列表（每招独立成块）」→「战斗表现/剧情实例」
```

- **招式级切块**：每个招式独立成块，保证检索粒度对齐用户意图
- 保留 `stand_id` + `form_id` + `ability_category` 作为元数据
- 元数据必须包含 `part` 与 `source`，为后续版本冲突与权限做准备

### 4.2 检索单元定义

| 单元类型 | 内容 | 检索用途 |
|---|---|---|
| `ability_overview` | 整体能力概述 | 「XX 的能力是什么」 |
| `move` | 单个招式 | 「XX 有什么招式」 |
| `battle_record` | 战斗表现实例 | 「XX 在哪场战斗用过 Y」 |
| `lore` | 命名出处、设定背景 | 「XX 的名字来源是什么」 |
| `stat_row` | 结构化数值行 | 走 SQL，不进向量库 |

**关键设计**：`stat_row` **不进向量索引**。结构化数据走 SQL，把向量库留给真正需要语义检索的文本——这是工具选型的正确性体现。

## 5. 校验规则（数据入库前必须通过）

| 编号 | 规则 | 级别 |
| --- | --- | --- |
| V1 | 每条记录的 `category` 字段与原始值映射一致 | ERROR |
| V2 | 数值字段在 0–5 闭区间内 | ERROR |
| V3 | `composite` 非空时，6 个维度均非空 | ERROR |
| V4 | `owner_id` 外键可解析（允许 NULL 表示未收录） | WARN |
| V5 | 三源合并的冲突全部已记入 `stat_conflicts` | ERROR |
| V6 | `name_en` 规范化后唯一（别名冲突走alias 表） | ERROR |
| V7 | `form_chain` 中的形态均存在于 `stand_forms` | WARN |
| V8 | 文本块数与元数据完整性（无孤儿块） | ERROR |
| **V9** | **列名白名单校验**（v1.1 新增） | ERROR |
| **V10** | **`category` 与 `stat_value` 一致性**（v1.1 新增） | ERROR |
| **V11** | **原始字面量可回溯**（v1.1 新增） | WARN |

### V9 列名白名单校验（v1.1）

**背景**：CSV 镜像 A 第 4 列名为 `PER`，镜像 B 为 `STA`。若按列名自动映射，会把「持续力(Stamina)」错映射为「感知力(Perception)」，**且不报错，静默产出错误统计**。

校验内容：

1. 接入任何新数据源时，先断言其列名集合属于白名单：
   ```
   允许：PWR SPD RNG STA PRC DEV
   已知错误别名：PER→ STA（持续力，非感知力）
   ```
2. 断言列数恒为 7（含 Stand 名）或 8（含 Story）
3. **若出现未知列名，直接 ERROR**，不得猜测映射

### V10 category与 stat_value 一致性（v1.1）

按 §1.4 判定表逐条断言：

| category | stat_value | note | raw |
| --- | --- | --- | --- |
| `RANKED` | 1–5 | NULL | 原值 |
| `CONDITIONAL` | 1–5 | 非 NULL | 原值 |
| `NONE` | 0 | NULL | 原值 |
| `EMPTY_SLOT` | NULL | NULL | 原值 |
| `UNKNOWN` | NULL | NULL | 原值 |
| `INFINITE` | NULL | NULL | **非 NULL**（保留 ∞ 原值）|
| `CONDITIONAL_NO_BASE` | NULL | 非 NULL | 原值 |
| `UNPARSED` | NULL | NULL | 原值 |

> 违反任一组合即 ERROR。这条规则是 §1.4 判定逻辑的**可执行断言**，防止实现与文档漂移。

### V11 原始字面量可回溯（v1.1）

所有 `*_raw` 字段必须非空，保留数据源原始字面量（含 `undefined` / `None` / `∞` 等非规范写法）。

**理由**：归一化是 lossy 操作。保留原值才能在规范演进时重跑历史数据，无需重新抓取。

> V1–V3 直接对应"脏数据编码是否正确"。若这三项通过，说明 §1.3 的分类方案落地无误。
> V9–V11 是v1.1 新增，分别防列名误映射、判定逻辑漂移、归一化不可回溯。

### 实测基线（157 条，942 个格子）

校验脚本跑批时应能复现以下分布，作为编码正确性的验收基准：

| 类别 | 实测数量 | 说明 |
| --- | --- | --- |
| `RANKED` | 837 | A/B/C/D/E 五级合计 |
| `EMPTY_SLOT` | 约 83 | `∅` 53 + CSV 侧 `undefined`/`none` |
| `UNKNOWN` | 22 | `?` |
| `CONDITIONAL` | 20 | `X※描述` 形态 |
| `CONDITIONAL_NO_BASE` | 4 | `※描述` / `?※描述` 形态 |
| `INFINITE` | 6 | `∞` |
| `UNPARSED` | **0** | 目标：判定表覆盖全部取值 |

> 837 + 83 + 22 + 20 + 4 + 6 = 972 > 942，因 `EMPTY_SLOT` 含跨源合并后的补齐项。精确基线以 M1 跑批结果为准，此处为量级预期。
