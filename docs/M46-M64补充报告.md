# M46–M64 补充报告：从「我能跑通」到「用户真的看到」

> 完成日期：2026-10-13 ~ 2026-10-15
> 目的：M46–M64 这十九轮的改动此前只存在于 commit message 与开发记录中，
> 本文统一归档。
> **贯穿主线：M39–M45 解决的是「表里有数据 ≠ 用户能查到」；
> 这十九轮解决的是它的下一层 —— 「代码改了 ≠ 用户看到的东西变了」。**

---

## 0. 为什么值得单独写一份

M39–M45 那份报告的结论是：**静态校验全绿，用户入口可能是 0**。
这一轮之后，我以为剩下的只是把功能补齐。

但用户连续反馈的问题，落点全在**我验证不到的地方**：

| 用户原话 | 我当时以为 | 实际 |
|---|---|---|
| 「为什么 act1-4 的图片都是一样的呢」 | 抓取可能崩了 | 源站没有形态页 + 抓取器没按 ACTn 分 |
| 「点击一个 act 之后 点击其他的就不管用了」 | 前端事件没绑好 | **后端 500** + 编造词过滤器误伤真形态 |
| 「我的网页还是没区别 到底怎么完全刷新」 | 服务端没更新 | 服务端对，**浏览器缓存** |
| 「我强刷新过了 还是这个样子」 | 应该好了 | **我上一轮修错了位置**（改的是另一个页面的同一处） |
| 「左边文字有一大边空白」 | 布局该缩窄 | 方向反了：该让左栏**有内容** |
| 「点击 tusk act4 就显示服务可能暂停」 | 服务真的挂了 | 服务活着，**500 被文案说成"服务已停止"** |
| 「上传 git 没成功」 | 代码有问题 | GitHub 从沙箱**不可达** |

**十八轮里能让用户直接看到"出错了"的只有两次**（M56 网页白屏、M58b 的后端 500）。
其余全是**静默的**：页面照常渲染、接口照常 200、日志照常干净，
只是显示出来的东西是错的、或者该有的东西没出现。

本文逐轮记录修了什么，并在第 7 节归纳这十九轮反复出现的元错误模式。

## 1. 图片链路：三处「看起来没有数据」（M47 / M48b / M48c）

用户的起点是「抓取图片的速度有点慢」。顺着它挖出三个独立缺陷。

### 1.1 M47 提速 6.8 倍 —— 先测瓶颈，再优化

**实测规模**：库里 187 个替身，**只抓了 23 个**（339 张图 / 80MB）。
按原速度约 **43 分钟**。

**先量再改**，每一个环节都实测：

| 环节 | 实测 |
|---|---|
| 单张 400px 缩略图 | 1.3 ~ 3.5 s（中位 ~1.5s），经代理 |
| 首次请求（冷启动） | **27 ~ 58 s**（代理 CONNECT + TLS 首建） |
| 页面抓取（替身页 + 角色页，串行） | 4.1 s |

**逐步优化，每步都测**（同一批 8 替身 / 112 张图）：

| 配置 | 耗时 | 相对 |
|---|---|---|
| workers=1（urllib） | 150.5s | 1.0x |
| workers=4（urllib） | 91s | 1.65x |
| workers=8（urllib） | 132s | **1.14x（反而退了）** |
| workers=1 + 连接复用 | 45s | 3.3x |
| **workers=4 + 连接复用** | **22s** | **6.8x** |
| workers=8 + 连接复用 | 27s | 5.6x |

两处改动的贡献要**分开看**才有意义：

**【1】连接复用是最大收益（150→45，3.3x）**
对照组实测（同 6 张图、串行、同代理）：

```
urllib（每次新建连接）     10.18 s
requests.Session（复用）    2.00 s   ← 5 倍
```

原因：`urllib.request.urlopen` 每次调用都新建 TCP + TLS；经代理还要
重走一次 CONNECT 隧道。**这部分开销与图片大小无关**，每张图都得付一次。

→ 改为**线程局部** `requests.Session`。
★ 为什么是 `threading.local` 而不是全局一个 Session：
`requests.Session` 的连接池/cookie **没有为多线程共享设计**，
而本脚本正是线程池并发下载 → 每线程一个 Session，既复用连接又没有竞态。
（全局 Session + 一把锁会把并发变回串行。）
★ 失败时清掉该线程的连接池：代理抖动常留下坏连接，复用它会连着失败第二次。

**【2】替身级并发（45→22，2x）**
单个替身内部原本就是「先串行抓页面、再 4 线程下图片」，
但**替身与替身之间没有重叠** → A 等网络时 B 完全闲着。

**【3】workers=8 反而更慢，这条负结论同样重要**
并发不是越多越好 —— 代理侧会成为新的瓶颈，而**多出来的线程只是在排队**。
所以最终配置是 `--workers 4`。

### 1.2 M48b：`imlimit` 是**总上限**，不是每页上限

**现象很隐蔽**：8 个替身一起跑，**前 5 个正常、后 3 个一张图都没有**。
而且**和位置强相关**（不是随机）。

单独跑这两个替身完全正常（各 15 张）；单独调 API 也正常（70 个）。
只有「批量预取 + 并发」这一条路径会失败 → 说明问题在**批量请求**本身。

**根因**：`imlimit=500` 是**所有页面共享的总上限**：

```
Atum 84 + Bastet 49 + Cream 169 + Death_Thirteen 99 + Geb 39 = 440
再加 High_Priestess(70) 就超过 500
→ 从 High_Priestess 开始，后面所有页面全部返回 0 个文件
```

★★ 最坑的是**它不报错**：既没有 `missing`、也没有 error，
就是 `images: []` —— 表现成"这些替身一张图都没有"。
（M48 的实测恰好只验了 3 个替身，混在一次小查询里没触发上限，所以没暴露。）

**修法**：按 MediaWiki 的 `continue` 续查 —— 读响应里的 `continue` 字段，
带着它继续请求同一批，直到没有为止；结果 `extend` 累积并去重。

| 替身 | 修复前 | 修复后 |
|---|---|---|
| Cream | 155 | 155 |
| **Geb** | **24** | **79** |
| **High_Priestess** | **0** | **60** |
| **Horus** | **0** | **66** |
| **Judgement** | **0** | **57** |

★ 注意 **Geb 从 24 → 79**：它也被截断了，只是没截到 0 ——
**"不报错 + 数字非零"最容易让人以为没问题**。

### 1.3 M48c：日志总数与磁盘实际文件数**对不上账**

**怎么发现的**：`--force` 全量重跑后日志报「共 2162 张」，
但磁盘上数出 **2709 个**图片文件 —— 差 547。

**根因**：文件名是 `{kind}_{序号}{后缀}`，重抓时张数可能变少，
**旧的高编号文件不会被覆盖**：

```
上次 stand_1..4，这次只有 stand_1..3  →  stand_4.jpg 留在原地
```

实测 **150 个替身目录、547 个残留文件、约 101 MB**。危害有两个：

1. 白占磁盘（101 MB）
2. **界面若按目录扫图，会把上一轮淘汰的图也显示出来** ——
   而 manifest（`_images.json`）里根本没有它们，
   于是"界面显示"与"数据清单"不一致

**修法**：`save()` 写完 manifest 后，删除目录里**不在 manifest 内**的图片文件。
★ 只在**本次有成功下载**时才清理 —— 全失败时保留原有图，不至于清空。

一次性清理现存残留：**134 个目录 / 498 个文件 / 释放 101 MB**。
复核：manifest 与磁盘不一致的替身 = **0**。

### 1.4 本节教训

**「日志说抓到了」与「磁盘上真的有」是两件事。**
前者来自 manifest，后者来自文件系统；两者不一致时，
通常是"旧文件没清"或"新文件没记" —— 这类问题不会报错，只能靠**对账**发现。

## 2. 展示层：四处「显示出来的东西是错的」（M49 / M51 / M52 / M53）

这一组问题有共同特征：**接口正常返回 200，页面正常渲染，但内容是错的**。

### 2.1 M49：六维表三列全错

用户的切入点是外观：「为什么这个类别的后面的字会占很多空格」。

**先查清「空白」从哪来**（不猜）：`.kv` 那套 grid 布局实测 gap 只有 16px，不是它。
用 Playwright 量六维能力值表（`维度 | 值 | 原始 | 类别`）：

| 列 | 宽度 | 对齐 |
|---|---|---|
| 维度 | 241 | left |
| 值 | **504** | right |
| 原始 | 178 | right |
| **类别** | **178** | left |

表格 `width:100%`（1102px），四列内容都只有 2 个字，
多余空间被均摊 →「类别」列被撑到 178px 而内容仅约 22px。

**但顺带发现更严重的问题：三列取值全错。**
接口的 `stats` 是 `{PWR:{value,label}, ...}`，而前端写的是：

```js
st[k]        → 拿到对象 → 渲染成 [object Object]
st[k+'_raw'] → 这个键根本不存在 → 「原始」恒为「—」
st[k+'_cat'] → 同上            → 「类别」恒为空白
```

★ 也就是说这一页的「原始」「类别」两列**从来没有正确显示过**
（M38 加这两列时没有对着接口验）。

**修法**：后端 SELECT 补上 `st.*_raw` 与 `st.*_cat`（数据库里本来就有这些列，
只是一直没查出来）；前端按新结构取值；表格加 `class="tight"`（`width:auto`）。

| | 前 | 后 |
|---|---|---|
| 表格宽 | 1102px | **185px** |
| 值列 | `[object Object]` | **E** |
| 原始列 | 恒 `—` | **E** |
| 类别列 | 恒空白 | **正常** |

### 2.2 M51：可继承属性 + ★ 我上一轮修错了位置

用户三张截图：「你确定吗 **我强刷新过了** 还是这个样子」。

**★ 先认一件事：M49 我修错了地方。**
用户问的是**问答页的「答案」卡片**（`.kv` 键值表），
而我量的是**数据浏览页的六维能力值表**（`renderStand`）。
那个 `[object Object]` 的 bug 是真的，但**不是用户在看的东西** ——
所以他强刷新后依然没变。**"改对了但改的不是那一处"比没改更让人困惑。**

**这一轮的真问题**：`white-space` 是**可继承属性**。

```
index.html:225  .answer { white-space: pre-wrap }
```

本意是保留**纯文本**答案里的 `\n\n` 空行（拒答文案、生成式答案）。
但结构化答案是**多行模板字符串**拼的 HTML 片段，于是被一起继承。
而事实模板里恰好**只有「类别」**那一行写成：

```html
<dt>类别</dt><dd>
  <span class="c-cat">无限</span></dd>
```

它以「换行 + 8 个空格」开头；其余 4 行 `<dd>` 都紧跟标签、无前导空白
→ **只有它中招**：pre-wrap 把这段空白原样渲染成换行 + 缩进。
★ 缩进宽度还随字号变（= 8 个空格宽）。

**为什么我上一轮量不出来**：我量的是 `dd.getBoundingClientRect()` ——
那是**网格单元格**的位置，单元格确实在正确的一列；
问题出在**单元格内部文字自己换了行**，元素位置量不到。
→ 改用 `Range.getClientRects()`（一行一个矩形）数真实行数才看见。

**修法**（三层防御）：
1. 结构化答案显式关掉 pre-wrap（`.answer.ans-html { white-space: normal }`），
   纯文本答案**保留** pre-wrap（`\n\n` 空行是要显示的）
2. `.kv` 自身声明 `white-space: normal` —— 第二道防线
3. 模板里 `<dd>` 后面不再留换行（源码也清理）

### 2.3 M52：左栏空白 201px —— 用户明确禁止"缩小雷达"

用户：「左边文字有一大边空白 因为右边的六维图会比文字大很多
……**不要跟我说缩小六维图这种解决方法**」。

**先量**（Playwright，视口 1163px）：

```
左栏文字 .zh-card-inner   174px
右栏雷达 .sp-radar        375px
→ 左栏下方 201px 空白 = 右栏高度的 54%
```

**根因**：`.stand-panel { align-items: flex-start }` 让左栏高度
**只按内容算**，行高由最高的子元素（雷达）决定 → 多出来的高度全成空白。

**做法**：反过来让左栏**有足够内容**（雷达一个像素都没动）：

1. **「六维」从一行挤 6 个 → 3×2 六格明细**
   ★ 这是雷达**同一份数据的另一种表示**，不是新数据；
   并且能表达雷达给不出的东西 ——「无数据」是**明确状态**，不是 0。
   ★ 顺手清掉了不再使用的 `.zc-dims/.zc-dim` 样式（避免两套表示漂移）。
2. 让左栏铺满右栏高度（去掉 `align-items:flex-start`，
   `.sp-info` 改纵向 flex，`.zc-dimgrid { flex:1 1 auto }`）
3. 窄屏 ≤560px 时明细改 2 列

| 替身 | 左栏 | 右栏 | 底部差 |
|---|---|---|---|
| Tusk（六维全缺） | 375 | 375 | **0px** |
| Star Platinum | 343 | 343 | **0px** |

★ **用户说"不要缩小 X"时，他要的是"让另一侧变好"，不是"哪里妥协一下"。**

### 2.4 M53：「无限」被当成「无数据」

用户：「明明天堂制造的速度是无限 为什么六维图和六维明细里写的是无呢」。

**数据**：它确实有值，不是缺数据。

```
stand_stats: made_in_heaven.spd = value NULL, raw '∞', cat 'INFINITE'
```

∞ 放不进 1..5 的等级刻度，所以数值列是 NULL —— 但它是**有值**的。

**★ 判定依据：先查真实分布，不凭直觉。**
`value` 为 NULL 时各类别的实测分布（共 276 处）：

| 类别 | 数量 | raw | 含义 |
|---|---|---|---|
| NOT_APPLICABLE | 198 | `None` | 该源未提供 |
| EMPTY_SLOT | 53 | `∅` | 空位（真缺失） |
| UNKNOWN | 16 | `?` | 未知（存在争议） |
| **INFINITE** | **6** | **`∞`** | **← 有值！** |
| CONDITIONAL_NO_BASE | 3 | `※…` | 条件值无基础等级 |

→ **只有 INFINITE 的 raw 是一个"值符号"**，其余都是真的"没有这个数"。
所以只把 INFINITE 单列，其余一律仍然算「无数据」。
★ 如果当时按直觉写「value 为 NULL 即视为缺维」，**这 6 处真值会被错杀**。

**修法**（4 处链路）：
- `media.radar_payload` 新增 `specials = {dim: 原始字面量}`，INFINITE 走这里，
  **不计入 missing**
- `radar_chart` 标签第二行直接写 `∞`；外圈画**空心**标记（区别于实心数据点
  = "超出刻度"，不猜它在刻度上的位置）；**不连线**（∞ 在刻度上没有位置）
- `executor` 新增 `level_label(value, cat)`，INFINITE → `'∞'`
- 查询链路的 SELECT **补上 `*_raw` / `*_cat`**

### 2.5 本节教训

**「先量、先查分布」在这一节救了至少两次**：
一次是发现 276 处 NULL 里只有 6 处是"有值"（否则错杀），
一次是发现「空白」的真实来源不是布局（否则改错地方）。

**而 M49→M51 这次翻车证明：只量对数值还不够，还要确认量的是用户看的那一处。**

## 3. 客户端层：改了两次都「看不到」（M50 / M56）

### 3.1 M50：服务端对，文件对，端口对 —— 差异在浏览器那一层

用户：「我看的网页还是没变，但是双击 bat 显示服务已经打开」。

**逐层排查**：

1. `start.bat` → `start.py --port 8765`，**端口与我验证的一致**
   → 不存在"改了 A 服务、用户看 B 服务"
2. `curl http://127.0.0.1:8765/ | grep 'table class="tight"'` → **命中**
   → **服务端返回的确实是新版**
3. 看响应头：只有 `etag` / `last-modified`，**没有 `Cache-Control`**
   → 浏览器按「启发式缓存」把页面缓存了

**修法**：`root()` 返回 index.html 时显式带
`Cache-Control: no-cache, must-revalidate`。
★ 与图片那条路的**策略差异是有意的**：`/images/...` 仍保留
`max-age=604800` —— 图片内容不变，缓存划算。这里只针对 HTML 入口。

★ 教训：**静态入口页默认不该被缓存**。这类问题排查起来很绕 ——
服务端、文件、端口全对，唯一的差异在浏览器那一层，**纯看日志发现不了**。

### 3.2 M56：让页面自己暴露它是不是最新版

用户：「我的网页还是没区别 **到底怎么完全刷新**」。

**先查清事实**：8765 只有一个进程（就是我起的），
响应头带 `cache-control: no-cache`，`curl / | grep` 命中的确实是最新内容
→ **服务端没问题**。但双方都无法判断是哪一种：

1. 浏览器缓存了旧页面（在加 no-cache 头**之前**缓存过的副本）
2. 打开的不是这个服务（旧进程 / 别的端口）

→ 所以光说"强刷新"解决不了，**得让它自己暴露出来**。

**做法**：
1. **构建号注入页面**：把响应体里的占位符换成 index.html 的修改时间
   （`MM-DD HH:MM`），侧栏底部印出「网页版本 10-14 18:27」，`/health` 返回同一个值
2. **页面自检**：值不像构建号 → 服务是**旧进程** → 提示重启；
   与 `/health` 不一致 → 浏览器缓存了旧页面 → 提示强刷新
3. **打开页面时自动带构建号**：`http://127.0.0.1:8765/?v=1014182701` ——
   浏览器缓存**按完整 URL** 分，页面一改参数就变，缓存必然失效。
   ★ 这比"教用户按 Ctrl+Shift+R"可靠：那是要人记住的操作，这是双击 bat 就生效

**★★ 途中我自己造了 3 个 bug，全是"不报错"那一类 ★★**

| # | 操作 | 后果 | 为什么不报错 |
|---|---|---|---|
| 1 | 插入 `_web_build()` 时把原来的 `@app.get("/")` 留在了它头上 | `/` 返回 13 字节 JSON 字符串，**整个网页白屏** | 同一路径注册两次时先注册的生效，`root()` 被**静默忽略** |
| 2 | `/health` 加了字段却没进 `HealthResponse` 模型 | 页面拿不到值 | `response_model` 会**静默丢掉**未声明字段 |
| 3 | 用**全局**文本替换注入构建号 | JS 里的 `mine === '__WEB_BUILD__'` 也被改写 → **正确的构建号反而被判成占位符**，页面自己误报"旧版本" | 字符串替换是纯文本操作，不看上下文 |

★ 共同点：都是**文本层面的操作不看上下文**（路由注册 / 模型过滤 / 字符串替换），
运行时全都不报错，**只有端到端验证才会露出来**。
→ 现在断言"占位符在 HTML 里只出现一次"（注释里提到也算），
判断"没被替换"改用**格式校验**，不再依赖会被改写的字面量。

## 4. 「导航栏」：我理解错了两次（M54 / M55 / M57）

这是本阶段唯一一组**由我的理解偏差造成**的返工。

### 4.1 M54：一次做了三件事，其中第三件理解错了

用户（一次提三件）：「A 然后帮我把答案调到替身档案之上 让人一下子就能看到答案
然后帮我做个左侧导航栏」。

前两件做对了：

**【1】让「无限」在极值排名里算最高**
「速度最高的是谁」**把速度无限的天堂制造排除了**，返回的是 A 级的 Ball Breaker。
根因：极值 SQL 用 `{dim} IS NOT NULL AND composite IS NOT NULL` 过滤 ——
∞ 的数值列是 NULL → 整行被排除。
→ 放宽为 `(composite IS NOT NULL OR {d}_cat='INFINITE')`，
并 `ORDER BY ({d}_cat='INFINITE') DESC NULLS LAST, {d} DESC NULLS LAST`。
★ **Postgres 的 DESC 默认 NULLS FIRST** —— 不显式写 `NULLS LAST`，
∞ 那一行的数值 NULL 反而会排到最前面（这个坑很容易踩）。
★ 加 caveat 说明「∞ 按高于 A 级排在 A 之前，无法与 A~E 直接比较」——
不解释的话"∞ 排第一"看着像排序出错。
★ **ASC（最低）分支保持排除** —— ∞ 不是「最低」，它不该出现在"最低"榜。

**【2】答案卡片移到替身档案之上**
`[档案+雷达] → [答案]` 改为 `[答案] → [档案+雷达] → [图片/证据] → [相似替身]`。

**【3】左侧导航栏 —— 理解错了（见 4.3）**

### 4.2 M55：把「一坨内容」变成「板块」

用户纠正：「我不是这个意思啊 是搜索出来如果是替身有关的 就应该有好几个板块
如答案 替身信息 和图片 **你先改回去** 然后再按照我的改」。

**我上一轮做错在哪**：把「图片 + 证据」塞进**同一张没有标题的卡**：

```html
<div class="card">${_media}${_ev}</div>
```

两个后果：
1. 那张卡**没有 h3** —— 它不是一个「板块」，只是一坨内容
2. 证据（折叠后 30px）被压在 **1500px 的图片墙下面** → 等于看不见

**改回 + 按用户描述做板块**：

| 板块 | 内容 |
|---|---|
| ① 答案 | 答案 + 警告/生成式 + **证据** |
| ② 替身信息 | 档案键值 + 六维明细 ｜ 六维雷达 |
| ③ 图片 | 按来源分组（本体/使者/漫画/动画/其它）|
| ④ 相似替身 | 原有 |

★ 「图片」板块由 `renderMedia` 自己产出整张卡：三种状态
（已就绪 / 抓取中 / 失败）都装在同一 个 head 里 ——
异步抓完替换内容时**标题不会消失**。
★ 没有图片信息时返回 `''` —— 不占位、不出空板块。

### 4.3 M57：「导航栏」＝ 结果页内的板块索引

用户：「我不是让你把这个改回去吗 **我要的导航栏是搜索结果出来后
能够导航到各个部分 如答案 替身资料 检索过程 图片**」。

**M54 我做成了应用级导航**（问答 / 数据浏览 / 冲突记录 / 系统状态）。
用户要的是**页面内的目录**。

| | 我做错的（M54） | 用户要的（M57） |
|---|---|---|
| 位置 | 左侧全局侧栏 | 结果区内的左侧索引 |
| 指向 | 四个**应用视图** | 一页内的**内容板块** |
| 内容 | 静态 | **按实际渲染出的板块动态生成** |

**做法**：
- 全局导航**改回顶栏**；结果区改两列 `.result` = `.res-toc` + `.res-main`
- 索引项 = 「本页内容」+ 1.答案 2.替身资料 3.检索过程 4.图片 5.相似替身
- ★ **按实际渲染出的 `[data-sec]` 生成** —— 排名类问题只有 1 块时整条隐藏，
  不会出现"点了跳不过去"的死链
- 点击平滑滚动（`scroll-margin-top` 让开 sticky 顶栏）；滚动时 scroll-spy 高亮
- 板块会**异步**增加（相似替身 / 图片抓完）→ `MutationObserver` 自动补建
- 窄屏 ≤860px 索引变成一行横排 chip
- **「检索过程」从页顶静态折叠块变成正式板块**（可被索引到），证据也归它
- 按用户用词改名：「替身信息」→「**替身资料**」

**★ 途中两个"不报错但完全失效"的坑**：

| # | 我写的 | 后果 |
|---|---|---|
| 1 | `getElementById(data-sec)` | 板块用的是 **data-sec 属性**、没有 id ⇒ 永远取到 null ⇒ **点了完全没反应**（不报错、不跳转）|
| 2 | 先 `renderProcess` 再 `renderAnswer` | `#proc` 现在由 `renderAnswer` 生成 ⇒ 往不存在的节点写入，**静默失效** |

### 4.4 本节教训

**「导航栏」这类词，先问清导航的**对象**是"应用页面"还是"内容板块"。**
两种都需要，但位置、生成方式、稳定性要求完全不同：
应用级导航是静态的，内容板块索引必须**按实际渲染结果生成**（否则出死链）。

另外：**用户说"改回去"时，要精确复原他不要的那一层，而不是全盘回退。**
M57 我保留了「答案置顶」「板块化」「检索过程成板块」，
只把"全局导航"这一件改回顶栏 —— 用户要的就是这个。

**查证结论 —— 不是"缺数据"，是"查不到 + 看不见"**：

| # | 事实 | 证据 |
|---|---|---|
| ① | 母体 `echoes` 在 `stands.json` 里**确实缺失**（只有 act1/2/3） | DB 里的母体是入库时按聚合规则**补建**的 |

   「回音ACT1」「獠牙ACT4」汉字只有 2 个。
   → 细化判据：含 `ACT+数字` 的一律放行（天然唯一、不可能是日常词）；
   其余短名走**白名单**（目前只有「回声」——**用户实际输入的全名**）
2. 母体不在 `stands.json` → 主循环遍历不到 → 「母体名反推」的后处理
   **又只查抓取源、不查补录表** → 补录的「回声」也进不来
3. `tusk_act*` 的来源译名是「牙ACT1」，其中「牙」是单字被拒 →
   **整条丢弃**，根本轮不到补录名 → 改为"来源名不合格时**退回人工补录名**"

**★ 写法差异在生成层解决，不靠人肉枚举**：
我第一版在补录表里逐条枚举「獠牙ACT1 / 獠牙ACT 1 / 獠牙 Act 1…」，
结果用户敲「獠牙 ACT2」**还是查不到** —— **枚举永远补不全**。
→ `aliases.expand_variants`：对含 `ACT+数字` 的名字自动生成
`ACT/act/Act` × 前后空格共 12 种组合（非形态名不展开，别名表不爆炸）。
**别名表 821 → 1057，16 种写法全部命中。**

**形态链在界面上可见**：
- API `/query` 响应新增 `forms`（链 + 当前段标记）；
  形态成员（`xxx_actN`）也查得到：去掉后缀取母体，返回整条链并标出当前段
- 前端「形态」行：`ACT1 → ACT2 → …`，**每段可点**，当前段高亮
- 母体自身没有六维时（数据记在各形态上）明说 ——
  否则六格"全部无数据"会被读成"这个替身什么都不知道"

### 5.3 M59：四个形态的图"一模一样"

用户：「为什么 act1-4 的图片都是一样的呢」。

**实测根因（两层）**：

**【1】源站没有形态页**
jojowiki 上 `Tusk ACT1`~`ACT4`、`Echoes ACT1`~`ACT3` **全部重定向到主条目**
→ 用形态标题去抓，拿到的必然是主条目那一批文件
→ **5 个目录的本体图 md5 逐字节完全相同**

**【2】形态专属图其实存在，只是没去分**
主条目页里就有：`Tusk ACT1 SBR Infobox Manga.png`、`Echoes ACT3 DU Infobox Manga.png`…
实测 **Tusk 有 5 张、Echoes 有 10 张**分形态的官方图。

**顺带发现的数据 bug**：抓取标题用的是 **`Echoes (ACT1)`（带括号）**，
而那个标题在 jojowiki 上**根本不存在** → Echoes 的三个形态是**零图**
（`Echoes ACT1` 才存在）。

**★ 踩的坑：不能用 `\bact\d`**
`api.php` 返回的文件名里**空格已换成下划线**（`Tusk_ACT2_SBR_...`），
而 `_` 是单词字符 → `\b` 在它前面**不成立**：
`act_label` 全返回 None，更糟的是**按 ACT 过滤会把形态的图全滤光**（又变零图）。
→ 自己定义边界：前一字符不能是字母数字（下划线算分隔符）、
ACT 与数字之间允许空格或下划线、数字后不能再跟数字。
反例验证：`Contact2.jpeg` 不会被误判成 ACT2（`cont-act2`）。

| 替身 | 修复前 | 修复后 |
|---|---|---|
| Tusk ACT1~4 | 各 4 张，与母体**逐字节相同** | 各 1~3 张**自己的 ACTn 图**，题注 ACTn |
| **Echoes ACT1~3** | **0 张** | 4 / 3 / 2 张 |
| 母体 Tusk / Echoes | 混着周边商品（亚克力摆件）| **形态图集**，每张标出是第几形态 |

不同形态之间共用图：**原来 4 组全同 → 现在 0 组**（哈希核对过）。

### 5.4 本节教训

**「四个东西一模一样」有四种可能**：源站就这样 / 抓取回退了 / 没按维度分 /
展示层拿错了。**要逐层验到源站**，否则会在中间层改错。

另外：**审计（爬到 vs 库里的差集）本身就是一种验证。**
用户说"好像没有 echo"，如果我只信这句去补数据，就会把已有的母体重做一遍；
审计结果（184 个页面 0 缺失）直接改变了处理方向 —— 从"补数据"变成"修可查性"。

## 6. 测试与 CI：让失败说清「是环境还是功能」（M60 / M61 / M62 / M63 / M64）

`/health: status=degraded database=disconnected n_stands=0`，5432 无监听。

| 断言 | 为什么依赖 DB |

### 6.2 M61：环境不满足 → 跳过，而不是报错

★ **语义上数据库属于环境前提**，不该让整条流水线因为没开 Docker 而挂红。

- `test_gui_e2e`：缺库时**默认"跳过"不算失败（退出码 0）**，
  并打印醒目横幅说明原因与起库命令；
  需要严格时用 `--require-db`（或 `CI=true`）→ 缺库即失败（退出码 1）
- 新增 `evaluation/check_env.py`：一条命令看清"能不能跑测试"
  （数据库连通性 / playwright / 网页服务），退出码 0=就绪 1=环境不满足

**★ 写它时踩了个坑**：`load_db.connect()` 连不上时是**直接 `sys.exit(1)`**
（它自己打排查清单），而 `SystemExit` **不是 `Exception` 子类** →
我只写 `except Exception` 时，脚本在打印 ✗ 之前就退出了（表现为"只打了个标题就没了"）。

→ 前端走"后台抓取中"分支（转圈 + 轮询），而抓取远慢于 25 秒 → 超时。

★ 我前两次都按"本地缺数据库"处理，**没认出是 CI 环境**。

**修法**（与 M61 同一套）：
- `test_gui_e2e` [4]：无缓存则跳过该断言（它只检查"**已缓存**的图会立刻出"）
- `test_m19_thumbs` / `test_m59_form_images`：整体跳过（核对的正是抓取产物）
- 实测两条路径：**有缓存 → 真检查（`gui_e2e` 16 张 PASS）；无缓存 → 跳过且 rc=0**

**★★ 差点搞丢 423MB 图片（记下来避免再犯）**
模拟 CI 时 `mv images _images_bak` → 跑测试（app 又 mkdir 出空 `images/`）→
`mv _images_bak images` 把备份**嵌进了** `images/_images_bak`
（表现为"目录只剩 1 个子项"）。
→ 已恢复并校验：**188 目录 / 188 清单 / 423M**，抽查 `images/tusk/` 正常。

★ 教训：**目录级 mv 做临时腾挪，目标必须放到项目外**；
且恢复后必须核对**条目数（目录数 / 清单数 / 体积）**，不能只看"命令没报错"。

### 6.5 本节教训

**「环境不满足」与「功能坏了」必须分开报。**

同一句 `FAIL 已缓存替身图片直接显示`，三次的真实原因分别是：

| 次数 | 报错 | 真实原因 |
|---|---|---|
| 1 | 等 25 秒仍未出现 | 本地 Docker 没启动（数据库不可用）|
| 2 | 同上 | 同上（用户已启动 Docker，但那次运行在启动之前）|
| 3 | 同上 | **CI 环境没有 images/（.gitignore）** |

**报错文案不区分这两类，就会让每一次排查都从零开始** —— 我自己就误判过两次。

### 6.6 补档时发现：对外数字闸门一直红着

`evaluation/collect_metrics.py` 有一道「对外表达」闸门（M8 建的）：
`PUBLIC_NUMBERS` 把简历/报告里引用的数字与产物比对。这次补档跑 `--check`：

```
✗ M1.替身数: 对外写 154，产物是 187——报告与数据脱节，面试会被问穿
✗ M1.形态数: 对外写 146，产物是 153
✗ M1.完整度: 对外写 0.7987，产物是 0.6578
```

**这三个不是"写错了"，是"时点不同"** —— 它们是 M1 时的基线，
而 M39–M45 补了第 8/9 部。闸门把「历史基线」和「当前值」混在一张表里，
于是每次补数据都产生假告警。**假告警多了，真脱节就没人看了。**

→ 拆成两张表：`PUBLIC_NUMBERS`（只校验**当前**值）
+ `HISTORICAL_NUMBERS`（历史基线，仅作对照、不校验）。

**★★ 更要紧的是「六维完整度」这一项。**
79.87% → 65.78% 看着像退步，实测根因是**分母变了**：

| | M1 时 | 现在 |
|---|---|---|
| 替身数（分母） | 154 | **187** |
| 六维**齐全**的替身（分子） | 123 | **123（没变）** |
| 齐全率 | 79.87% | **65.78%** |

按部看很清楚（充实测输出）：

```
按部齐全率：第3部 100% 第4部 82% 第5部 81% 第6部 56%
            第7部 76%  第8部 19% 第9部 0%
```

**第 8/9 部的低不是我们的问题** —— 第 9 部 13 个替身共 78 个槽位**全空**，
是数据源（jojowiki 的 `Stand_Stats` 表）本身不提供这两部的六维。
→ 现在摘要里**同时**打印「齐全率」与「按部齐全率」，并明确写出这一条原因，
防止这个数字被（我或读者）误读。

★ 这条对**简历**有直接后果：
**「六维完整度 79.87%」不能再用了** —— 它现在是 65.78%，
而唯一诚实的写法是「第 3–7 部完整度 56–100%，第 8/9 部数据源不提供六维」。

### 6.8 M64 收尾：最后一个失败查清了 —— **三个假设，前两个都是错的**

补档后跑全套 **27/28**，唯一失败 `test_generate_mode`。
这个"最后一个失败"花的时间最多，**完整记录排查路径**（因为走错了两条路）。

**现象**（随机得毫无规律）：

| 哪一次跑 | 结果 |
|---|---|
| 全套回归 | 第 5 项第一次 32.8s 成功、**第二次超时** |
| 单独跑 A | 第一次 32.8s 成功、**第二次超时** |
| 单独跑 B | **第一次就超时** |
| 单独跑 C | 第一次 36.3s 成功、**第二次超时** |
| 对照脚本（另一脚本、同一条序列）| **三次全部 200 OK**（38.8s / 14.3s / 14.6s）|

#### 假设 ① 「显存 / 进程竞争」→ **证伪**

测前先查环境：GPU 上**没有** python 进程、无残留服务、无监听端口（1279 MiB）。
**在完全干净的环境里重跑 → 仍然第二次超时。**

#### 假设 ② 「本地请求走了代理」→ **证伪**

发现环境带 `http_proxy=127.0.0.1:54302`（Clash 类），而
`urllib.request.urlopen` **默认读代理环境变量** —— 连 `127.0.0.1:PORT` 也走代理。
于是做了对照实验：

| 实验 | 默认 opener | `ProxyHandler({})` |
|---|---|---|
| 短请求 | 成功 0.05s | 成功 0.03s |
| **25 秒慢响应**（模拟生成式）| 成功 25.0s | 成功 25.0s |

→ 代理本身不背这个锅。（但"回环请求不该走代理"仍是对的，顺手统一改了。）

#### 假设 ③ 「子进程 `stdout=PIPE` 但全程不读」→ **成立** ★

`_start()` 起服务时 `stdout=subprocess.PIPE`，而父进程**直到服务退出才读**。
服务加载 Qwen 时 tqdm 会打出大量进度行（`Loading weights: 38%|███▊| 130/338`），
**Windows 管道缓冲区（约 4KB）写满后，子进程会阻塞在 write 上** ——
服务就此卡死：既不回响应、也不退出，客户端只能等到 300 秒超时。

**为什么"随机"**：输出总量在缓冲区边界附近波动 → 有时刚好没写满（成功）、
有时写满（卡死）。这正好解释了"第一次成功第二次失败"与"第一次就失败"的交替。

**修法**：服务端输出**写日志文件**（永不阻塞），失败时读它打印。

| | 修复前 | 修复后 |
|---|---|---|
| 总耗时 | 5m5s ~ 5m45s（都在等 300s 超时）| **58s ~ 1m6s** |
| 第二次生成 | 超时 | **15.1s / 15.4s**（连跑 2 次均通过）|

#### 顺带查出并修掉的两个真 bug（同一家族）

1. `test_alias_and_relevance` / `test_m39_zh_variants` / `test_degraded_mode`
   也在用 `urllib.request.urlopen` 打本机服务 → 统一改走 `_opener()`（绕过代理）
2. ★★ **我的 `_opener()` 第一版就写错了**：`urllib.request` 在
   `test_alias_and_relevance` 里是**函数内 import** 的，而我把 `_opener()`
   定义在模块级 → 调用时 `NameError`，而它被
   `except Exception: pass` **吞掉** → 表现为"**服务启动超时**"，
   与真实原因毫无关系。→ 把 import 移进函数体。

★ 又一次"不报错但完全失效"，与 §4.3（data-sec）、§6.7（旧数字）同一个家族。

#### ★ 这次最该记的不是结论，是**过程**

三个假设里**前两个都是错的**，而且每个都"看起来很像"。
把它们写下来是因为：**只看结论的话，下次还会从同样的错误假设开始。**
真正的定位靠的是**逐项排除 + 对照实验**——干净环境跑一次、
用 25 秒慢响应单独验代理、拿另一个脚本作对照 —— 而不是"想明白了"。

★ 这条也补上了 §6 主线的第四种形态：环境问题除了「**缺东西**」（DB / 模型 / 图片），
还有「**缓冲/资源被卡住**」，而后者更难认——因为它表现得像"服务死了"。

## 7. 贯穿十九轮的结构性教训

### 7.1 静默错图谱（本轮新增的四类）

M39–M45 归纳过四类静默错（丢数据 / 答错 / 拒答 / 用旧数据）。
这十九轮又出现四类**新的**：

| 类型 | 例子 | 危险之处 |
|---|---|---|
| **静默截断** | `imlimit` 是总上限，超了返回 `[]` | 不报错，表现成"这个替身没有图" |
| **静默继承** | `white-space: pre-wrap` 被结构化答案继承 | 不报错，只有某一行多出缩进 |
| **静默错列** | 前端按 `st[k]` 取对象、按不存在的键取 raw/cat | 不报错，**两列从来没有正确显示过** |
| **静默忽略** | 同路径注册两次路由；`response_model` 丢字段 | 不报错，前者让整页白屏，后者让字段消失 |
| **静默阻塞** | 子进程 `stdout=PIPE` 而父进程不读 → 写满管道缓冲后卡死 | 不报错，服务"像是死了"（见 §6.8）|

★ 共同点：**运行时不报错，只有"对着用户看到的东西验一遍"才能发现。**

### 7.2 「归一化 / 模糊匹配」踩了三次

| # | 场景 | 错误假设 | 实际 |
|---|---|---|---|
| 1 | 补录译名的空格变体 | 逐条枚举就够了 | 枚举**永远补不全**（用户敲「獠牙 ACT2」仍查不到）|
| 2 | 编造词比对 | 直接 `in` 比对 | 别名表存「獠牙ACT4」，用户写「獠牙 ACT4」→ **必须去空格** |
| 3 | ACT 图片过滤 | 用 `\bact\d` | **api.php 返回的文件名里空格已换成下划线** → `\b` 不成立 → 过滤把图全滤光 |

→ 已成规则：**凡是要做模糊匹配的地方，先确认那批数据的真实形态**
（空格？下划线？大小写？），再决定归一化规则。

### 7.3 「先量 / 先查分布」救了几次

| 场景 | 如果按直觉写 | 实际查完发现 |
|---|---|---|
| ∞ 是否为缺值 | 「value 为 NULL 即缺维」→ **错杀 6 处真值** | 276 处 NULL 里只有 INFINITE 的 raw 是值符号 |
| 「类别后面的空白」 | 以为是 grid 的 gap | gap 只有 16px，真因在**单元格内部换行** |
| 「左边一大边空白」 | 以为该缩窄右栏 | 方向反了，该让左栏**有内容** |
| 「图片都一样」 | 以为是抓取 bug | 源站把形态页**重定向**到主条目 |
| 「好像没有 echo」 | 以为缺数据 | **审计显示 184 个页面 0 缺失** |

### 7.4 我的元错误清单（可迁移）

这十九轮里，**由我造成的返工**有五处，模式高度一致：

| # | 元错误 | 表现 | 对策（已落地）|
|---|---|---|---|
| 1 | **改对了但改的不是那一处** | M49 修了数据浏览页，用户看的是问答页 | 修之前先确认**用户看的是哪个页面/哪个元素** |
| 2 | **文本操作不看上下文** | 全局字符串替换改坏了 JS 字面量；路由注册两次 | 替换前后断言"占位符只出现一次"；端到端验一次 |
| 3 | **验证脚本自己写错** | 用 `index()` 找代码却命中注释里的同一句 | 断言用**按行正则**匹配 |
| 4 | **判据与实现不一致** | 前置检查去查 HF 缓存，代码实际读项目内 models/ | 判据向**被测代码自己的判据**看齐 |
| 5 | **临时腾挪不看条目数** | `mv` 把 400MB 图片嵌进子目录 | 目标放项目外；恢复后核对**条目数** |
| 6 | **新加的 helper 依赖了作用域外的东西** | `_opener()` 定义在模块级，而 `urllib.request` 是**函数内** import → 静默 `NameError`，被 `except Exception: pass` 吞掉 → 报成「**服务启动超时**」 | 依赖在 helper **自己的作用域内**导入；不要用裸 `except Exception: pass` 吞异常 |

★ 这六条的共同点：**都是"我以为是 A，实际是 B"，而当时都有可用的信号能发现。**
所以对策统一为一句 —— **别只看命令的返回码，要看它的产物。**
