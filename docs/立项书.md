## 1. 项目定位

### 1.1 一句话定义

> **一个面向异构知识源的检索系统：当一次查询同时需要结构化精确计算和语义理解时，系统如何决策"查哪边"、如何融合两边的结果、以及如何处理两者之间的冲突。**

数据集采用系列作品设定集（172 条结构化记录 + 配套文本），作为方法的验证载体；方案本身不绑定该领域。

### 1.2 为什么不叫"设定集知识库"

| 考量 | 说明 |
| --- | --- |
| 面试官认知标签 | 标题带特定作品名，第一印象是"兴趣驱动"而非"工程能力" |
| 可迁移性证明 | 标题绑定领域，等于自证方法不可迁移 |
| 数据集规模 | 172 条被质疑"为什么要用 RAG"时，无法自圆其说 |

**处理方式**：项目标题与简历中不出现作品名；数据集作为 `dataset/` 下可替换的资产存在；技术文档中论证"本项目研究的是检索决策机制，语料规模不是自变量"。

### 1.3 三个差异化护城河（均架在 C++ 后端背景上）

| 差异点 | 具体内容 | 面试可深挖的深度 |
| --- | --- | --- |
| **混合检索决策** | 意图路由 + 冲突消解 + 脏数据分类处理 | 讲清"什么时候不该用 RAG"比"怎么用 RAG"更显功力 |
| **C++ 服务层** | epoll 事件循环 / 线程池 / SSE 流式 / 语义缓存 / 多租户 | 唯一能体现 C++ 功力的落点，且是简历硬差异点 |
| **量化评测体系** | 180 条可 100% 人工核对的评测集，全指标自动对比 | 别人只能说"效果不错"，我能说"切块策略 B 使 Recall@5 提升 12.3%，P99 增加 40ms" |

## 3. 技术架构

### 3.1 整体链路

```
                        ┌────────────────────────────┐
   自然语言查询  ────────►│  意图路由 Intent Router    │
                        │  纯事实 / 纯语义 / 混合 / 无  │
                        └───┬────────────────┬───────┘
                            │                │
              ┌─────────────▼──┐         ┌──▼─────────────┐
              │ 结构化路径      │         │ 语义路径        │
              │ Text-to-Query  │         │ 向量 + BM25    │
              │ 编译为 SQL      │         │ RRF 融合       │
              │ 极值/链式 JOIN  │         │ 交叉编码器重排   │
              │ 单位解析        │         │                │
              └───────┬────────┘         └──────┬─────────┘
                      └───────────┬──────────────┘
                                  │
                    ┌─────────────▼─────────────┐
                    │  融合与冲突消解            │
                    │  两侧结果可能矛盾           │
                    │  加权 RRF / 规则 / 置信仲裁  │
                    └─────────────┬─────────────┘
                                  │
                    ┌─────────────▼─────────────┐
                    │  无答案判定与拒答│
                    └─────────────┬─────────────┘
                                  │
                    ┌─────────────▼─────────────┐
                    │  C++ 服务层│
                    │  epoll / 线程池 / SSE       │
                    │  语义缓存 / 多租户 / 限流    │
                    └─────────────┬─────────────┘
                                  │
                    ┌─────────────▼─────────────┐
                    │  观测 + 评测               │
                    │  Prometheus / Grafana      │
                    │  180 条评测集 / 版本对比    │
                    └───────────────────────────┘
```

### 3.2 双数据集

| 数据集 | 角色 | 规模 | 目的 |
| --- | --- | --- | --- |
| **设定集数据**（主） | 深度挖掘混合检索难题 | 172 条结构化 + 文本 | 结构化/语义冲突、脏数据、多跳查询 |
| **企业文档集**（验证） | 证明方案可迁移 | 公开技术文档若干 | 验证同一套检索逻辑在纯文本场景仍有效 |

**为什么必须做第二个数据集**：只在一个小众领域验证，面试官无法判断方法是通用解法还是为数据集定制。这是「方法论项目」与「玩具项目」的分界线。

### 3.3 技术栈（已定稿）

| 层 | 选型 | 关键说明 |
| --- | --- | --- |
| 解析 | PyMuPDF · trafilatura · 自写 HTML/MD 解析 | 第二数据集需要 |
| 切块 | 自实现，**招式级语义切分** | 能力描述有天然结构，不用固定长度 |
| Embedding | **bge-m3，fp16** | 568M 参数，2.2GB 显存，MIT 授权 |
| 向量库 | **pgvector**（非 Milvus） | 172 条数据无需专用向量库，部署成本低 |
| 稀疏检索 | PostgreSQL 全文检索 / BM25 | 同库，减少依赖 |
| 重排 | bge-reranker-v2-m3 | 0.6B，1.1–2.4GB，与 embedding 错峰 |
| 生成 | **Qwen2.5-1.5B (Q4) 为主力** | 1.2GB；7B 作对照实验 |
| 服务层 | **C++20** | epoll · 线程池 · SSE |
| 编排 | LangGraph | Agent 能力需要 |
| 监控 | Prometheus + Grafana | 工业界标准 |
| 评测 | 自建评测集 + RAGAS 交叉验证 | 自建为主体 |

### 3.4 显存分配（8GB 硬约束下的工程决策）

| 用途 | 模型 | 显存 | 策略 |
| --- | --- | --- | --- |
| Embedding 常驻 | bge-m3 fp16 | 2.2 GB | 常驻 |
| Rerank 错峰 | bge-reranker-v2-m3 | 1.1 GB | 与生成模型错峰加载 |
| 生成常驻 | Qwen2.5-1.5B Q4 | 1.2 GB | 常驻 |
| KV Cache 预留 | 8K 上下文 | 2.0 GB | **最易被忽略的一项** |
| 余量 | — | 1.5 GB | 防止长输入 OOM |

**关键约束**：使用 fp16 而非 fp32（实测 bge-m3 fp32 需 3.5GB，fp16 仅 2.2GB，检索任务精度损失几乎可忽略）。省下的 1.3GB 决定 7B 对照模型能否塞入。

**追加实验（吃 Ada 架构红利）**：RTX 4060 Laptop 为 Ada 架构（Compute 8.9），支持 FP8 推理。可做 **FP8 vs FP16 vs INT4 的精度-吞吐对比**。

**资源约束下的取舍论证**（可写进报告）：
```
理论吞吐上限( tok/s ) ≈ 显存带宽(GB/s) ÷ 模型文件(GB)
RTX 4060 Laptop: 256 GB/s ÷ 1.2 GB ≈ 213 tok/s
```
实际输出远低于此（KV Cache 读写、采样开销、笔记本降频）。给出理论上限再解释实际差距，比只报单一数字更专业。

## 4. 核心设计决策（实验假设，非既定结论）

| 编号 | 决策点 | 对比方案 | 观测指标 |
| --- | --- | --- | --- |
| D1 | 文本切块策略 | 固定长度 / 递归字符 / 招式级语义切分 | Recall@K、答案正确率、token 消耗 |
| D2 | 检索模式 | 纯向量 / BM25 / 混合 RRF | 召回率、延迟 |
| D3 | Rerank 开关与深度 | 不重排 / Top-50 / Top-20 | MRR、nDCG、TPOT |
| D4 | 混合权重 α | 扫描取值 | 召回率-α 曲线拐点 |
| **D5** | **结构化-语义冲突消解** | 加权 RRF / 规则优先 / 置信度仲裁 / 二次验证 | 冲突检出率、误仲裁率 |
| **D6** | **生成模型规模与精度** | 1.5B FP16 / 1.5B INT4 / 1.5B FP8 / 7B Q4 | 准确率、成本、延迟、**显存可行性** |
| D7 | 语义缓存阈值 | 关闭 / 0.92 / 0.95 / 0.98 | 命中率 vs 误命中率、TTFT |
| **D8** | **脏数据编码策略** | 异常值当缺失 / 分类编码（本项目方案） | 脏数据处理准确率、冲突误判率 |
| **D9** | **检索路由决策** | 规则分类 / 小模型分类 / 混合 | 路由准确率、误路由惩罚 |

> D5、D8、D9 是本项目区别于普通 RAG 的三个核心实验，也是面试时的主讲内容。

## 5. 评测方案

### 5.1 评测集（180 条，7 类）

| 题型 | 数量 | 标注成本 | 考察点 |
| --- | --- | --- | --- |
| 事实型 | 40 | 极低 | 基准准确率 |
| 极值推理 | 30 | 低 | 结构化计算（Text-to-Query） |
| 多跳/实体链 | 25 | 中 | 跨表 JOIN、形态链遍历 |
| 语义理解 | 25 | 中 | 向量检索质量 |
| **混合协同** | 25 | 高 | **核心差异化**：需两侧同时参与 |
| 无答案/边界 | 20 | 中 | 拒答与幻觉抑制 |
| **脏数据/冲突** | 15 | 高 | **独特考点**：∞ ∅ ? 条件值 |

**核心优势**：172 条数据可 100% 人工核对并交叉验证——这是企业场景根本做不到的，评测可信度天然解决。

### 5.2 指标体系

```
检索层：Recall@K · MRR · nDCG@K
编译层：Text-to-Query 编译准确率 · 无法编译时的拒答率
路由层：路由准确率 · 误路由导致的错误率
消解层：冲突检出率 · 误仲裁率
生成层：答案正确率 · 忠实度 Faithfulness · 引用准确率
系统层：TTFT · TPOT · P95/P99 · QPS · token 成本 · 缓存命中率
```

## 10. 简历项目描述（草稿，待数据回填）

> **多模态混合检索系统：结构化-非结构化联合推理** ｜ 个人项目 ｜ 2026.10 –
>
> 面向异构知识源（结构化数值表 + 非结构化文本）的联合检索系统，解决"一次查询同时需要精确计算与语义理解时如何决策与融合"的问题。
>
> - 构建 180 条可 100% 人工核对的评测集（7 类题型：事实型/极值推理/多跳/语义/混合协同/无答案/脏数据），量化对比各版本策略，避免主观评价。
> - 设计意图路由层，将查询分流至结构化 SQL 路径或语义向量路径，路由准确率达 XX%，误路由导致的错误率 XX%。
> - 实现混合融合与冲突消解机制，识别两侧结果矛盾（如结构化"等级 E" vs 文本"时停 5 秒"），冲突检出率 XX%，误仲裁率降至 XX%。
> - 设计脏数据分类编码方案，区分「缺失（∅）」「未知（?）」「不适用（N/A）」「无限（∞）」「条件值」五类语义，在脏数据样本上处理准确率达 XX%。
> - 在 8GB 显存约束下完成 fp16/INT8/FP8 精度对比与模型错峰加载，量化不同模型规模的成本-准确率-延迟三角权衡，输出选型结论。
> - 基于 C++20 实现服务层（epoll 事件循环 / 线程池 / SSE 流式 / 语义缓存 / 多租户隔离），P99 延迟 XX ms，语义缓存使重复问题 TTFT 下降 XX%。
>
> **写法要点**：
> - 每个数据点必须来自真实评测，不允许估算
> - 百分比必须写清基线（"从 X% 提升至 Y%"而非"提升 Y%"）
> - 保留一个取舍陈述，体现工程判断力
> - 投 AI Infra 岗时把 C++ 服务层那条提到首位
