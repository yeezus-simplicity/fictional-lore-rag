# M74：搜索体验（模糊 / 多候选）+ 角色与地点图片

> 本文档由**用户实测反馈**驱动 —— 不是我自己找的方向。
> 用户原话（一次报完）：
>
> 1. 搜索人物时不会返回人物的图片
> 2. 我搜索承太郎、迪亚哥、齐贝林都搜索不到
> 3. 搜英文好像必须分清大小写还是什么，根本没有模糊搜索，我搜 dio 也搜索不到
> 4. 地点要是有图片也加上吧
> 5. 要是有重名的角色，如齐贝林、乔斯达、东方仗助，就都返回就行了

---

## 1. 五个诉求 → 五个根因

| # | 用户感受 | 实际根因 |
|---|---|---|
| 1 | 人物没有图片 | 替身图片 M17 就有，**角色/地点从来没做** —— 而它们的 infobox 里本来就有图 |
| 2 | 「承太郎」搜不到 | `match()` 的方向是「**名字 ⊂ 问句**」，用户打简称时方向反了 |
| 3 | 「齐贝林」搜不到 | M73 把**歧义简称（姓氏）整条丢掉** —— 理由是"收了必然答错" |
| 4 | 「dio」搜不到 | 英文只做**全名**匹配：`(?<!…)dio brando(?!…)` 在 "dio" 里当然找不到 |
| 5 | 重名只答一个 | 命中多个时只取 `from_name[0]` → 随机答一个 |

**注意 2 和 3 是我上一轮（M73）自己造成/遗留的**：
- M73 给「含间隔号的名字」拆简称，但**无间隔号的日式名字**（空条承太郎）不拆 → 承太郎搜不到
- M73 判断「歧义简称收了必然答错」→ 干脆不收 → 齐贝林搜不到

第 3 条尤其值得记：M73 的推理在**"精确反查"**的语境下是对的
（一个名字只能对应一个 id），但我把它套到了**"搜索"**上 ——
搜索要的恰恰是"把这些人都列出来"。**同一个词，两种场景，两种正确行为。**

## 2. 修法

### 2.1 模糊搜索：两轮匹配，方向相反

```
match()       = 名字 ⊂ 问句      （用户打全名）
fuzzy_hits()  = 问句片段 ⊂ 名字  （用户打简称/姓氏）
```

`fuzzy_hits()` 的做法：
1. 建**中文名子串索引**（≥2 字，过滤问法词）
2. 从问句里找出所有命中片段，**按长度降序贪心选取、不重叠**
   （「齐贝林是谁」先命中「齐贝林」，不会再用「贝林」去撞别人）
3. 英文另走一路：问句里的英文词是某英文名的**前缀/整词**（`dio` → `Dio Brando`）

实测结果：

| 查询 | 修前 | 修后 |
|---|---|---|
| 承太郎 | ✗ | 空条承太郎 |
| 迪亚哥 | ✓ | 迪亚哥·布兰度 |
| 齐贝林 | ✗ | **5 个** |
| 东方 | ✗ | **11 个** |
| dio / DIO | ✗ | 迪奥·布兰度 |
| Jotaro | ✗ | 空条承太郎 |

### 2.2 歧义：从「不收」改成「**都返回**」

新增 `build_char_alias_index()`（多值、含歧义），与 `build_char_alias_table()`
（单值、歧义不收）**并存**：

| | 用途 | 歧义处理 |
|---|---|---|
| `table()` | 按名字查**一个人**（精确反查、`by_name`） | 不收（无唯一答案） |
| `index()` | 查这个名字**属于哪些人**（搜索、路由判定） | **全收** |

答案层新增 `character_candidates`：命中多个时**列出全部**，每张卡片带头像、
部数、替身名，点击可继续问。

```
问：齐贝林是谁
答：「齐贝林」匹配到 5 个角色，全部列出：
    [头像] 杰洛·齐贝林     Gyro Zeppeli        第7部  替身 铁球破坏者
    [头像] 西撒·A·齐贝林   Caesar A. Zeppeli   第2部  替身 泡沫
    [头像] 格雷戈里奥洛·齐贝林 / 马力欧·齐贝林 / 威廉·A·齐贝林
```

### 2.3 角色与地点图片

替身图片机制（M17/M19/M59）已经很成熟，直接复用它的两样东西：
- `_thumb_url()`：按 MediaWiki 的 md5 规则构造 400px thumb URL（**对任意文件名通用**）
- `_fetch_one` 的「thumb 失败退原图」逻辑

新增 `dataset/sources/images/fetch_entity_images.py`：
- 角色：`{{Character Infobox | image = …}}` 的第一个 `[[File:XXX.png`
- 地点：`{{Location Infobox | image}}`，兜底 `{{Media | *Av = XXXAv.png}}`
- **1 张/实体**（不像替身要抓整页几十张）→ 492 个实体 2.5 分钟（4 并发）

| | 解析到 | 抓取成功 | 入库索引 |
|---|---|---|---|
| 角色 | 363/368 | 358 | 358 |
| 地点 | 157/157 | 131 | 131 |
| 合计 | 520 | **489** | **489**（150.9MB） |

地点从 157 掉到 131 是**对的** —— 26 个用的是源站占位图
（`NoPicAvailable.png` / `NoPicAv.png`），显示出来就是一个"无图"方块。

端点：`GET /media/{kind}/{entity_id}`（`kind` ∈ character / location），
按 `media_index.json` 服务文件，带 7 天缓存。

## 3. 踩的坑

**① 正则没跨行 → 只认出 116/368 个角色**
`|image = {{Tabber\n|Part 3|\n{{Switch\n|Tab1 = Manga|[[File:…`
只取同一行会停在 `{{Tabber`。改成「`|image =` 之后 900 字符内找 `[[File:`」
→ 116 → **363**。

**② 占位图过滤写窄了**
第一版写 `NoPicAvailable`，测试当场抓到实得 `['NoPicAv.png']` ——
源站有两种缩写。改成 `NoPic` 前缀。

**③ 索引"合并旧键"导致脏数据删不掉**
`fetch_entity_images.py` 第一版从旧 `media_index.json` 读进来再更新 →
被过滤的占位图条目**永远留在索引里**。改成全量跑时**从零重建**
（`--only` 时才合并，因为要保另一类）。

**④ 放宽匹配的最大风险是守门**
子串索引一旦过宽，「今天天气怎么样」就会变成"有答案"。
两道防线：
- 索引只含**角色名**的片段（「天气预报」是**替身**名，不在角色表 →
  「天气」不进索引）
- Router 的 `has_domain` 只加 `character_hit`，不加"随便命中"

实测「今天天气怎么样」「华盛顿在哪里」「甘道夫的替身是什么」仍全部 abstain。
