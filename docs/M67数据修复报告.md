# M67：多值字段粘连修复 —— 从「角色名粘成一串」到「M65 埋下的库灌不进去」

> 完成日期：2026-10-15
> 主线：**「有这条数据」≠「这个实体是对的」**，以及**「本地能跑」≠「全新部署能跑」的第三种形态**。

本文逐段记录修了什么，并在第 6 节归纳三类结构性教训。

---

## 1. 起点：M66 报告里留下的那条「已知问题」

M66 结束时发现：DB `characters` 有 178 行，其中 **10 行没有独立角色页**，
而且名字是**多个角色名粘连**：

```
Andre BoomboomL.A. Boomboom
Caravan SeraiChakaFour Unnamed miceKhanJean Pierre PolnareffUnnamed boyCow
Whitesnake's Unknown Victim Thunder McQueen
```

当时判断「与 M65 那 13 个抓不到的角色页同一根因，属 M1 抽取链，改动面大」，
于是只记报告没有修。本轮（用户「先修」）把它连根挖了一遍。

---

## 2. 根因：抓取层把 `<br>` 当成了「无分隔符」

先看**未修复前的数据长什么样**：

```python
>>> next(s for s in stands if s['stand_id']=='anubis')
{'owner_name': 'Caravan SeraiChakaFour Unnamed miceKhan...', ...}
```

而**同一份数据的 wikitext 语料里**（`articles.json`，M58 起就抓了）：

```
|User = [[Caravan Serai]]<br />[[Chaka]]<br />[[Four Unnamed mice]]<br />[[Khan]]<br />...
```

→ **信息一直在，只是在 M1 的 HTML 抓取层被压掉了。**

根因在 `dataset/pipeline/scrape.py`：

```python
val = _clean(sib.text_content())      # ← 问题在这
```

`text_content()` 只取文本节点，**`<br>` 不产生任何字符**；
随后的 `_clean()` 又做 `" ".join(s.split())` 压空白。
两个名字之间**一个分隔符都不剩**，于是：

```
Caravan Serai<br />Chaka   →   "Caravan SeraiChaka"
```

★ 这与 M65 的坑 2（只取 wiki 链接丢掉裸文本）**同族但不同层**：
那次是「取值方式丢信息」，这次是「**分隔符本身就是信息，而它不落地**」。

---

## 3. 修法：三层，每层都有校验门

### 3.1 根因层：`_text_with_breaks()`（`scrape.py`）

不删 `<br>`，而是**把它换成 `, `**：

```python
def _text_with_breaks(node) -> str:
    """按 <br> 插入 ', ' —— 源站用 <br> 表示「并列的多个值」。"""
```

★ **长度阈值用无分隔版本判定**（保持原有语义不变）——否则加了 `, ` 之后
长值可能被新阈值误杀。宁可漏修，不可错删。

### 3.2 数据层：`repair_owner_split.py`（不重抓，就地恢复）

既然 wikitext 语料里有显式分隔符，**不必重抓 154 个页面**。
脚本做三件事：

1. **检测**：`owner_name` 无 `, ` 但源站 `|User =` 有多个 `[[...]]` 段
   → 判为粘连。★ 判据是「**以源站为准**」，不是「名字里有没有驼峰边界」——
     后者会把 `McQueen`、`Jolyne Cujoh` 这种正常名字误判成粘连。
2. **修复**：用源站的段重建 `owner_name`（`,` + 空格分隔）。
3. **校验门**（`sig()`）：新旧值的「字母数字指纹」必须相同，
   或旧值是新值的子串（源站比我们多一段的情况）。
   → **18/18 全部通过校验才写盘**，1 条不过就整体不写。

★ 途中这条校验门拦下过一次真实错误：我第一版把「分隔符带入的逗号」
也算成差异 → 15 个全部被拦下。**校验门严一点是好事，但严错了方向就等于没有。**

### 3.3 展示层：`stand_type` 明确**不修**（附原因）

`stand_type` 有同样的问题（`AutomaticShort-Range` 这种）。
我试过用**约束求解**从数据反推 `{{ST|缩写}}` → 全名的映射：

```python
m: dict[str, str] = {}
for _ in range(12):                      # 迭代消元
    for sid, ts in tokens.items():
        unknown = [i for i, t in enumerate(ts) if t not in m]
        if len(unknown) != 1: continue
        # 用「前后已知段能对齐」推出中间那段
        ...
```

结果**解不出来**：

- `Bound` 被错配（首答优先，两个缩写争同一个值）
- `PH` → `Phenomenon` 还是 `Physical Humanoid`？**两种都对得上**
- 源站没有 `Template:ST` 的定义页，主表 HTML 也没有展开列

→ **结论：缩写展开无法确定，就不修**。只把 45 个粘连的 `stand_type`
连同「为什么修不了」写进脚本注释。
★ 这与 M65 中文名那条同一取舍：**宁可少修，不出错数据。**

## 4. ★ 顺带挖出 M65 埋的两个坑（都是「本地能跑、全新部署炸」）

修完 owner 重建数据库时，`load_db --load` 直接报错。逐一定位：

### 4.1 `text_chunks` 没写 `location_id` → 违反三选一约束

```
CheckViolation: chk_chunk_owner
Failing row contains (6762, null, 'Air Supplena Island', …)
```

M65 建了 `chk_chunk_owner`（替身/角色/地点三选一），
但 `load_db` 写 `text_chunks` 时**只写 `stand_id` / `character_id`**
→ 1179 个地点块全部违反约束。

★★ **为什么一直没暴露（这才是要记的）**：

| 环境 | 为什么看不见 |
|---|---|
| CI | 用**合成语料**（`make_min_fixture` 只造替身/角色块），**没有地点块** → 这条路径永远走不到 |
| 本地库 | `text_chunks` 是 M65 **之前**灌的；M65 之后只跑过 `--init`（只建表不入库）→ 也看不见 |

**这正是「本地能跑 ≠ 全新部署能跑」的第三种形态**：
前两种是「缺依赖」「表不在 schema 里」，这次是——
**缺的不是代码，是「某条数据路径从来没被跑过」。**

→ 用 `git checkout` 还原 HEAD 版 `load_db.py` 复跑 `check_fresh_deploy`，
确认**失败在 HEAD 上就存在**（M65 留下的，不是本轮引入的）——这正是我记忆里那条
「判断某失败是不是自己造成的：`git stash` 后复跑」。

### 4.2 `locations` 三张表只有 schema、没有 loader

M65 建了表、写了 JSON 产物，但 `load_db` **从不读 `locations.json`**
→ 全新库里 `locations` / `location_places` / `location_mentions` **全是空的**。

补上 loader（含 `types` 数组的传参细节，见 §5.3）。

## 5. 途中我自己制造 / 踩到的坑

### 5.1 `ON CONFLICT DO UPDATE` 从不删旧行

修完 `stands.json` 重新入库，DB 里**旧粘连 id 仍在**：
`INSERT ... ON CONFLICT DO UPDATE` 只覆盖、不删除。

→ 加一段「清理已不再产生的角色行」：

```sql
DELETE FROM characters c
 WHERE c.character_id <> ALL(%s)          -- 不在本次产出的 id 里
   AND NOT EXISTS (SELECT 1 FROM stands s WHERE s.owner_id = c.character_id)
```

★ **只删无人引用的**（`NOT EXISTS`）——被 `stands.owner_id` 引用的不能删，会违反外键。

### 5.2 `split_owner_names` 的保护把 Anubis 当过拆

修完 owner，`Caravan SeraiChaka…` 变成了带逗号的一整串（还是一个角色）。
根因：`split_owner_names` 里有条「**拆出 >6 段 → 回退整体**」的保护，
而 **Anubis 有 7 个持有者**（Caravan Serai / Chaka / Four Unnamed mice / Khan /
Jean Pierre Polnareff / Unnamed boy / Cow）——**源站真的就是 7 个**。

→ 保护阈值从 `>6` 放宽到 `>12`，并注释说明「源站确实存在 7 持有者（Anubis）」。
★ 这类「防过拆」的保护**本身就是个假设**：它假设了「正常数据不会有那么多段」。
  假设错了，保护就会把真数据打成异常。

### 5.3 `TEXT[]` 传了 SQL 文本 → `malformed array literal`

`locations.types` 是 `TEXT[]`。我第一版用了本文件的 `array_literal()`
（产出 `ARRAY['a','b']` 这种 **SQL 文本**）塞进 `%s`
→ psycopg2 把它当字符串 → `malformed array literal: "ARRAY['…']"`。

→ INSERT 的 `VALUES` 里**必须传 Python list**（psycopg2 自己适配成数组字面量）；
`array_literal()` 是给 `= ANY(...)` 这种**直接拼接**场景用的。
★ 同一个文件里两种用法并存，用错时不报「参数类型错」而是报
  「数组字面量格式错」——**报错信息离根因很远**。

### 5.4 中文名自动重键会错配

`zh_char_pairs.json` 里粘连 id 挂着多个名字（`['安得列·祊玢','L·A·祊玢']`），
我第一版写「按位置对应」自动搬到新 id。跑完抽查发现错值：

```
thunder_mcqueen → ['白蛇']        # ← 「白蛇」是 Whitesnake 这个**替身**的中文名
```

→ 改成**人工确认表** `zh_char_remap_manual.json`（与 M41「单字名不收」、
M65 中文名同一套做法），测试里专门加一条断言：
「`白蛇` 不该挂在角色上」。

★ 还有一处细节：长名会被 `_char_id` 截断 + 哈希兜底
（`caravan_seraichaka…_0b0ac773`），**用字符串包含去认粘连 id 会失效**
（我第一版只命中 1/7）。正确做法是「**用旧值重算出粘连 id**」（与入库同一条路径）。

## 6. 三类结构性教训

### ① 「有这条数据」≠「这个实体是对的」

`Caravan SeraiChaka…` 这个名字**在 DB 里、能被查出来、有 id、有中文名挂靠**——
它是「一条像样的数据」。但它描述的现实**不存在**。

→ 判据不是「有没有值」，而是「**这个值能不能拆回它描述的那几个东西**」。
本轮为此加了校验门（`sig()` 指纹）和人工确认表。

### ② 修复 ≠ 重建

`INSERT ... ON CONFLICT DO UPDATE` **从不删旧行**；
`split_owner_names` 的防过拆保护会把 7 个真持有者打回一个；
`TEXT[]` 传错载体报的是「数组字面量格式错」。

→ **改数据之后必须重建 + 逐项核对**，不能只改上游文件。
本轮 DB 角色数 178 → **186**，8 个粘连 id 消失、13+ 个新角色出现。

### ③ 「本地能跑」的第三种形态：**那条路径从来没被跑过**

CI 用合成语料（没地点块）、本地库是 M65 之前灌的 → M65 的
「`locations` 表没 loader」「地点块不写 `location_id`」**两边都看不见**。

→ 判定责任归属的办法还是那条老规则：**还原旧版复跑**。
  本轮证实：HEAD 版 `load_db.py` 在 `check_fresh_deploy` 里同样失败
  → 是 M65 留下的，不是本轮引入的。

## 8. 仍已知的局限（不修，记下来）

- **`stand_type` 粘连未修**：45 个替身的类型串仍是粘的
  （`AutomaticShort-Range`）。缩写展开无法确定（`PH` 两种都对得上），
  详见 §3.3。**界面上它会显示成一串**，但不影响按类型筛选以外的功能。
- **13 个角色页抓不到**：名字本身是抓取时就粘上的
  （`Andre BoomboomL.A. Boomboom`），`fetch_articles` 的 target 列表就带着粘名字，
  wiki 上查不到这个「页面」。需要另抓一次详情页才能拆——属 M1 抓取链，单独再排。
- **`_char_id` 的截断 + 哈希**：长名字的 id 人类不可读
  （`caravan_seraichaka…_0b0ac773`）。本轮只保证它**唯一且稳定**。
