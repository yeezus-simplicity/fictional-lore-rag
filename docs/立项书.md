## 1. 为什么做这个项目

### 1.1 定位

一个**企业级 RAG 知识库平台**：从文档接入、解析、切块、索引、混合检索、重排、生成，到服务化、监控、评测的完整链路。

### 1.2 差异化定位：不做「玩具」，做「有工程量的系统」

市面上 90% 的同类项目是「基于 LangChain 的聊天机器人」——面试官一眼能认出。搜索到的评价里已经把这句话列为典型水项目表述：

> 别再写"基于 LangChain 的聊天机器人"了，太水了。

本项目的差异化护城河是三条，全部建立在我的 C++ 后端背景上：

| 差异化点 | 说明 | 面试可讲的深度 |
| --- | --- | --- |
| **量化评测体系** | 自建评测集，每次迭代自动跑 Recall@K / MRR / nDCG / 端到端正确率，出对比表 | 别人只能说"效果不错"，我能说"切块策略 B 相比 A，Recall@5 提升 12.3%，但 P99 延迟增加 40ms，这是取舍" |
| **C++ 高性能服务层** | 检索调度、并发、流式输出用 C++ 实现，讨论内存分配、线程池、批处理 | 唯一能体现 C++ 功力的地方，且是差异化护城河 |
| **成本与延迟工程** | 完整埋点：TTFT / TPOT / token 成本 / 缓存命中率，可视化 | 搜索到的 CSDN 案例里，这个项目让作者直接转岗涨薪 45% |

### 1.3 与已有项目形成叙事闭环

简历上三个项目组成一条完整故事线：

```
[图像处理综合实践]  数据与特征工程能力
        ↓
[RAG 知识库平台]      AI 工程落地能力  ← 本项目，承上启下
        ↓
[Mini 推理引擎]       底层性能优化能力  ← 路线一主攻项目
```

中间这个项目是**连接器**：向上用到了图像/文本特征与检索，向下用到了推理服务的延迟与成本。单独看每个项目都不算惊艳，串起来看就是"一个懂全链路的 AI 系统工程师"。

### 3.2 技术栈

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 解析 | PyMuPDF / unstructured / trafilatura | PDF 版面解析是这个项目的隐藏难点，用主流库而非自己撸 |
| 切块 | 自实现（可插拔策略） | **必须自己写**，这是切块对比实验的前提 |
| Embedding | bge-m3 或 Qwen3-Embedding | 开源、可本地部署、避免 API 依赖，中文效果好 |
| 向量库 | Milvus（主）/ pgvector（轻量备选） | Milvus 是国内工业界标准，面试提及率高 |
| 稀疏检索 | Elasticsearch 或 Milvus BM25 | 混合检索是效果提升最明显的手段之一 |
| 重排 | bge-reranker-v2-m3 | 交叉编码器重排，Recall@5 通常有显著提升 |
| 生成 | Qwen2.5-7B-Instruct（本地）/ API 双通道 | 支持本地部署作为对照组，凸显成本对比 |
| 服务层 | **C++20**（主）+ Python SDK（便捷调用） | 差异化点，简历主战场 |
| 编排 | LangGraph 或自实现轻量状态机 | 自实现更能体现能力，用框架会显得只会调 API |
| 监控 | Prometheus + Grafana | 工业界标准，直接对应 JD「可观测性」 |
| 评测 | 自建评测脚本 + RAGAS 交叉验证 | 自建是主体，RAGAS 做交叉验证防止自说自话 |

### 3.3 C++ 服务层设计要点

这部分是本项目对 C++ 背景的正面回应，每个要点都是面试可深挖的：

1. **流式输出（SSE）**：基于 `epoll`/`io_uring` 的事件循环，chunk 到达即推送。需处理客户端断开检测、慢消费者背压（backpressure）、连接级取消。
2. **并发模型**：检索与生成是两阶段不同耗时的工作，用工作窃取线程池；生成阶段受 GPU 显存约束，需信号量限制并发请求数，超出即排队。
3. **内存管理**：检索结果的生命周期管理，避免长连接下的内存增长。批量场景下用对象池复用缓冲区。
4. **缓存设计**：语义缓存（相似问题直接命中答案）——这是 RAG 服务降本最有效的一招，但要注意相似度阈值误杀，且必须按租户隔离防数据泄露。
5. **多租户隔离**：请求级上下文、限流配额、缓存命名空间、日志审计四层隔离。
6. **可观测性**：全链路 traceId 贯穿，OpenTelemetry 风格埋点，输出 P50/P95/P99 延迟分解（排队 / 检索 / 重排 / 生成首字 / 流式）。

## 5. 数据与评测方案

>⚠️ 业务领域与语料来源待用户指定后填充。方法论部分先行确定，不受领域影响。

### 5.1 语料准备（通用方法论）

1. **选取3–5 类真实文档**，需覆盖：长文档、表格、含图片、章节层级深、更新频繁
2. **构造「脏数据」子集**：扫描件、公式、表格错位、双栏排版——真实企业文档不会是干净的 PDF
3. **文档元信息入库**：来源、版本号、更新时间、密级、章节路径。后续做增量更新与权限隔离都依赖这些字段

### 5.2 评测集构建（最容易被忽略、最能加分）

**这是本项目最重要的一节。** 绝大多数 RAG 项目没有评测集，所以无法证明任何优化有效。

| 部分 | 规模 | 构建方式 |
| --- | --- | --- |
| 问答对 | 150–200 条 | 从文档人工标注，覆盖事实型/多跳型/无答案型/边界型四类 |
| 无答案样本 | ≥ 20 条 | 故意问文档外的问题，考察拒答能力——这是幻觉治理的核心 |
| 多跳问题 | ≥ 20 条 | 需要跨 2–3 个章节综合，回答错说明检索只命中了单块 |
| 客观题 | ≥ 30 条 | 有确定答案的填空/选择，便于自动判分 |

**难题处理**：人工标注 200 条枯燥且容易出错。折中方案——先用大模型批量生成候选问答，再人工只做校验（判断是否正确），成本降低 60%。简历里要写清标注方法，体现评测可信度。

### 5.3 评测指标体系

```
检索层（Retrieval）
├── Recall@K          正确证据是否被召回
├── MRR / nDCG@K      正确证据的排序质量
└── 命中率             正确块出现在 Top-K 的比例

生成层（Generation）
├── 答案正确率         人工/模型判定
├── 忠实度Faithfulness  答案是否完全基于给定上下文（防幻觉）
├── 答案相关度         是否切题
└── 引用准确率         引用的来源是否真的支撑该结论

系统层（System）
├── TTFT              首 token 延迟
├── TPOT              每输出 token 延迟
├── P95 / P99 延迟
├── 吞吐量QPS
├── token 成本         单次问答总成本（元）
└── 缓存命中率
```

**必须产出的核心对比表**（简历素材的直接来源）：

| 版本 | 切块策略 | 检索 | Recall@5 | nDCG@5 | 正确率 | 忠实度 | TTFT | 成本/次 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| v0 朴素基线 | 固定512 | 纯向量 | - | - | - | - | - | - |
| v1 切块优化 | 标题感知 | 纯向量 | - | - | - | - | - | - |
| v2 +混合检索 | 标题感知 | 向量+BM25 RRF | - | - | - | - | - | - |
| v3 +Rerank | 标题感知 | 混合+重排 | - | - | - | - | - | - |
| v4 +语义缓存 | 标题感知 | 混合+重排+缓存 | - | - | - | - | - | - |

**这张表是整个项目最有价值的产出。** 面试时讲不清指标就等于没做。

**写法要点**：
- 每个数据点都必须来自真实评测，不允许估算或编造
- 百分比变化要写清基线（"从 XX% 提升至 XX%"而非"提升 XX%"）
- 保留一个**取舍陈述**（如缓存换来的延迟下降伴随的误命中代价），体现工程判断力
- 若投 AI Infra 岗，把 C++ 服务层那条提到第一位
