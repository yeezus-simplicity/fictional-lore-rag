# M79：句式体检（答非所问 / 没识别出问什么）

> 起因：用户连续报「回答对不上提问」「他无法识别做出正确答案」。
> 于是做了一件本项目**从没做过**的事：**用 20 个真实问句做端到端体检**——
> 每条预先写好「应该是什么答案类型」，起真实服务跑 `/query`，跑完看哪些不符。
>
> 结果：**20 条里 5 条答歪**，其中一条极严重。

## 一、结果（修前 → 修后）

| 问句 | 修前 | 修后 |
|---|---|---|
| 承太郎的替身是什么 | **snippet（返回 Sun 的介绍）** | stand_of → 空条承太郎，共 1 个：白金之星 |
| 乔斯达的替身 | snippet（无关原文） | stand_of → 明确提示 12 个乔斯达，请带全名 |
| 黄金体验有几招 | snippet（人物介绍） | moves → 3 招 |
| 谁打败了普奇 | character_fact（普奇档案） | abstain + 说明本库不含战况 |
| 空条承太郎第一次出场是第几话 | 掉进语义检索 | character_fact，mangadebut = Chapter 113 |
| 白金之星在哪一话出场 | snippet（人物介绍） | appearance → 108 话 |

## 二、五条根因（不是同一种病）

### 【1】★★「承太郎的替身是什么」返回 **Sun**

问句主体是**角色简称**。`STAND_OF_ASK` 命中后走 structured，那条路靠
`extract_stand_name()`，而它**只在替身名表里找**——「承太郎」永远抽不到 →
executor 放弃 → 回退语义检索 → BM25 给了一个高频替身（Sun）。

> 这是最严重的一类答非所问：**答案存在、机制存在，只是没接上**。
> 承太郎的替身是 Star Platinum，Sun 是「阿拉伯之剑」系列的路人替身。

修：`executor._stand_of()` 在两条 SQL 都查不到时，用 `characters.match()` 兜底
（认「承太郎 ⊂ 空条承太郎」）；命中唯一角色就照常给 `stand_of`，
命中多个（歧义姓氏）就**明确要求带全名**，不随机答一个。

> ★★ **这里我第一版走错了路，值得记下来** ★★
> 我第一版改的是**路由**：让「主体是角色」时改走 `character` 维度。
> 结果 5 个测试文件当场变红（M20 / M21 / M25 / M25ui / M66）——
> 因为那会把 `answer_type` 从 `stand_of` 换成 `character_stands`，
> **打破了既有契约**（M25 的多轮追问还依赖 `stand_of.stands` 建立上下文）。
> → **兜底要放在"抽不出名字的那一层"，不要动路由的分类**。
> 同一个 bug，路由层改 = 破契约；执行器层改 = 零破坏。

### 【2】★ 同一个词，**Router 认了、执行器没认**

「黄金体验有几招」：Router 的 `MOVE_ASK` 认「几招」→ 判成 structured；
但 executor 的 `INTENT_MOVES` 没认 → `intent=unknown` → **降级语义检索**。

> 「路由对了、答案还是错的」——两处正则必须同步。
> 同一个坑还有单数出场：`INTENT_APPEARANCE` 只认复数（「哪几话」「哪些话」），
> 「在哪一话出场」「首次登场是第几话」全部掉进语义检索。

### 【3】★★ 库里没有的数据，却拿不相干的内容充数

「谁打败了普奇」→ 问句带着实体名 → 任何分支都会去查角色 → 返回普奇档案。

> **拿不相干的内容充数，比明确拒答更糟**——用户看到的是"完全对不上的介绍"，
> 还会以为系统坏了。

修：`NO_DATA_ASK`（谁打败/谁杀了/怎么死的/死因/宿敌/敌人/谁赢了/战斗结果/结局）
→ abstain，并把「本库有什么、没有什么」讲清楚。

### 【4】「乔斯达的替身」

歧义姓氏（12 个乔斯达）走进语义检索。与【1】同一条修复路径（执行器兜底）——
命中多个角色时**明确要求带全名并列出候选**，而不是随机答一个。

### 【5】「空条承太郎第一次出场是第几话」

角色卡里本来就有 `mangadebut`（**344 / 368** 个角色有），只是没被路由认出来。
修：`CHAR_DEBUT` + 角色命中 → 走角色维度。

## 三、这轮的通用教训

**中文里同一个问法有很多说法**：

| 意思 | 我只列了 | 其余说法（全部掉进语义检索） |
|---|---|---|
| 招式 | 招式 / 有哪些招 / 招数 | **有几招、多少招、几个招式** |
| 出场章节 | 哪几话 / 哪些章节 | **在哪一话、第几话、首次登场** |

而语义检索**永远能返回点什么**，所以界面看起来「有答案」，实际是答非所问——
这是最难被发现的一类 bug：**它不报错**。

**体检脚本本身也值得沉淀**：20 句 × 预期答案类型，已经固化成
`evaluation/test_m79_intent_audit.py`，以后每轮改动都会被它拦一次。

## 四、验证

- `evaluation/test_m79_intent_audit.py`（意图正则 10 项 + 端到端 21 项）全过
- 全套回归：见下节
- 守门未放宽：天气 / 特朗普的替身 / Ora Ora 是什么 仍正确拒答

## 五、遗留（体检里没覆盖、但同类风险还在）

- 「谁和谁认识」「谁喜欢谁」「X 的结局」等**人物关系类**问题：本库无此数据
- 「X 和 Y 谁更强」：需要跨实体比较，当前只有单表极值
- 同一种问法的其它说法（继续扩体检句集才能发现）

# M80：体检第二弹（关系 / 结局 / 比较 / 类型 / 第 N 形态）

M79 结尾说「这三类风险还没覆盖」，于是把 **19 句**加进去再跑一遍：
**8 句不符**，修完 **19/19**。

| 问句 | 修前 | 修后 |
|---|---|---|
| 谁和空条承太郎认识 | character_fact（承太郎档案） | abstain（本库没有人物关系数据） |
| 空条承太郎和乔瑟夫是什么关系 | character_candidates | abstain（同上） |
| 空条承太郎的结局是什么 | character_fact | abstain（没有剧情结局数据） |
| 普奇最后怎么样了 | character_fact | abstain |
| 白金之星和黄金体验谁更强 | snippet（前一个替身的介绍） | **compare**：PWR 5>3；SPD 5=5；RNG 3=3；STA 5>2；PRC 5>3；DEV 5=5 → Star Platinum 3:0 |
| 白金之星是近战型吗 | snippet | **stand_type**：是，近距离型·射程无关·侦查型·自然人型 |
| 白金之星是自动型吗 | snippet | 不是 + 附源站类型原文 |
| 哪些替身是自动型 | snippet | **stand_type_list**：21 个 |
| 杀手皇后第二形态是什么 | snippet | **forms**：源站只列 1 个形态（败者食尘是能力不是形态） |

## 关键点

**① 数据都在，只是没有入口**：`stand_type_cn`（168/188 个替身有中文类型标签）、
`stand_stats`（六维）、`stand_forms`——三个表都从没接过自然语言。

**② 「拿不相干内容充数比拒答更糟」的延续**：关系 / 结局类问句带着实体名，
任何分支都会拿它去查档案。`NO_DATA_ASK` 扩展后明确拒答并说明本库有什么、
没有什么。★ 边界：`乔鲁诺的父亲是谁` 仍走 M77 的亲属问答，不能被误拦。

**③ 比较的口径**：只比**两边都有值**的维度，逐项列出胜负；共同维度少于 3 个
不比（与 `/similar` 同一条口径——缺维度不按 0 计）。

**④ 修 bug 时踩的两个小坑**：`na/nb` 在 verdict 之后才定义 → UnboundLocalError
（名称要先用先取）；测试字符串里嵌 ASCII 双引号 → SyntaxError。

**两次体检合计：39 句，13 条答歪。** 全部已固化进
`evaluation/test_m79_intent_audit.py`（33 项端到端断言 + 意图正则）。

# M81：体检第三弹（多轮追问 + 时间线）14 句 5 条答歪

| 问句 | 修前 | 修后 |
|---|---|---|
| 白金之星有什么招式 → **那它一共出场多少话** | snippet | appearance（108 话） |
| 黄金体验的射程是多少 → **和疯狂钻石比呢** | snippet（疯狂钻石的介绍） | **compare**：PWR 3<5；SPD 5=5；RNG 3>2；STA 2<4；PRC 3<4；DEV 5>3 → Crazy Diamond 3:2 |
| 白金之星一共出场多少话 | snippet | appearance |
| 白金之星动画出场多少集 | snippet | appearance |
| 白金之星在漫画里出场吗 | snippet | **appearance_bool**：出场过：漫画 108 话、动画 65 集 |

## 三个关键点

**① 省略主语的比较**：「和疯狂钻石比呢」**没有代词**，coref 原来只处理「它/他」→
不放行 → 比较只找到疯狂钻石一个 → 返回它的介绍。
→ coref 补主语：以「和/与」开头 + 带比较词 + **句子里没有上一轮实体**。

> ★★ 判据不能用 `guess_stand(q) is None`——问句里往往有**第二个**替身
> （疯狂钻石），那样永远不触发（第一版就是这么失效的）。
> 同时 compare 意图要补**第三种形态**（`和X比`，没有"谁/哪个"），
> 否则 coref 补完主语后正则仍然不匹配。

**② 时间线问法（数量 / 布尔）**：「一共出场多少话」「动画出场多少集」是问**数量**，
「在漫画里出场吗」是**布尔**——两者都没有任何意图认，全掉进语义检索。
→ `INTENT_APPEARANCE` 补数量/布尔分支；`_appearance` 返回 `appearance_bool`
（只答"有没有 + 多少"，不甩整张章节表）。

**③ 三次体检合计：53 句，18 条答歪**，全部固化进
`evaluation/test_m79_intent_audit.py`（单句 33 项 + 多轮 8 组 + 内容核对）。
