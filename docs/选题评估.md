# 选题评估：JoJo 替身知识库平台

> 评估日期：2026-10-02
> 结论：**原始想法不可行，但内核可改造**。需重新定义问题才能立成简历级项目。

---

## 一、原始想法的三个死穴

### 死穴① 规模不匹配（致命）

公开数据集的实际规模：

| 来源 | 记录数 | 字段 |
| --- | --- | --- |
| Kaggle *JoJo Stand Stats* | 156–172 条 | 6 维能力值 + 名称 |
| jojowiki *Stand Stats* | 同上（同一来源） | A–E / None / ∅ / Infinite / ? |
| GitHub `CrabSkin/Jojo-s-Bizarre-Project` | 清洗后 **141 条** | 剔除 Infinite 后 |
| 中文维基「替身」条目 | 第三部起分卷整理 | 能力描述长文本 |

**面试官的反问：**

> "172 条数据，直接把CSV 喂给大模型让它记住不就完了？为什么需要 RAG？"

这个问题答不出来，项目在技术追问环节直接出局。RAG 存在的意义是**语料规模超出上下文窗口、或知识需要频繁更新**——两者都不成立。

### 死穴② 工具选型错误

替身数据是**高度结构化**的：

```
stand_name | PWR | SPD | RNG | STA | PRC | DEV | owner | part | type
Star Platinum | A | A | C(2m) | A | A | A | 空条承太郎 | 3 | 力量型
```

这种数据用向量索引是**反模式**。正确的做法是 SQL：

```sql
SELECT stand_name FROM stands
WHERE PWR = 'A' AND SPD <= 'C'
ORDER BY RNG;
```

一条查询解决的问题，套上 Embedding + 向量库 + Rerank 解决，是**技术上的倒退**，而且面试官一眼能看出来你为了用 RAG 而用 RAG。

### 死穴③ 领域过轻 + IP 风险

- **面试官无感**：技术面看到"JoJo 知识库"，认知标签是"兴趣驱动"，不是"工程能力"
- **无法量化业务价值**：说不出"节省了多少成本 / 提升了多少效率"
- **图片素材有版权风险**：立绘、漫画截图不可入库，公开仓库传播有法律风险
- **叙事局限**：无法与后续的推理引擎项目串成连贯故事线

## 二、可行的改造方案

### 核心洞察

JoJo 数据天然裂成两半，而**这两半的协同问题**恰好是当前工业界最真实的难题：

| 层 | 内容 | 正确工具 |
| --- | --- | --- |
| **结构化事实** | 6 维数值、使用者、所属部、类型、形态 | SQL / 结构化过滤 |
| **非结构化文本** | 能力描述、念写机制、战斗录像、剧情设定 | 向量检索 |

问题不是"怎么做个查设定的机器人"，而是：

> **当一次查询同时需要结构化精确计算和语义理解时，系统如何决策"查哪边"、如何融合两边的结果？**

这是**混合检索（Hybrid Retrieval）** 的核心难题，2026 年工业界仍在攻。换成任何企业场景（HR 政策 + 报销规则 + 合同条款）都是同一类问题。

用 JoJo 当载体的价值：**规模小到能人工核对全量答案**。172 条数据，评测集可以做到 100% 准确标注——这是企业场景根本做不到的。评测可信度是 RAG 项目最难的部分，这里天然解决了。

### 改造后的项目定义

**名称建议**（不要出现"JoJo"字样在项目标题里）：

> **多模态混合检索系统：结构化-非结构化联合推理**
> *Hybrid Structured-Unstructured Retrieval with Text-to-Query Compilation*

**核心子问题**（每一条都是可实验验证的）：

#### ① Text-to-Query 编译（Text-to-SQL 方向）

自然语言问题 → 结构化查询。例：

| 用户问题 | 编译目标 | 难点 |
| --- | --- | --- |
| "哪个替身力量最强但速度最慢" | `WHERE PWR=max AND SPD=min` | 极值推理、多条件组合 |
| "白金之星的能力是什么" | 查 owner 反查 stand | 实体消歧（中英文名、多形态） |
| "DIO 的替身最终变成什么" | 遍历 evolution chain | 链式查询、非等值 JOIN |
| "哪些替身射程超过 10 米且持久力为 C" | 范围解析 | **单位解析**（"2m" vs 等级 C） |

**可量化**：Query 编译准确率、执行结果准确率、无法编译问题的拒答率。

#### ② 检索路由决策（Routing）

给定 query，判断走哪条路径：纯结构化 / 纯语义 / 混合。这是分类问题，可用规则或小模型。

**可量化**：路由准确率、误路由惩罚（该走 SQL 却走了向量检索 → 答案错误）。

#### ③ 混合融合与冲突消解（最核心）

两条路径返回的结果**可能冲突**：

```
Vector path  → "The World 时停 5 秒"（来自能力描述）
SQL path     → The World: STA = E（持续力等级）
Conflict!    → STA 等级与"5 秒"语义矛盾，需消解策略
```

融合策略可对比：加权 RRF / 规则优先 / 置信度仲裁 / 二次验证。

#### ④ 脏数据与冲突知识处理（JoJo 数据的独有难题）

数据集中大量无法直接处理的等级值：

| 异常值 | 出现场景 | 处理难点 |
| --- | --- | --- |
| `Infinite` / `∞` | 诺比 B.I.G、白色专辑部分形态 | **序数 →基数转换失效**（无数值上限） |
| `∅` | 无穷药房、黄金体验镇魂曲 | 缺失 vs 零值语义歧义 |
| `?` | Whitesnake、王白蛇部分维度 | **未知不等于缺失**，与∅ 必须区分 |
| `N/A` | Super Fly | 与缺失的区分 |
| 条件值 | Black Sabbath "※ 依成熟度而定"、Baby Face | **数值随状态变化**，静态表无法表达 |
| 版本冲突 | jojowiki 页修订历史中数值被修正 | **知识时序与来源可信度** |

**这是本项目最独特的技术点**：真实企业知识库同样充满脏数据、单位不一致、版本冲突，但规模大到无法人工穷举。JoJo 规模小，可穷举全量验证处理策略的正确性。

**可量化**：脏数据样本上的处理准确率、冲突检出率、误仲裁率。

#### ⑤ 无答案与幻觉抑制

- **无答案**：问jojowiki 未收录的替身（如替身使者未明的替身）→ 必须拒答
- **部分可答**：问"乔斯达家族的替身"（跨代际、多部）→ 需聚合
- **知识边界**：第六部"石之海"部分设定未公布 → 不可幻觉

**可量化**：无答案集拒答准确率（≥95% 是硬指标）、幻觉率。

#### ⑥ 评测集构建（可100% 人工标注）

| 题型 | 数量 | 标注成本 | 价值 |
| --- | --- | --- | --- |
| 事实型（能力值查询） | 40 | 极低 | 基准准确率 |
| 极值推理 | 30 | 低 | 测结构化计算 |
| 多跳（实体链） | 25 | 中 | 测跨表join |
| 语义理解（能力描述） | 25 | 中 | 测向量检索 |
| 混合（需两侧协同） | 25 | 高 | **核心差异化** |
| 无答案/边界 | 20 | 中 | 测拒答 |
| 脏数据/冲突 | 15 | 高 | **独特考点** |

共 180 条，可全量人工核对 + 交叉校验。

## 三、改造后的差异化对比

| 维度 | 原始版（JoJo 知识库） | 改造版（混合检索系统） |
| --- | --- | --- |
| 核心问题 | 如何检索设定 | 结构化与语义检索如何协同决策 |
| RAG 必要性 | 不必要（172 条） | **必要**（两类数据异构，必须分别处理再融合） |
| 工具选型 | 全部向量检索 | SQL + 向量 + 路由 + 融合，**按数据性质选型** |
| 技术深度 | 浅（调API + 拼prompt） | 深（Text-to-Query、路由、冲突消解、脏数据） |
| 评测可信度 | 低（LLM 判分循环论证） | **高**（全量人工标注，可交叉验证） |
| 业务迁移性 | 差 | **强**（HR/法务/财务知识库同构问题） |
| 简历可讲性 | "我做了个查设定的" | "我解决了两类异构知识联合推理的冲突问题" |
| 面试官反应 | "他喜欢 JoJo" | "这个设计意识可以" |

## 四、保留 JoJo 作为载体的额外收益

1. **可100% 穷举验证**：172 条数据，每条问题的正确答案都能人工确认，这在任何企业场景都做不到
2. **数据公开无授权风险**：统计数据（能力值）为事实性数据，标注来源即可
3. **视觉化呈现有说服力**：六维能力雷达图、替身关系图谱，演示效果强
4. **叙事有辨识度**：一个 C++ 后端做 JoJo 设定检索，记忆点强，面试时是加分而非减分
5. **与已有项目互补**：图像处理项目里用过CUB-200 图像特征，与多模态检索天然呼应

## 五、风险与规避

| 风险 | 规避 |
| --- | --- |
| 被质疑"用 JoJo 不严肃" | 项目标题与README **完全不提 JoJo**，只提"结构化-非结构化混合检索"。JoJo 语料作为 `dataset/` 下的可替换数据集出现 |
| 被质疑"数据太小没意义" | 在技术文档中明确论证：**本项目研究的是检索决策机制，语料规模不是变量**。附上"同一套检索逻辑在企业知识库上的迁移路径" |
| 赛道太窄 | 补充一组真实企业文档作为第二个数据集，验证方案的通用性（**这一条强烈建议做**） |
| 版权 | 只用事实性统计数据 + 能力描述文本，注明来源与用途；**不使用任何图片/漫画截图** |

## 六、与企业文档版 RAG 的关系（决策点）

| | 纯 JoJo 版 | 纯企业文档版 | **双数据集版（推荐）** |
| --- | --- | --- | --- |
| 技术深度体现 | 强（混合检索） | 中（纯文本 RAG） | **强** |
| 评测可信度 | 极高（可穷举） | 中（需大模型标注） | **高** |
| 业务说服力 | 弱 | 强 | **强** |
| 工作量 | 小 | 中 | **中** |
| 简历叙事 | 需包装 | 直观 | **有层次** |

**建议**：JoJo 数据集作为**主数据集**（深度挖掘混合检索难题），企业文档作为**验证集**（证明方案可迁移）。两份评测集互相验证，既保深度又保说服力。
