## 1. 第一部分：rendered 快照缺口

### 1.1 怎么发现的

M70 结尾我列了下个方向，第一条就是「补 rendered 快照缺口」。
查证过程：

```
dataset/sources/rendered/  只有 148 个快照
替身（stands.json）         187 个
★ 缺 40 个 → 这些替身的出场记录/必杀技恒为空
```

而 `stand_appearances` 正是从 `rendered/*.json` 解析的
（`database/collect_extras.py` → `tools/render_fetch.js` 抓的渲染快照）。

### 1.2 上游比快照更旧

继续往上查：`details.json`（render_fetch 的输入）只有 **154** 条，
时间戳 10月3日 —— 比 M39–M45 补第 8/9 部替身还早。

```
details.json      154 条（10-03，M39–M45 之前）
rendered/         148 个快照
stands.json       187 个替身（当前）
```

### 1.3 ★ 这是同一类问题的第三次

| 轮次 | 问题的形状 |
|---|---|
| M68 | 角色页「从没进过抓取队列」—— target 名单是运行时从旧 stands.json 生成的 |
| M70 | 抓取名单有盲区 —— 从 `owner_name` 反推，非持有者角色永远进不来 |
| **M71** | **下游产物没跟着上游数据重算** —— 补了第 8/9 部替身，但 rendered 快照、出场记录都没重建 |

三次共同的根：**上游数据增长了，下游产物停在旧状态，而输出看着完全正常**。

### 1.4 修法与结果

没有重跑整条旧管道（那会重抓主表），而是：

1. 从 `articles.json`（已有全部 187 个替身页）补出缺失的 37 条 details 条目
2. `node render_fetch.js --only <37个id>` 只抓缺的
3. 重跑 `load_db --load`

```
快照            148 → 185
出场记录        4111 → 4902 条
有出场记录的替身 145 → 182 个
必杀技          19 → 23 条（覆盖 11 个替身）
37/37 全部抓取成功，0 失败
```

### 1.5 剩余 6 个缺口是真实情况，不是解析失败

```
第4部 (3):  Echoes (ACT1/2/3)     ← 没有独立 wiki 页面（M1 已记录）
无部号 (3): Remote Romance / House of Holy / Smallfaces
```

后三个查了快照：它们的 `APPEARANCE` 段讲的是**外观长相**
（"Smallfaces manifests as paper which can be folded like origami…"），
不是话数出场 → `battles=0` 是**正确的**。

## 2. 第二部分：篇章语料证据链

### 2.1 ★ 核心陷阱：章号口径不统一

源站章节编号有**两种互不兼容的口径**：

| 部 | 形态 | 实例 |
|---|---|---|
| 第 1–5 部 | **绝对章号**，连续编号 | `Chapter 419: Bites the Dust, Part 4` |
| 第 6–9 部 | **部内相对章号 + 作品名** | `JoJolion Chapter 22: Morioh 1901 (ACT4)` |

而 `story_arcs.json` 的 `chapters` **全部是部内相对**（带前缀）：
`JJL 18-22` / `SBR 1-4` / `DU 153-162`。

**直接匹配的后果**：把 `DU 153-162` 拿去和绝对章号比 → **0 个替身**
（实测 Killer Queen 明明在第 4 部 418–427 章出场，一条都匹配不上）。

→ 两侧都换算到绝对章号后再比，偏移：
```
第1部 +0   第2部 +44   第3部 +113   第4部 +265   第5部 +439
```
偏移判据（用「替身已知部号 + infobox 的 manga_debut」反推，不靠记忆）：
第 3 部替身最早登场 Chapter 114 → 第 3 部绝对起点 114 → 偏移 113。

### 2.2 第二类必须排除的：外传作品

`stand_appearances` 里混着非正传作品（90+ 条）：
`Crazy Heartbreakers` / `Purple Haze Feedback` / `JORGE JOESTAR` /
`Iggy the Stray Dog` … 它们的章号**各自从 1 重新编号**。

**不排除的后果**：只按章号范围查「第 7 部 ch1-4」会误撞出 **37** 个替身，
而正确结果只有 **1** 个（`In a Silent Way`，正是该段反派 Sandman 的替身）。
→ 按用户口径（只 9 部正传）排除，实测排除 175 条。

### 2.3 结果

```
篇章 189 个：有替身关联 164 / 区间判不出 1 / 区间内无出场 24
有替身关联的篇章按部：第1部 1  第3部 28  第4部 27  第5部 26
                      第6部 26  第7部 25  第8部 22  第9部 9
```

关键案例（全部经人工核对）：

| 篇章 | 部 | 区间 | 圈出的替身 |
|---|---|---|---|
| Shakedown Road | 8 | JJL 18-22 | **Les Feuilles**、Soft & Wet、Nut King Call、Paisley Park、Tusk |
| San Diego Beach | 7 | SBR 1-4 | In a Silent Way ✓（该段反派 Sandman 的替身） |
| Another One Bites the Dust | 4 | 绝对 418-427 | Killer Queen、Bites the Dust、Crazy Diamond…（11 个） |
| Anubis | 3 | 绝对 193-198 | Anubis、Silver Chariot、Star Platinum |

★ `Les Feuilles` 是**勒索之路现象的真正来源**，也正是 M70 答案里漏掉的那个。

### 2.4 现在能答了

```
问：篇章 勒索之路 的替身是什么
答：篇章：Shakedown Road（第8部）· 章节 JJL 18-22
     该篇章章节范围内出场的替身：
     Les Feuilles ch18 · Soft & Wet ch19 · Nut King Call ch20
     Paisley Park ch21 · Tusk ×5 ch22
     ★ 另有同名地点，口径不同（问地点请去掉「篇章」二字）
```

每条替身都带**最早出场话数 + 原文片段**（悬停可见），可回查。
没提「篇章」二字时仍走地点口径，不抢答。

## 3. 这轮踩的坑

### 3.1 ★ 列名误导：`stand_forms.parent_id` 不是父替身

第一次写形态折叠时，我按列名字面意思建映射：

```python
form_parent = {sid: pid for sid, pid in cur.fetchall()}   # ❌ 写反了
```

而 `stand_forms.parent_id` 存的是**形态标签**（`form_0` / `tusk__f2` 这种
form_id），真正的父替身在 `stand_id` 列。

**后果很隐蔽**：得到 `{'tusk': 'tusk__f2'}` → 真实的 Tusk 出场被**改名**成
`tusk__f2`，而 DB 里没这个 id → `name_en` 变成 None → 前端显示字面量 "None"。
35 条记录受影响，而我一开始以为是「DB 里缺名字」。

改走命名规则 `^(echoes|tusk)_act\d+$`（与 load_db 建聚合父记录**同一条正则**，
两边规则一致才不会对不上）。

### 3.2 名字要从 DB 取，不能从 stands.json 取

`echoes` / `tusk` 这两个聚合父记录是 load_db **现场合成**的
（M1 遗留的形态组未消解），`stands.json` 里没有它们 →
从文件取名会让 16 条出场记录的 `name_en` 为 None。

### 3.3 闸门连续两次抓到口径不一致

给 `collect_metrics` 加「出场记录数」闸门时：

```
第一次：对外写 4902，产物是 2739   ← 我只数了漫画，DB 是全 kind
第二次：对外写 4902，产物是 4806   ← 少算了 echoes/tusk 两个聚合父
```

两次都是**我的统计口径与 DB 不一致**，而闸门每次都准确指出来了。
第三次才对上（4902 / 182）。

> ★ 这道闸门证明了自己的价值：如果靠我"看着差不多"就填数，
> 这三个数字会一直是错的。

### 3.4 后台 shell 的 `/tmp` 与前台不是同一个

第一次用 `nohup ... &` 起抓取，子进程读不到我在前台写的 `/tmp/only_ids.txt`
（报 `cat: /tmp/only_ids.txt: No such file or directory`）。
→ 临时文件放项目目录内。

## 5. 遗留

- **24 个篇章区间内无替身出场**。多为源站该替身无 Appearance 段
  （如 Smallfaces 那段讲的是外观），或篇章以叙事为主。
  已在数据里逐条注明 `note`，不硬凑。
- **27 个篇章判不出部号**（源站 `part` 字段为空），如 `Sun`、`Tusk`。
- **1 个篇章章节区间无法解析**（`a_letter_from_the_past` 的
  `Chapters 6 - 7` 与正传编号体系对不上），已标 `note` 不猜。
- **角色 ↔ 篇章的证据链还没建**（目前只有替身 ↔ 篇章）。
  `characters` 表没有出场记录，要做需另抓角色页的 Appearance 段。
- 快照补齐只做了 `--only` 增量；`details.json` 仍是 154+37 混合来源，
  下次若再新增替身，需要重跑一次「补 details → 抓快照 → load_db」三步。
